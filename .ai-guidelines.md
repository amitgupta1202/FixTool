# AI Development Guidelines

This document provides guidelines for AI assistants (like Claude Code) working on this project.

## 🔀 Branch Management

### Always Use Feature Branches

- **NEVER commit directly to `main`** or the primary branch
- Create a descriptive feature branch for each task
- Branch naming convention: `feature/`, `fix/`, `refactor/`, `docs/`

```bash
# Good examples:
git checkout -b feature/add-session-timeout
git checkout -b fix/connection-retry-logic
git checkout -b refactor/simplify-message-parser

# Bad examples:
git checkout -b temp
git checkout -b changes
git checkout -b bug
```

### When to Create a Branch

- Before starting ANY code changes
- At the beginning of the conversation if working on a feature
- Exception: Documentation-only updates to non-code files (with user approval)

## 📝 Commit Message Guidelines

### What NOT to Include

❌ **DO NOT mention:**
- Test pass/fail status (e.g., "All tests passing", "246 tests pass")
- AI tool usage (e.g., "Generated with Claude Code", "AI-assisted")
- Co-Authored-By lines (e.g., "Co-Authored-By: Claude <...>")
- Implementation details about testing frameworks
- Personal notes or observations

### What TO Include

✅ **DO include:**
- Clear, concise description of WHAT changed
- WHY the change was necessary (root cause for bugs)
- WHAT the impact/benefit is
- Breaking changes (if any)

### Commit Message Format

```
<type>: <short summary>

<detailed description of what changed and why>

<optional: list of changes>

<optional: breaking changes or migration notes>
```

#### Types
- `feat:` New feature
- `fix:` Bug fix
- `refactor:` Code refactoring (no functionality change)
- `docs:` Documentation updates
- `test:` Adding or updating tests
- `chore:` Maintenance tasks

#### Good Examples

```
fix: Prevent message routing to wrong session with duplicate credentials

Root cause: QuickFIX identifies sessions using BeginString, SenderCompID,
TargetCompID, and SessionQualifier. Multiple connection profiles shared
identical credentials with no SessionQualifier, causing QuickFIX to treat
them as the same session.

Changes:
- Add sessionQualifier field to FixConnectionConfig
- Update FixConnectionManager to include SessionQualifier in settings
- Add SessionQualifier input field to ConnectionPanel UI
- Migrate existing profiles with appropriate qualifiers

This ensures each session has a unique QuickFIX SessionID.
```

```
feat: Add connection retry logic with exponential backoff

Adds automatic reconnection when FIX connection is lost unexpectedly.
Implements exponential backoff (1s, 2s, 4s, 8s, max 30s) with configurable
maximum retry attempts.

Changes:
- Add RetryStrategy class with backoff calculation
- Update FixConnectionManager to handle connection failures
- Add retry settings to ConnectionPanel UI
```

#### Bad Examples

```
❌ fix: Fixed the session bug (all 246 tests passing)
❌ feat: Add new feature. Generated with Claude Code.
❌ update: Made some changes to connection logic. Tests work now!
❌ feat: Add feature

   Co-Authored-By: Claude <noreply@anthropic.com>
```

## 🧪 Testing Guidelines

### Test Coverage Requirements

- **Write tests for ALL code changes** (no exceptions)
- **Prefer integration tests** over unit tests when practical
- **Include E2E tests** for critical user workflows
- **Keep tests simple** - avoid overly complex test setups

### Test Priority

1. **Integration Tests** (Highest Priority)
   - Test multiple components working together
   - Verify actual behavior users will experience
   - Example: Test connecting to profile + sending message + receiving response

2. **E2E Tests** (High Priority for critical paths)
   - Test complete user workflows
   - Cover happy path and common error scenarios
   - Example: Create profile → Connect → Send message → Verify delivery

3. **Unit Tests** (Medium Priority)
   - Test individual functions/classes in isolation
   - Use for complex business logic
   - Keep mocking to a minimum

### Test Simplicity Guidelines

✅ **Good Test Characteristics:**
- Clear test name describing what is being tested
- Single assertion or closely related assertions
- Minimal setup (use helper functions for common setup)
- Easy to understand what failed when test breaks

❌ **Avoid:**
- Tests that require extensive mocking (5+ mocks)
- Tests that depend on execution order
- Tests with complex async/threading logic
- Tests that test implementation details vs behavior

### Test Coverage Areas

When making changes, ensure tests cover:
- ✅ **Happy path**: Normal successful operation
- ✅ **Edge cases**: Empty inputs, null values, boundary conditions
- ✅ **Error handling**: Network failures, invalid data, timeouts
- ✅ **Integration points**: How components interact
- ⚠️ **Backward compatibility**: Ensure old data/configs still work

### Example Test Structure

```kotlin
// GOOD: Integration test
@Test
fun testConnectAndSendMessageToCorrectSession() {
    val profile1 = createProfile(sessionQualifier = "DEV1")
    val profile2 = createProfile(sessionQualifier = "LOCAL")

    // Connect both
    session1.connect(profile1.config)
    session2.connect(profile2.config)

    // Send message to session1
    val message = createTestMessage()
    session1.sendMessage(message)

    // Verify message sent from session1's connection
    assertMessageSentFrom(session1, message)
}

// AVOID: Overly complex unit test with many mocks
@Test
fun testSendMessage() {
    val mockConnection = mock<Connection>()
    val mockSession = mock<QuickFixSession>()
    val mockDictionary = mock<Dictionary>()
    val mockValidator = mock<Validator>()
    val mockParser = mock<Parser>()
    // ... many more mocks

    // Complex setup
    whenever(mockConnection.getSession()).thenReturn(mockSession)
    whenever(mockSession.send(any())).thenReturn(true)
    // ... many more mock setups

    // Test becomes brittle and hard to maintain
}
```

## 📚 Documentation Guidelines

### Keep README Up to Date

When making changes that affect:
- **Features**: Update feature list
- **Setup**: Update installation/configuration instructions
- **Usage**: Update usage examples
- **Dependencies**: Update requirements
- **Breaking changes**: Add migration guide

### README Update Checklist

- [ ] Version number (if applicable)
- [ ] New features added to feature list
- [ ] New configuration options documented
- [ ] New dependencies listed
- [ ] Examples updated if API changed
- [ ] Migration guide for breaking changes

### Code Documentation

- Add KDoc comments for public APIs
- Document WHY, not just WHAT (code shows what)
- Update comments when code changes
- Remove outdated comments

## 🧹 Code Cleanup

### Remove Unused Code

Always check for and remove:
- ✅ Unused imports
- ✅ Commented-out code
- ✅ Dead code (unreachable code)
- ✅ Unused variables/parameters
- ✅ Unused private functions
- ✅ Deprecated code (after migration period)

### Before Committing

Run these checks:
```bash
# Check for unused code (if using detekt)
./gradlew detekt

# Look for TODO comments added during development
git diff | grep -i "TODO\|FIXME\|HACK"

# Check for debug logging
git diff | grep -i "println\|console.log"
```

### Refactoring Guidelines

- Remove duplicate code
- Extract complex logic into well-named functions
- Keep functions small (< 60 lines)
- Use meaningful variable names
- Remove magic numbers (use constants)

## 🔒 Security & Secrets

### NEVER Commit

- ❌ API keys, passwords, tokens
- ❌ Connection credentials
- ❌ Organization-specific data
- ❌ Email addresses (use `user@example.com` in tests)
- ❌ Server hostnames (use `localhost` or `example.com` in tests)

### Test Data Guidelines

Use only generic test data:
- `SENDER_CLIENT`, `BUYER_FIRM`, `SELLER_FIRM`
- `TARGET_SERVER`, `EXCHANGE_TARGET`
- `test@example.com`, `user@test.com`
- `localhost`, `test.example.com`
- `DEV1`, `LOCAL`, `QA1`, `STAGING`

## 🔄 Workflow Summary

### Standard Development Workflow

1. **Start**: User describes the task
2. **Plan**: Understand requirements, identify affected components
3. **Branch**: Create feature branch with descriptive name
4. **Implement**: Write code following project conventions
5. **Test**: Write integration/E2E tests (preferably before or alongside code)
6. **Verify**: Run all tests, ensure they pass
7. **Cleanup**: Remove unused code, update imports
8. **Document**: Update README and code comments if needed
9. **Commit**: Write clear commit message (no test status, no AI mentions)
10. **Review**: Ask user if they want to review before pushing

### Before Committing Checklist

- [ ] Code compiles without errors
- [ ] Tests written for all changes
- [ ] All tests pass locally
- [ ] Unused code removed
- [ ] No debug/console logging
- [ ] No TODOs/FIXMEs without issue tracking
- [ ] README updated (if needed)
- [ ] No secrets or org-specific data
- [ ] Commit message follows guidelines

## 📦 Project-Specific Guidelines

### This Project (FixTool)

#### Technology Stack
- Kotlin Multiplatform (JVM)
- Compose for Desktop UI
- QuickFIX/J for FIX protocol
- Kotlinx.serialization for JSON

#### Testing Approach
- Prefer Compose UI tests for UI components
- Integration tests for service interactions
- Mock external dependencies (FIX servers, file system)
- Use `composeTestRule` for UI tests
- Keep test data in `src/jvmTest/resources` if needed

#### Code Style
- Follow Kotlin conventions
- Use data classes for models
- Prefer immutability
- Use coroutines for async operations
- Avoid nullable types when possible

#### File Organization
```
composeApp/src/
├── jvmMain/kotlin/com/knapsack/fixtool/
│   ├── model/           # Data models
│   ├── service/         # Business logic, external integrations
│   ├── ui/              # Compose UI components
│   ├── viewmodel/       # UI state management
│   └── util/            # Utility functions
└── jvmTest/kotlin/com/knapsack/fixtool/
    ├── model/           # Model tests
    ├── service/         # Service tests
    ├── ui/              # UI component tests
    └── integration/     # Integration/E2E tests
```
