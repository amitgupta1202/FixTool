# FixTool

A desktop UI-based FIX client tool for manual testing of FIX protocol communications. FixTool provides a comprehensive environment for constructing, sending, receiving, and inspecting FIX messages.

## Features

- **Message Construction**: Build FIX messages with an intuitive UI, supporting standard fields and repeating groups
- **FIX Client Connectivity**: Connect to FIX servers as a client with configurable connection profiles
- **FIX Acceptor Mode**: Run FixTool as a FIX server to accept incoming connections and respond to messages
- **SSL/TLS Support**: Secure connections with full SSL/TLS support for encrypted FIX sessions
- **Message Inspection**: View and analyze incoming and outgoing FIX messages in real-time
- **Session Management**: Manage multiple FIX sessions with connection profiles
- **Multi-Session Load Testing**: Open up to 100 concurrent sessions from one profile, with per-session identities via `{n}` numbering patterns or comma-separated CompID lists
- **Bulk Send**: Send one message to all logged-on sessions at once, with template expressions re-resolved per session
- **Message Validation**: Validate messages against FIX data dictionaries
- **Saved Messages**: Save and reuse frequently used message templates

This is a Kotlin Multiplatform project built with Compose Multiplatform, targeting Desktop (JVM). The project uses QuickFIX/J for FIX protocol implementation.

## Development

### Prerequisites

- JDK 17 or higher
- Gradle (wrapper included)

### Build and Run

To build and run the development version of the desktop app:

**macOS/Linux:**
```shell
./gradlew :composeApp:run
```

**Windows:**
```shell
.\gradlew.bat :composeApp:run
```

Alternatively, use the run configuration from your IDE's toolbar.

### Running Tests

To run all tests:

**macOS/Linux:**
```shell
./gradlew :composeApp:jvmTest --no-daemon
```

**Windows:**
```shell
.\gradlew.bat :composeApp:jvmTest --no-daemon
```

To run a specific test class:
```shell
./gradlew :composeApp:jvmTest --tests "com.knapsack.fixtool.ui.ConnectionPanelTest" --no-daemon
```

To run a specific test method:
```shell
./gradlew :composeApp:jvmTest --tests "com.knapsack.fixtool.ui.ConnectionPanelTest.testAutoGeneratedProfileNamePopulatesInputField" --no-daemon
```

Add `--info` flag for detailed test output.

### Building Executables

This will create a platform-specific executable in the `composeApp/build/compose/binaries/main/` directory.

### Releasing

2. Find the draft release
3. Upload the macOS `.dmg` file (built in Step 1)
4. Edit release notes as needed
5. Publish the release ✅

**Testing:** Create a release candidate tag first (e.g., `v1.0.0-rc1`) to test the workflow before the official release.

### 1. Static Code Analysis - Detekt

**What it does:**
- Analyzes Kotlin code for code smells, complexity issues, and potential bugs
- Checks for common anti-patterns and style violations
- Helps maintain code quality and consistency across the project

**Configuration:**
- Config file: `config/detekt/detekt.yml`
- Baseline file: `config/detekt/baseline.xml` (tracks existing issues)
- Rules are tuned for Compose Multiplatform projects

**Commands:**

Run static analysis:
```shell
./gradlew detekt
```

Generate a new baseline (use when accepting current issues):
```shell
./gradlew detektBaseline
```

**Reports Location:**
- HTML: `composeApp/build/reports/detekt/detekt.html`
- XML: `composeApp/build/reports/detekt/detekt.xml`
- TXT: `composeApp/build/reports/detekt/detekt.txt`
- SARIF: `composeApp/build/reports/detekt/detekt.sarif`
- Markdown: `composeApp/build/reports/detekt/detekt.md`

**What it checks:**
- Complexity (cyclomatic complexity, nested blocks)
- Code smells (long methods, large classes, too many parameters)
- Potential bugs (empty catch blocks, unreachable code)
- Performance issues (unnecessary instantiations)
- Naming conventions
- Best practices

**Tips:**
- Review the baseline file periodically and work to reduce issues
- New issues will fail the build, encouraging immediate fixes
- Use `@Suppress("RuleName")` sparingly for false positives

### 2. Code Formatting - ktlint

**What it does:**
- Enforces consistent Kotlin code style across the project
- Automatically fixes formatting issues
- Integrates with `.editorconfig` for IDE consistency

**Configuration:**
- EditorConfig: `.editorconfig`
- Max line length: 150 characters
- Compose-friendly rules (allows PascalCase for Composable functions)
- Trailing commas enabled

**Commands:**

Check code formatting:
```shell
./gradlew ktlintCheck
```

Auto-fix formatting issues:
```shell
./gradlew ktlintFormat
```

**Disabled Rules (for Compose compatibility):**
- `standard:function-naming` - Allows PascalCase Composable functions
- `standard:backing-property-naming` - For StateFlow patterns
- `standard:no-consecutive-comments` - For documentation style

**Tips:**
- Run `ktlintFormat` before committing code
- Configure your IDE to use the `.editorconfig` settings
- Most IDEs (IntelliJ IDEA, Android Studio) will auto-format on save

**Integration with IDEs:**
The project includes an `.editorconfig` file that most modern IDEs will automatically recognize and apply. This ensures consistent formatting across all developers.

### 3. Test Coverage - JaCoCo

**What it does:**
- Measures how much of the codebase is covered by unit tests
- Generates HTML and XML reports showing line and branch coverage
- Helps identify untested code paths

**Configuration:**
- Configured in `composeApp/build.gradle.kts`
- Automatically runs after test execution
- Excludes generated code and test classes

**Commands:**

Run tests and generate coverage report:
```shell
./gradlew :composeApp:jvmTest jacocoTestReport
```

**Reports Location:**
- HTML Report: `composeApp/build/reports/jacoco/jacocoTestReport/html/index.html`
- XML Report: `composeApp/build/reports/jacoco/jacocoTestReport/jacocoTestReport.xml`

**Understanding Coverage Reports:**
- **Green lines**: Covered by tests
- **Red lines**: Not covered by tests
- **Yellow lines**: Partially covered (some branches not tested)

**Coverage Metrics:**
- **Line Coverage**: Percentage of code lines executed by tests
- **Branch Coverage**: Percentage of conditional branches tested
- **Method Coverage**: Percentage of methods called by tests

**Tips:**
- Aim for 70-80% coverage for business logic
- 100% coverage is not always necessary or practical
- Focus on testing critical paths and complex logic
- UI code (Composables) is harder to test and may have lower coverage

### Dependency Management

This project uses Gradle Version Catalogs for centralized dependency management.

**Configuration File:** `gradle/libs.versions.toml`

**Benefits:**
- Single source of truth for all dependency versions
- Type-safe accessors in build scripts
- Easy to update dependencies across the project
- Prevents version conflicts

**Structure:**
```toml
[versions]
kotlin = "2.2.20"
compose = "1.9.0"

[libraries]

[plugins]

```

**Adding a new dependency:**
1. Add version to `[versions]` section
2. Add library to `[libraries]` section
3. Reference it in build.gradle.kts: `implementation(libs.library.name)`

### Troubleshooting

**Issue: ktlint fails on generated code**
- Generated code is automatically excluded via `.editorconfig`
- If needed, add exclusions in `composeApp/build.gradle.kts`

**Issue: Detekt reports too many issues**
- Run `./gradlew detektBaseline` to create a baseline
- The baseline allows existing issues but catches new ones

**Issue: Tests fail intermittently**
- Some UI tests may be timing-sensitive
- Run tests with `--rerun-tasks` to bypass cache

**Issue: Coverage report not generated**
- Ensure tests run successfully first
- Coverage is only generated if tests pass

## Contributing

Contributions are welcome! Please follow these guidelines:

### Development Workflow

1. **Create a feature branch** for your changes (never commit directly to main)
   ```bash
   git checkout -b feature/your-feature-name
   git checkout -b fix/bug-description
   ```

2. **Write tests** for all changes
   - Prefer integration/E2E tests over unit tests
   - Keep tests simple and maintainable
   - See [TEST_SUGGESTIONS.md](TEST_SUGGESTIONS.md) for testing guidelines

3. **Follow code quality standards**
   - Run `./gradlew detekt` before committing
   - Run `./gradlew ktlintFormat` to auto-format code
   - Ensure all tests pass: `./gradlew jvmTest`

4. **Write clear commit messages**
   - Describe WHAT changed and WHY
   - Don't mention test status or tools used
   - Don't include Co-Authored-By lines
   - Follow conventional commit format (feat:, fix:, docs:, etc.)

5. **Update documentation**
   - Update README if adding features or changing setup
   - Add KDoc comments for public APIs
   - Remove unused code and comments

### AI-Assisted Development

If using AI tools (like Claude Code, GitHub Copilot, etc.) to assist with development, please follow the guidelines in [.ai-guidelines.md](.ai-guidelines.md). This ensures consistency and quality across AI-assisted contributions.

Key AI guidelines:
- Always use feature branches
- Write tests for all changes
- Use generic test data (never commit secrets or org-specific credentials)
- Keep README up to date
- Remove unused code

### Security

- Never commit API keys, passwords, or credentials
- Use generic test data in tests (e.g., `test@example.com`, `localhost`)
- User configuration in `~/.fixtool/` is not tracked by git
