1. Getting Started

What is FixTool?

FixTool is a desktop application for working with the FIX (Financial Information eXchange) protocol. It allows you to:

  • Connect to FIX servers and receive messages
  • Send FIX messages with custom field values
  • View and analyze message history
  • Search and filter messages
  • Create reusable message templates

Quick Start

  1. Click Start Demo Server in the toolbar to launch the built-in FX exchange
  2. Select one of the auto-created Demo User profiles
  3. Click Connect to establish a FIX session
  4. Use the pre-loaded FX templates to send orders and receive fills
New to FixTool? Start with the Demo FX Server - it's the fastest way to explore FIX messaging without any external dependencies.

Overview

FixTool includes a built-in FX exchange simulator that provides a realistic trading environment for testing and learning. The demo server:

  2. The server starts on localhost:19876
  3. Four demo profiles are automatically created: Demo User 1-4
  4. Six FX message templates are added to the saved messages
Tip: Multiple demo users allow you to simulate multi-party trading scenarios. Connect with different profiles to see how messages flow between counterparties.

Order Types and Execution

Market Orders (OrdType=1)

Market orders are filled immediately at the current market price:

  • Buy orders fill at the current ask (offer) price
  • Sell orders fill at the current bid price
  • You receive an ExecutionReport (35=8) with ExecType=2 (Fill)

Limit Orders (OrdType=2)

Limit orders specify a maximum buy price or minimum sell price:

  • Marketable limit orders (buy at/above ask, or sell at/below bid) fill immediately
  • Non-marketable limit orders rest in the order book and receive OrdStatus=0 (New)
  • Resting orders fill automatically when the price ticks to touch your limit

Example: Limit Order Lifecycle

  1. Current EUR/USD: Bid=1.0890, Ask=1.0893
  2. You send: Buy limit at 1.0850 (below market)
  3. Server responds: ExecutionReport with OrdStatus=0 (New) - order is resting
  4. Price ticks down... eventually Ask reaches 1.0850
  5. Server sends: ExecutionReport with OrdStatus=2 (Filled) at 1.0850

Price Simulation

The demo server simulates realistic market movement:

  • Prices tick every 1 second
  • Each tick moves prices 0-3 pips in either direction
  • Spreads vary between 2-5 pips
  • Resting limit orders are checked and filled when prices move

Message Type Name Server Response

35=F OrderCancelRequest ExecutionReport (Canceled) or OrderCancelReject (35=9)

3. Managing Connections

Creating a Connection Profile

Connection profiles store your FIX session configuration for reuse:

  1. Click New Connection in the toolbar
  2. Fill in the connection details:
    • Profile Name: A friendly name for this connection
    • Host: FIX server hostname or IP address
    • Port: FIX server port number
    • SenderCompID: Your FIX session identifier
    • TargetCompID: Server's FIX session identifier
    • BeginString: FIX protocol version (e.g., FIX.4.2, FIX.4.4)
  3. Click Save Profile to save for later use
  4. Click Connect to start the session

Multiple Sessions per Profile (Load Testing)

A profile can open several concurrent FIX sessions in one click - useful for market data load testing. Set the Sessions field (initiator connections only, 1-100) and click Connect: each session opens as its own tab, named Profile Name [1], Profile Name [2], and so on.

Each session needs its own identity. When Sessions is greater than 1, the identity fields (SenderCompID, TargetCompID, Username, Password) accept three forms:

Form Example Result (3 sessions)
Numbering pattern LOADGEN{n} LOADGEN1, LOADGEN2, LOADGEN3. Use {nn} for zero-padding: LOADGEN01, LOADGEN02, ...
Comma-separated list SESS_A, SESS_B, SESS_C Session 1 gets SESS_A, session 2 gets SESS_B, etc. The list must contain exactly 1 or N values - anything else is rejected before connecting.
Single plain value LOADGEN Shared by all sessions. A unique SessionQualifier is derived per session automatically so the sessions stay separate on the client side.

Each field resolves independently, so for example 10 sessions can share one password while having 10 different usernames. The panel shows a live preview of the resolved identities and the aggregated group status, e.g. Logged On (3/3).

Shared CompIDs: a single plain SenderCompID/TargetCompID only works if the server accepts multiple concurrent logons with the same CompIDs - many venues reject the second logon. If your server assigns distinct session IDs, use a numbering pattern or a list.
  • Disconnect stops every session in the group
  • Connect reconnects any sessions that are down and re-opens closed session tabs until the configured count is reached
  • Profile edits take effect when a session reconnects
Load test setup: configure the profile once (e.g. SenderCompID LOADGEN{nn}, Sessions 10), then copy ~/.fixtool/connection_profiles.json and ~/.fixtool/saved_messages.json to the other machines.

Demo Server

For testing and learning, use the built-in Demo FX Server (see Section 2). It provides:

  • A realistic FX exchange simulation on port 19876
  • Live price movements and order execution
  • Pre-configured profiles and message templates
  • No external dependencies required

5. Sending Messages

Opening the Message Editor

Click the Message Editor button in the toolbar to open the message editor panel.

Building a Message

  1. Click Add Field to add a new field row
  2. Enter the Tag number (e.g., 35 for MsgType)
  3. Enter the Value (e.g., D for NewOrderSingle)
  4. Repeat for all required fields
  5. Click Send to send the message

Example: New Order Single (35=D)

Tag 35 : D (MsgType = NewOrderSingle)
Tag 11 : ORDER123 (ClOrdID = Order ID)
Tag 55 : EUR/USD (Symbol)
Tag 54 : 1 (Side = Buy)
Tag 38 : 1000000 (OrderQty)
Tag 40 : 2 (OrdType = Limit)
Tag 44 : 1.0850 (Price)

Send to All Sessions (Bulk Send)

Next to the Send button is a Send to All Sessions button (megaphone icon). It sends the current message over every logged-on session - for example, one MarketDataRequest subscribing all load-test sessions in one click.

  • Template expressions are re-resolved for each session, so ${UUID.randomUUID()} in MDReqID produces a different value per session (see Per-Session Variables)
  • Sessions that are not logged on are skipped
  • A notification summarizes the result and names any sessions where the send failed

Saving Message Templates

Save frequently used messages for reuse:

  1. Build your message in the editor
  2. Click Save Message
  3. Enter a template name
  4. Load it later from the Saved Messages dropdown

6. Message Templates (Advanced)

What are Template Expressions?

Template expressions allow you to dynamically generate field values using Kotlin expressions. This is especially useful for:

  • Generating unique IDs automatically
  • Inserting current timestamps
  • Referencing values from previously received messages
  • Creating responsive message workflows

Template Syntax

Template expressions are enclosed in ${...} and evaluated when you send the message:

Basic Templates

Template Result Description
${UUID.randomUUID()} a1b2c3d4-e5f6-... Generate random UUID
${System.currentTimeMillis()} 1705419265123 Current Unix timestamp
ORDER-${UUID.randomUUID()} ORDER-a1b2c3d4-... Prefix with text

Timestamp Formatting

${LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMdd-HH:mm:ss.SSS"))}

Result: 20250116-14:32:45.123

Common patterns:

  • "yyyyMMdd" → 20250116
  • "HHmmss" → 143245
  • "yyyyMMdd-HH:mm:ss" → 20250116-14:32:45

Variable Assignment and Reuse

When you need to use the same generated value in multiple fields (like using the same UUID in multiple tags), you can assign the value to a variable and reuse it:

Assignment Syntax

${varName = expression}

The first time you use a value, assign it to a variable. Then reference the variable name elsewhere:

${orderId = UUID.randomUUID()}

Later in the same message, simply reference the variable:

${orderId}

Example: Reusing a UUID in Multiple Fields

Tag 11 : ${orderId = UUID.randomUUID()} (Assign and use in ClOrdID)
Tag 37 : ${orderId} (Reuse same value in OrderID)
Tag 41 : ${orderId} (Reuse again in OrigClOrdID)

Result: All three tags will have the same UUID value.

Example: Reusing a Timestamp

Tag 52 : ${ts = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMdd-HH:mm:ss.SSS"))} (SendingTime)
Tag 60 : ${ts} (TransactTime - same timestamp)

Result: Both timestamps will be identical.

Variable Naming Rules

  • Variable names must start with a letter or underscore
  • Can contain letters, numbers, and underscores
  • Examples: orderId, my_timestamp, id123

Multiple Variables

You can define and use multiple variables in the same message:

11=${orderId = UUID.randomUUID()}
37=${orderId}
52=${timestamp = LocalDateTime.now()}
60=${timestamp}
Tip: Variables are evaluated left-to-right. Make sure to assign a variable before you try to use it. If you reference an undefined variable, it will appear as ${varName} in the message.

Real-World Example: Quote Request Message

When building a QuoteRequest message where you need the same QuoteReqID in multiple fields:

In the Message Editor, add these fields:

Tag Value Description
35 : R (MsgType = QuoteRequest)
131 : ${quoteReqId = UUID.randomUUID()} (QuoteReqID - assign to variable)
132 : ${quoteReqId} (BidRequestTransType - reuse same ID)
133 : ${quoteReqId} (OfferRequestTransType - reuse same ID)
55 : EUR/USD (Symbol)

When you click Send:

The same UUID (e.g., a1b2c3d4-e5f6-7890-abcd-ef1234567890) will be used for tags 131, 132, and 133.

Per-Session Variables (Multi-Session)

When a message is sent - and especially during Send to All Sessions - these variables describe the session the message is going out on:

Variable Value
${sessionIndex} 1-based position among the targeted sessions (1, 2, 3, ...)
${sessionSenderCompID} The session's resolved SenderCompID (e.g. LOADGEN02)
${sessionQualifier} The session's SessionQualifier (may be empty)
${sessionTitle} The session tab title (e.g. MD Load [2])

Example: Traceable MDReqID per Session

Tag 262 : MD-${sessionSenderCompID} (MDReqID - resolves to MD-LOADGEN01, MD-LOADGEN02, ... per session)

Message References (Advanced)

Reference field values from previously sent or received messages:

Syntax

${incoming["MsgType"].valueOfTag(TagNumber)}
${outgoing["MsgType"].valueOfTag(TagNumber)}
  • incoming - References latest received message of that type
  • outgoing - References latest sent message of that type
  • "MsgType" - FIX message type (e.g., "D", "R", "AJ")
  • TagNumber - FIX tag number to extract

Shorthand Syntax (Recommended)

For convenience, you can use shorthand syntax instead of the verbose form above:

Shorthand Patterns

Shorthand Equivalent Full Syntax Description
${D.11} ${incoming["D"]...} Auto-detect: tries incoming first, then outgoing
${D.ClOrdID} ${incoming["D"].valueOfTag(11)} Use tag name instead of number
${in.D.11} ${incoming["D"].valueOfTag(11)} Explicit incoming only
${out.R.QuoteReqID} ${outgoing["R"].valueOfTag(131)} Explicit outgoing with tag name
${R.20013.0} ${incoming["R"].valueOfTag(20013, 0)} Repeating group: first occurrence (index 0)
${uuid} ${UUID.randomUUID().toString()} Generate a random UUID
${now} ${LocalDateTime.now()...} Current timestamp in FIX format (yyyyMMdd-HH:mm:ss.SSS)
${now:yyyyMMdd} ${LocalDateTime.now()...} Custom timestamp format (date only)
${now+1h} ${LocalDateTime.now().plusHours(1)...} Timestamp offset: 1 hour from now
${now-2d} ${LocalDateTime.now().minusDays(2)...} Timestamp offset: 2 days ago
${now+1w} ${LocalDateTime.now().plusWeeks(1)...} Timestamp offset: 1 week from now
${now+1m} ${LocalDateTime.now().plusMonths(1)...} Timestamp offset: 1 month from now
${now-1y} ${LocalDateTime.now().minusYears(1)...} Timestamp offset: 1 year ago
${now+1d:yyyyMMdd} ${LocalDateTime.now().plusDays(1)...} Offset with custom format: tomorrow (date only)

Offset units: h (hours), d (days), w (weeks), m (months), y (years)

Common Tag Names

These tag names work without a data dictionary:

  • ClOrdID (11)
  • OrderID (37)
  • OrigClOrdID (41)
  • Symbol (55)
  • Side (54)
  • OrderQty (38)
  • Price (44)
  • QuoteReqID (131)
  • QuoteID (117)

Real-World Example: Quote Response

Scenario:

You receive a QuoteRequest (35=R) and want to send a QuoteResponse (35=AJ) that references the original request:

Incoming QuoteRequest:

35 = R (MsgType = QuoteRequest)
131 = QUOTEREQ-001 (QuoteReqID)
55 = EUR/USD (Symbol)
38 = 1000000 (OrderQty)

Your QuoteResponse Template (using shorthand):

Tag 35 : AJ (MsgType = QuoteResponse)
Tag 131 : ${R.QuoteReqID} (Same QuoteReqID from request)
Tag 55 : ${R.Symbol} (Same Symbol from request)
Tag 117 : QUOTE-${UUID.randomUUID()} (New unique QuoteID)
Tag 132 : 1.0850 (BidPx)
Tag 133 : 1.0852 (OfferPx)

Resolved Message (when sent):

35 = AJ (MsgType = QuoteResponse)
131 = QUOTEREQ-001 (Matched from incoming)
55 = EUR/USD (Matched from incoming)
117 = QUOTE-f7e8d9c6-1234-5678-... (Generated UUID)
132 = 1.0850 (BidPx)
133 = 1.0852 (OfferPx)
Tip: Message references always use the latest message of each type. The application tracks incoming and outgoing messages separately across all sessions.

Common Message Types

Type Name Common Tags
D NewOrderSingle 11 (ClOrdID), 55 (Symbol), 54 (Side)
R QuoteRequest 131 (QuoteReqID), 55 (Symbol), 38 (OrderQty)
AJ QuoteResponse 131 (QuoteReqID), 117 (QuoteID), 132 (BidPx)
8 ExecutionReport 11 (ClOrdID), 37 (OrderID), 17 (ExecID)
Note: If a referenced message type doesn't exist (not received yet), the expression will evaluate to null. Make sure you've received the message before referencing it.

Accessing Repeating Groups

Many FIX messages contain repeating groups - fields that can appear multiple times. For example, a QuoteRequest with multiple legs, or a message with multiple parties. FixTool provides special syntax to access specific occurrences of fields in repeating groups.

Repeating Group Syntax

${incoming["MsgType"].valueOfTag(TagNumber, index)}
${incoming["MsgType"].allValuesOfTag(TagNumber)}
  • valueOfTag(tag, index) - Get value at specific index (0-based)
  • allValuesOfTag(tag) - Get all values as a list
  • valueOfTag(tag) - Get first value (backwards compatible)

Real-World Example: Multi-Leg Quote Request

Scenario:

You receive a QuoteRequest (35=R) with 2 legs, each with a unique Leg Quote Request ID (tag 20013):

Incoming QuoteRequest:

35 = R (MsgType = QuoteRequest)
131 = QUOTEREQ-001 (QuoteReqID)
555 = 2 (NoLegs = 2 legs)
20013 = 8c2b290c-f292-4ae9-af8f-66340623deec (Leg 1 Quote Request ID)
687 = 1000 (Leg 1 Quantity)
556 = EUR (Leg 1 Currency)
20013 = d119dad0-2dd9-4ef3-af56-de9395d5b57e (Leg 2 Quote Request ID)
687 = 2000 (Leg 2 Quantity)
556 = USD (Leg 2 Currency)

Your Quote Response Template:

To respond with specific values from each leg:

Tag 35 : S (MsgType = Quote)
Tag 131 : ${incoming["R"].valueOfTag(131)} (Same QuoteReqID from request)
Tag 555 : 2 (2 legs in response)
Tag 20013 : ${incoming["R"].valueOfTag(20013, 0)} (Leg 1 ID - index 0)
Tag 687 : ${incoming["R"].valueOfTag(687, 0)} (Leg 1 Qty - index 0)
Tag 132 : 1.0850 (Leg 1 BidPx)
Tag 20013 : ${incoming["R"].valueOfTag(20013, 1)} (Leg 2 ID - index 1)
Tag 687 : ${incoming["R"].valueOfTag(687, 1)} (Leg 2 Qty - index 1)
Tag 132 : 1.1200 (Leg 2 BidPx)

Resolved Message (when sent):

35 = S
131 = QUOTEREQ-001
555 = 2
20013 = 8c2b290c-f292-4ae9-af8f-66340623deec (Matched from leg 1)
687 = 1000 (Matched from leg 1)
132 = 1.0850
20013 = d119dad0-2dd9-4ef3-af56-de9395d5b57e (Matched from leg 2)
687 = 2000 (Matched from leg 2)
132 = 1.1200

Working with Lists

Use allValuesOfTag() to work with all occurrences at once:

List Operations

Template Result Description
${incoming["R"].allValuesOfTag(20013)} [leg1-id, leg2-id] Get all leg IDs as a list
${incoming["R"].allValuesOfTag(20013).size} 2 Count number of legs
${incoming["R"].allValuesOfTag(20013)[0]} leg1-id Access first leg via list
${incoming["R"].allValuesOfTag(20013)[1]} leg2-id Access second leg via list
Tip: Index-based access is 0-based. The first occurrence is at index 0, the second at index 1, etc. If you try to access an index that doesn't exist, the value will be null.
Backwards Compatibility: For messages without repeating groups, or when you only need the first value, valueOfTag(tag) still works as before - it returns the first (or only) value.

Template Expression Validation

FixTool automatically validates all template expressions before sending messages to ensure they evaluate correctly. This prevents sending messages with broken or invalid expressions.

What is Validated

When you click Validate or Send, FixTool checks all template expressions for:

  • Syntax Errors: Invalid Kotlin code that won't compile
  • Undefined Variables: References to variables that haven't been assigned
  • Null Evaluations: Expressions that evaluate to null (like accessing non-existent message fields)

Validation Errors

If validation fails, you'll see detailed error messages in the validation error section:

Example Validation Errors

❌ Cannot send message - Fix template expression errors:
Field 11: Template error in '${badSyntax!}': Expecting an element
Field 38: Template error in '${undefinedVar}': Undefined variable: undefinedVar
Field 44: Template error in '${incoming["D"].valueOfTag(99999)}': Expression evaluates to null

Validate Button vs. Send Button

  • Validate Button: Checks expression syntax and variable definitions without message context. Use this to catch basic errors before receiving incoming messages.
  • Send Button: Performs full validation with access to all incoming and outgoing messages. This catches null evaluations and message-dependent errors. Messages will not be sent if validation fails.
Best Practice: Use the Validate button while building your template to catch syntax errors early. When you're ready to send, the Send button will perform a complete validation including message context.
Important: Messages with template expression errors cannot be sent. Fix all validation errors before attempting to send. Expressions that evaluate to null (like accessing non-existent fields) are blocked to prevent sending incomplete data.

Common Validation Issues and Solutions

Error Type Cause Solution
Undefined variable Using a variable before assigning it Add ${varName = value} in an earlier field
Expression evaluates to null Accessing a field that doesn't exist in the message Verify the message type and field exist, or use a default value
Syntax error Invalid Kotlin syntax in the expression Check for typos, missing quotes, or incorrect function calls
Incomplete code Expression with unbalanced braces or quotes Ensure all opening braces { and quotes have matching closing ones

Example: Handling Potentially Missing Fields

If you're accessing a field that might not exist in all incoming messages, make sure to handle the null case or ensure the message type is correct:

// Will fail validation if tag 38 doesn't exist:
${incoming["D"].valueOfTag(38)}

// Better: Make sure you've received a NewOrderSingle (35=D) with Quantity (38) before referencing it
// Or use a different approach with proper null handling in your workflow

10. Latency Measurement

Overview

FixTool can measure round-trip time (RTT) for FIX messages by correlating outbound requests with their corresponding inbound responses. This helps you analyze trading system performance and identify latency issues.

How It Works

Latency tracking correlates message pairs using standard FIX correlation IDs:

  • When you send a message, FixTool records the timestamp and correlation ID
  • When a response arrives with a matching correlation ID, the round-trip time is calculated
  • Latency is displayed on the outbound message in the grid view
  • Each session tracks its own latency statistics independently

Supported Correlation IDs

Tag Name Typical Usage
11 ClOrdID Order requests → Execution Reports
131 QuoteReqID Quote Requests → Quotes
117 QuoteID Quote responses
262 MDReqID Market Data Requests → Market Data responses
37 OrderID Order-related messages
17 ExecID Execution Reports

Enabling Latency Tracking

  1. Open Settings from the toolbar
  2. In the Latency Tracking section, check Enable Latency Tracking
  3. Optionally check Show Latency Column to display RTT in the message grid
  4. Click Save
  5. Reconnect your session (latency tracking starts on connect)

Viewing Latency Data

Message Grid

When enabled, a Latency column appears in the grid view showing round-trip time in microseconds (μs) for correlated outbound messages. The column uses color coding:

  • Green - Normal latency (below warning threshold)
  • Yellow - Warning (above warning threshold, below critical)
  • Red - Critical (above critical threshold)

Latency Panel

Click the Timer icon in the toolbar to open the Latency Panel, which shows:

  • Capture Status - Shows timestamp source (Packet or App-level)
  • Aggregate Statistics - Combined stats across all correlation types
  • Per-Type Statistics - Breakdown by correlation ID type (ClOrdID, QuoteReqID, etc.)
  • Recent Correlations - Table of recent request/response pairs with RTT

Statistics Explained

Metric Description
Count Number of correlated message pairs
Min Fastest round-trip time observed
Max Slowest round-trip time observed
Mean Average round-trip time
Median (p50) Middle value - 50% of requests are faster
p90 90th percentile - 90% of requests are faster
p95 95th percentile - 95% of requests are faster
p99 99th percentile - 99% of requests are faster
Std Dev Standard deviation - measure of latency consistency
Tip: Percentiles are more useful than averages for understanding latency. A low p50 with a high p99 indicates occasional slow responses that averages would hide.

Timestamp Accuracy

FixTool supports two timestamp sources with different accuracy levels:

Packet-Level Timestamps (~10μs accuracy)

Uses kernel-level packet capture via pcap4j library for the most accurate timing. This measures the actual network wire time, eliminating application processing overhead.

Requirements:

  • macOS: Add user to access_bpf group or run with sudo
  • Linux: Grant CAP_NET_RAW capability or run as root
  • Windows: Run as Administrator with Npcap installed

macOS Setup (Recommended)

# Add current user to access_bpf group (one-time setup)
sudo dseditgroup -o edit -a $(whoami) -t user access_bpf

# Log out and log back in for changes to take effect

Application-Level Timestamps (~100μs accuracy)

Fallback mode using Java System.currentTimeMillis(). This is automatically used when packet capture is unavailable. While less precise, it still provides useful latency measurements for most purposes.

The Latency Panel shows a badge indicating which timestamp source is active:

  • Packet - Using packet-level timestamps
  • App-level - Using application timestamps (fallback)

TLS/SSL Encrypted Connections

Limitation: Packet-level timestamps cannot work with TLS/SSL encrypted connections. When you enable SSL in the connection profile, FixTool automatically uses application-level timestamps.

Why? Packet capture sees the encrypted TCP packets, but the FIX message content inside is encrypted and unreadable. Without being able to parse the messages, correlation IDs cannot be extracted.

Workaround: Using stunnel for Packet-Level Timestamps

If you need packet-level accuracy (~10μs) for a TLS server, you can use stunnel as a local TLS proxy:

Architecture

FixTool → localhost:9876 (unencrypted) → stunnel → remote-server:443 (TLS)

Packet capture on the loopback interface sees the unencrypted traffic between FixTool and stunnel.

stunnel Setup (macOS/Linux)

# Install stunnel
brew install stunnel   # macOS
apt install stunnel    # Linux

# Create config file: stunnel.conf
[fix-proxy]
client = yes
accept = 127.0.0.1:9876
connect = your-remote-server:443

# Run stunnel
stunnel stunnel.conf

Then in FixTool:

  • Set Host to localhost and Port to 9876
  • Disable SSL in the connection profile (stunnel handles encryption)
  • Packet capture will work on the unencrypted local traffic
Note: When using stunnel, the measured RTT includes stunnel's encryption/decryption overhead (typically <1ms). For most use cases, this is negligible compared to network latency.

Configurable Thresholds

In Settings, you can configure latency thresholds:

  • Warning Threshold: Default 100,000μs (100ms) - latencies above this show in yellow
  • Critical Threshold: Default 500,000μs (500ms) - latencies above this show in red
  • History Size: Number of samples retained for statistics (default 10,000)

Clearing Statistics

To reset latency statistics:

  • Open the Latency Panel (Timer icon in toolbar)
  • Click the Clear/Trash icon button
  • This resets all statistics, pending correlations, and history for the current session
Note: Clearing messages from the session (via "Clear All") does not clear latency statistics. They are tracked independently.

Troubleshooting

Latency column shows empty

  • Ensure latency tracking is enabled in Settings
  • Reconnect the session after enabling
  • Latency only appears on outbound messages after a matching response arrives
  • Check that your messages contain supported correlation IDs

"App-level" badge shown instead of "Packet"

  • Packet capture requires elevated privileges (see requirements above)
  • On macOS, ensure you're in the access_bpf group and have logged out/in
  • App-level timestamps still provide useful measurements, just with lower precision

Statistics not updating

  • Ensure you're sending messages with correlation IDs (ClOrdID, QuoteReqID, etc.)
  • Verify responses contain matching correlation IDs
  • Check that both request and response occur within the same session

11. Automation & AI Control

FixTool can be driven by Claude (or any MCP client), curl, or CI scripts for automated FIX testing — connect to a gateway, send messages, wait for and verify responses, manage templates, configure acceptor auto-responses, and capture screenshots. An MCP server is built into the app (loopback-only, off by default), so there is nothing extra to install.

Step 1 — Enable automation control

  1. Open Settings (gear icon).
  2. Scroll to Automation Control and tick Enable automation control.
  3. Choose a port (default 8765) and click Save.

The control + MCP server starts immediately, listening on 127.0.0.1 only.

Step 2 — Connect Claude Code

Register the built-in MCP server once (the Settings screen shows this exact command):

claude mcp add --transport http fixtool http://127.0.0.1:8765/mcp

This works from any project directory; add --scope user to make it available in every project. No Node, npm, or source checkout is required.

Step 3 — Ask Claude to drive FixTool

Describe the task in plain language and Claude picks the right tools. For example:

"Use the fixtool tools to connect to the demo server, send a NewOrderSingle for EUR/USD, then show me the ExecutionReport."

Claude can be working in a completely different codebase (your own FIX project) and still drive FixTool to test against your gateway.

Loopback & off by default. The server only accepts connections from this machine (127.0.0.1) and never starts unless you enable it. An optional shared secret (FIXTOOL_CONTROL_TOKEN environment variable) can be required on every request; developers can also enable the server with the FIXTOOL_CONTROL_PORT environment variable, which overrides this setting.

The full tool list, the HTTP API, and acceptor auto-response rules are documented in the Automation Guide.

12. Automated Verification & Scenarios

Instead of eyeballing a response to decide whether it looks right, you (or an agent) can machine-check a received message tag-by-tag against an expectation — a set of per-tag matchers. The result is a green/red verdict per tag, so a wrong field is pinpointed immediately and a check can be repeated identically every time. This is the foundation for turning a manual test flow into a repeatable regression check.

Two automation tools drive it (available over MCP, the HTTP API, and curl once automation control is enabled):

  • fixtool_capture_expectation — take a received message and get back a draft expectation whose matchers are pre-seeded from the data dictionary (timestamps become time matchers, prices/quantities become numeric matchers, IDs become presence checks, volatile header tags are dropped). You edit the draft instead of writing matchers from scratch.
  • fixtool_assert — assert a received message against an expectation. It selects the message (by message type / direction / index) or awaits one for up to timeoutMs, then returns {passed, tags:[{tag, matcher, expected, actual, passed}]}.

Matcher types

MatcherChecks that the tag…
exactequals a literal value (the default for business fields)
presenceis present; its value is ignored (e.g. a venue-assigned OrderID/ExecID)
absentis not present (e.g. no reject Text)
oneOfis one of a set of values (e.g. OrdStatus in 1 or 2)
regexmatches a regular expression
numericequals a number within a tolerance (so 1.2345 = 1.23450; widen the tolerance for fuzzy price/qty checks)
temporalis a timestamp near "now" (± N seconds) or a date equal to today — instead of a brittle literal time
referenceequals a ${…} expression resolved over the session, e.g. an ExecutionReport's ClOrdID echoes the order you sent: ${out.D.11}

For a tag inside a repeating group, add a path that locates the entry by identity rather than position (group order is not guaranteed) — e.g. "the PartyID of the entry whose PartyRole = 1".

OPEN vs STRICT

  • open (default) — only the tags you list are checked; extra tags on the response are ignored, so a venue adding an optional field doesn't fail the check. Use an absent matcher to forbid a specific tag.
  • strict — any unexpected tag (besides volatile header/trailer tags) fails the check. For contracts that must be exact.

Example

After sending a NewOrderSingle and receiving an ExecutionReport (35=8), assert it:

{
  "session": "Demo User 1", "messageType": "8", "direction": "in", "timeoutMs": 5000,
  "fields": [
    { "tag": 150, "matcher": { "type": "exact", "value": "0" } },
    { "tag": 39, "matcher": { "type": "oneOf", "values": ["0","1","2"] } },
    { "tag": 37, "matcher": { "type": "presence" } },
    { "tag": 11, "matcher": { "type": "reference", "expression": "${out.D.11}" } },
    { "tag": 60, "matcher": { "type": "temporal", "kind": "now_within_tolerance", "toleranceSeconds": 30 } }
  ]
}

Or just ask an agent in plain language:

"Send a NewOrderSingle for EUR/USD to the demo server, then assert the ExecutionReport has ExecType=New, an OrderID, and a ClOrdID that matches the order I sent."

Repeatable scenarios (author once, run forever)

An assertion checks one message; a scenario chains a whole flow — a saved, parameterized sequence of sends and assertions that a deterministic runner replays identically every time, with no AI in the loop. Author it once (by hand or with an agent); re-run it as a regression test forever.

A scenario is an ordered list of steps over a single persistent variable scope:

  • send — a (parameterized) message; ${…} resolves at run time, and a value set in one step is visible in later steps.
  • expect — await the next matching message and assert it against an expectation (the same matchers as above). Successive expects walk successive messages, so a partial-fill sequence (two partials then a fill) is just three expect steps.
  • wait — block until a state (e.g. LOGGED_ON) or a matching message.
  • clearMessages / resetSeqNum — typical setup steps for a clean start.

setup steps run first; teardown steps always run, even after a failure. Each step can target a different session, so one scenario can drive an initiator and assert on an acceptor.

Four tools manage them: fixtool_save_scenario, fixtool_list_scenarios, fixtool_run_scenario, and fixtool_delete_scenario. A run returns a per-step, per-tag pass/fail report; pass format:"junit" to get JUnit XML for CI.

Scenarios are stored as one JSON file per scenario under ~/.fixtool/scenarios/ — diffable, shareable, and easy to commit alongside your project.

In the app: click the Scenarios button (the ▶ playlist icon) in the toolbar to open the Scenarios panel. There you can run a saved scenario and watch its per-step, per-tag red/green result (each expect step expands to one row per asserted tag, showing expected vs actual — red where it failed), delete scenarios, or author a new one by pasting its JSON. This is where a failed assertion is rendered visually inside FixTool.

The point: the LLM (or a human) authors the scenario once; a dumb runner repeats it forever. The model is out of the hot path, so runs are fast, deterministic, and CI-friendly. Full design: docs/repeatable-scenarios-proposal.md.
