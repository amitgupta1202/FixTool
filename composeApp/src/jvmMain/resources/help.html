1. Getting Started

What is FixTool?

FixTool is a desktop application for working with the FIX (Financial Information eXchange) protocol. It allows you to:

  • Connect to FIX servers and receive messages
  • Send FIX messages with custom field values
  • View and analyze message history
  • Search and filter messages
  • Create reusable message templates

Quick Start

  1. Open the workspace switcher at the top left → Open workspace… and pick fx-venue — the examples are already folders there
  2. Select one of the Demo Client profiles the example brought with it
  3. Click Connect to establish a FIX session
  4. Use the pre-loaded FX templates to send orders and receive fills
New to FixTool? Start with the example workspace - it's the fastest way to explore FIX messaging without any external dependencies.

2. The Examples

Overview

FixTool ships five example venues, and none is a black box. Each is a workspace folder in ~/.fixtool/workspaces/, opened with Open workspace like any other, and built entirely out of features you already have: an acceptor profile whose venue behaviour is a list of rules you can read, client profiles pointed at it, message templates to drive it, repeatable scenarios that run green out of the box, a five-session load client, and a load set that runs without editing anything.

They are not five copies of one venue with different tickers. Each exists because it does something the others cannot, so the one to open is whichever is closest to the market you are testing against — and the second one to open is whichever does the thing you have never had to simulate before.

ExamplePortWhat it isWhat only it does

FX RFQ Venue19877 A request-for-quote desk in FX: quotes firm, books a hit at the price it quoted A quote book — so stale, spent and never sent are three different refusals, which nothing on the incoming message can tell apart

Two of them are an RFQ seen from two chairs, on purpose. Both play QuoteRequest → Quote → QuoteResponse. The FX RFQ venue is the dealer: you ask it for a price and it quotes. The Fixed Income platform is the venue between you and the dealers: it prices nothing, carries each request out to every dealer and each quote back, and confirms a trade to both sides. Open the FX one to test a client of a dealer, and the fixed-income one to test either side of a platform — or both at once, which is what its scenarios do.

Every example can be driven at volume. Each ships a five-session load client on a memory store and at least one load set, so a load run needs no profile edits: fx-order-book, rfq-round-trip, equity-rest-and-cancel, crypto-rest-and-refuse, and two on the fixed-income platform — fi-rfq-round-trip and fi-rfq-reactive. Read each venue's own section for what its set proves. From the command line, fixtool load --set takes the example's folder as --home, and needs the venue up in FixTool first: it opens the load client, not the venue.

Everything an example does, you can open, change, reorder or switch off, and everything you learn from it applies directly to simulating a real counterparty.

An example is a copy, in a folder of its own. Nothing is mixed into your own profiles or scenarios, so there is nothing to uninstall, and what you change in it is yours to keep or commit. The five venues listen on five different ports, so you can have all of them up at once.

Every example is written to the bundled FIX 4.4 dictionary. The dictionary does not move with the workspace (see Settings), so an installation that has a venue's own dictionary loaded under Settings → Protocol runs the examples against that dialect. Where the dialect renames or relocates a tag the example uses, a bundled expectation goes red on that tag: one dealer's dictionary defines tag 132 as a header field, so the RFQ venue's BidPx lands in the header there and RFQ book a trade fails on its Quote step. Switch to the bundled dictionary to run the examples as shipped.

Opening an Example

  1. Every example is already a folder in ~/.fixtool/workspaces/: ~/.fixtool/workspaces/fx-venue, rfq-venue, equity-venue, crypto-venue and fixed-income-rfq. FixTool lays down any that is missing when it starts, and never writes over one that is there, so your edits survive every restart and every upgrade: the copy happens once. For a pristine one, rename or delete the folder and start FixTool again, or use Settings → Storage → Reset
  2. Open the workspace switcher at the top left, choose Open workspace… — it starts in that folder — and pick the example you want. There is no separate button for an example: it is a workspace like any other
  3. The workspace opens with the venue and its client profiles, the templates and the scenarios. Connect the venue first, then the clients
  4. The venue binds its port and the clients log on to it
  5. The venue's own pane starts minimized, as a chip in the strip above the grid. It holds no traffic of its own, since every message on a venue belongs to one of its clients, and the chip carries what the pane says: the port, who is connected, and Rules and Stop. Click the chip to put the pane back
Tip: Each venue accepts any SenderCompID (its TargetCompID is *), so you can point your own connection profile at localhost:19876 with TargetCompID=DEMO_SERVER, or at localhost:19877 with TargetCompID=RFQ_SERVER, and it will be accepted too. Each counterparty gets its own pane on the venue side.

From a script or an agent, POST /workspace {"example":"rfq-venue"} opens an example by its id, and POST /demo keeps opening the FX venue under its old name. See 11. Automation & AI Control.

Minimizing a Pane

The — button on any pane sends it to the strip above the grid, and its chip brings it back. This is not closing: closing a pane disconnects its session and discards its log, while a minimized session stays connected, keeps logging, and stays the message editor's send target — a chip marked → editor is where Send will go, so minimizing never quietly points a composed order at a different counterparty.

A venue's chip stays quiet while the venue is healthy and grows a badge only when something has deviated: a client gone, a logon refused, replies pending, injected latency on, or no rules loaded. That last one is the answer to a venue that is answering nothing.

Reading the Venue's Rules

Select the venue profile, FX Demo Venue or RFQ Demo Venue, and open Auto-Responses in the Connection panel. Each rule is a card: what it triggers on, and what it replies with. First match wins, top to bottom, which is why the order matters: the FX venue's size-limit reject sits above its fill rules so a huge order is rejected rather than filled, and the RFQ venue's bookings sit above its wrong-price refusal so a hit at the quoted price is booked rather than refused.

Change a price, reorder a card, or switch one off, and the venue behaves differently on the next message. Nothing is compiled in. Both bundles are also in the rule editor's preset menu, under Bundles, so you can drop either venue's rules onto an acceptor of your own.

The Bundled Scenarios

The example brings scenarios that pass as soon as its sessions are up. EUR/USD order lifecycle is a limit order acknowledged, half-filled, filled, and then a cancel that is correctly refused as too late. Open the Scenarios rail and run it.

Session round-trip probe sends one TestRequest and waits for the Heartbeat that echoes its TestReqID. The venue's session engine answers that before any rule, order book or simulated latency is involved, so the round trip is the network and the engine and nothing else: the floor under every order. Run it once for one number; run it as a set of a hundred (right-click it in the rail, or POST /scenarios/runs) and the set report gives a p50/p95/max of the session layer, which is what a team qualifying a venue's connectivity used to script by hand. Point the client profile at a real venue and the same scenario probes that venue. Two things to know: the report's per-step latency is the FIX engine's stamp, while the Latency panel's figure for the same probe is the socket's and excludes FixTool's own path (see 10. Latency Measurement); and the expectation reads the Heartbeat from the session log, so Show heartbeat messages must be on for the client profile, as it is by default.

It is worth running twice. The scenario uses a fixed ClOrdID, so the second run would be rejected as a duplicate out of the venue's memory of the first — which is why its setup contains a Clear order book step aimed at the venue side. That step is the difference between a flow that repeats and one that only worked once.

Try this: run the scenario green, then open a venue rule and change the fill price. Run it again — it goes red, and the reconcile view shows exactly which field moved and what it moved to.

The Load Client, and What This Venue Can Be Asked

The FX Load Client is a profile of five sessions, FXLG1 to FXLG5, on a memory store with no message log and Reset on Logon — the same setting the RFQ load client carries, and the one Store and log describes. The example ships a three-phase load set, FX order book, in Run → Load sets or from the command line:

fixtool load --set fx-order-book --home ~/.fixtool/workspaces/fx-venue
PhaseSendsMatched onKeeps
1. Order250 market orders, 11=FXO-<run>-<n> ClOrdID to ClOrdID, reply 35=8 orderId from 37, per message
2. Unknown2,000 cancels for orders nothing ever placed ClOrdID to ClOrdID, reply 35=9nothing
3. Status250 status requests naming phase one's orders, at 37=${orderId} ClOrdID to ClOrdID, reply 35=8nothing

All three phases read the venue's order book, and that is what the set is for. Phase two is refused with 102=1 Unknown order because the book has never heard of those ids; phase three is answered out of the book with the order's real quantities. The ClOrdID is ours, so phase three can name an order phase one placed without being told; the OrderID is the venue's, so it is captured off the ExecutionReport that opened the order, exactly as the RFQ set captures a QuoteID. Message n goes to lane (n - 1) % lanes in every phase, which is what puts the status request on the same session that placed the order — the venue keeps one book per counterparty.

The phase sizes are this venue's ceiling, not a recommendation — and phase two's round trip is the proof. This venue draws its fill price with a Kotlin expression, and the script engine compiles one expression at a time for the whole process at about 60 ms each, so every order this venue accepts costs its dispatch thread that much. A cancel it refuses and a status it reads out of the book are pure substitution and cost microseconds. You can read both facts straight off the report: run phase two on its own and its 2,000 refusals are answered in about 150 ms; run it where it sits, behind 250 orders, and the same 2,000 refusals take about 15 seconds, because they are queued behind 250 fills being compiled one at a time. That is the whole lesson of the set, and it is why the phase that makes the venue price something is the small one. Do not read a throughput number off this venue. The number you want comes from the RFQ venue, whose replies are all generators, or from pointing the load client at a real venue.
Not there? Your copy is older than the set. An example's folder is copied once, so a folder laid down before this release has no load-sets/ directory and no FX Load Client, and nothing in the app mentions either. Settings → Storage → Reset lays the shipped example down again and brings both with it. It renames your current copy to fx-venue-before-reset-<date> rather than deleting it, so an edited rule or a captured scenario is still there to copy across.

The RFQ Venue

An RFQ Demo Venue acceptor on localhost:19877, open to any CompID, that plays a request-for-quote desk: a client asks for a quote with QuoteRequest (35=R), is quoted with Quote (35=S), hits or lifts it with QuoteResponse (35=AJ), and is booked with ExecutionReport (35=8). Everything a QuoteResponse can say that cannot be booked is answered with a QuoteStatusReport (35=AI) that says why in QuoteStatus (297) and Text (58), never left in silence. Two clients, RFQ Client 1 and RFQ Client 2, and an RFQ Load Client of five sessions are pointed at it. The venue injects no latency, because it is the venue a load run is measured against.

Two things differ from the FX venue on purpose, and both are about being a venue rather than an echo. The QuoteID is opaque: it is a fresh uuid, so the only way to answer a quote is to have read it, which is what every real RFQ venue requires. And the venue remembers what it quoted, in its quote book, so it can refuse a hit that arrived too late, a second hit on a quote it already booked, and a hit on a quote it never sent: three refusals that nothing on the incoming message could tell apart.

The shapes follow the bundled FIX 4.4 dictionary: a QuoteResponse carries no QuoteReqID and an ExecutionReport carries neither QuoteID nor QuoteReqID, so the trade report ties back by QuoteRespID (693) and the ClOrdID (11) the client named its trade with.

The Prices

Each side is drawn per quote from its own band, nine ticks wide on the pair's pipette so a five-decimal price does not always end in 0:

A buy lifts the offer and a sell hits the bid. The quote is for the size the request asked (134 and 135 echo 38) and stands for thirty seconds (62), which is long enough to hit by hand and short enough to watch expire.

Twenty-five rules, where the first slice of this venue needed eighteen and said less. Two of them are the whole booking: because the symbol and the price are read off the quote (quoteField in the trigger, ${quote.…} in the reply), the three pairs are one buy rule and one sell rule rather than six. None of them asks the order book, because a booked quote hit is a quote event and not an order event, so the quote book takes it off the order book's hands.

The Bundled Scenarios

RFQ book a trade requests a EUR/USD quote, expects a Quote carrying a QuoteID and both prices, lifts it at the id and the offer it was actually sent (117=${in.S.117}, 44=${in.S.133}), and expects an ExecutionReport with 150=F and a LastPx equal to that offer. Reading both back off the quote is not a convenience: neither can be predicted, which is the point of the venue.

RFQ pass and counter asks for a GBP/USD quote, counters it, hits it at the wrong price, then passes, and finally hits it once more, expecting “Quote already answered”. The order matters now. A pass spends the quote, so anything sent after one is refused as spent, and the last two steps are there to prove exactly that. Both scenarios clear the client pane and the venue pane's books in their setup, as the FX scenarios do, and both run green twice.

The Equity Venue

An Equity Demo Venue acceptor on localhost:19878, open to any CompID, that plays a US cash equities venue in AAPL, MSFT and TSLA. It is the first bundled venue whose book holds your order: send a Day limit and it is acknowledged and then nothing else happens to it. It rests until you cancel or replace it.

That one difference is the point of the example. The FX and RFQ venues answer everything at once, so whenOrder working lasted the 250 ms between an ack and its fill, a cancel was a race, and a replace was a rule with nothing to replace. Here they are behaviours you can drive by hand.

What TimeInForce decides

OrderWhat the venue does
Limit, Day (59=0, or absent) New, and it rests at 39=0 until you cancel or replace it
Limit, IOC (59=3) Marketable against the touch: New, then filled at the touch. Not marketable: New, then Canceled 39=4
Market (40=1) New, then filled: a buy pays the offer, a sell hits the bid

FIX's default TimeInForce is Day, so the resting rule carries no 59 condition at all and catches the order that says 59=0 and the one that says nothing. An IOC that crosses is filled at the touch and not at its own limit — a buy bidding 230.00 into a 227.42 offer pays 227.42, because the price improvement is the client's.

The three refusals

OrderAnswer
A limit price finer than a cent, 44=227.4213 Rejected, 103=11 — SEC Rule 612 forbids a sub-penny quote at or above $1.00. 227.4200 is not sub-penny and rests
Sell short (54=5) with no LocateReqd (114) Rejected, 103=0 — Reg SHO requires a locate. Add 114=Y and it rests
A limit more than 5% from the printed mid Rejected, 103=3, naming the bound it crossed

Every reason code is one FIX 4.4 actually defines. 103=18 Invalid price increment is the exact name for the sub-penny case and does not exist before FIX 5.0 — the 4.4 enum stops at 15 and 99 — so the venue sends 103=11 and puts the specifics in 58. Every reply this venue can plan is validated against the bundled dictionary by its own test, which is how that was caught.

Market data

This is the only bundled venue that publishes. A MarketDataRequest (35=V) naming a listed symbol draws a MarketDataSnapshotFullRefresh (35=W) with both sides of the touch in round lots; ask for updates as well (263=1) and two MarketDataIncrementalRefresh (35=X) messages follow, one per side. A name it does not publish gets a MarketDataRequestReject (35=Y) with 281=0.

Fixed prints, drawn quotes

Every price the venue prints is a literal and every price it publishes is drawn across a band, which is the opposite of the FX venue and deliberate. A printed price is one a scenario can assert — AAPL market order fills at the touch expects 31=227.42 and means it. And nothing here is a Kotlin expression, so unlike the FX venue this one can be asked for orders at volume: its load set does 2,000 per phase in about two hundred milliseconds each.

The Load Client, and the set the FX venue could not ship

The Equity Load Client is five sessions, EQLG1 to EQLG5, on a memory store with no log. The example ships Equity rest and cancel:

fixtool load --set equity-rest-and-cancel --home ~/.fixtool/workspaces/equity-venue

Cancelling what you placed is the phase the FX venue cannot have. There, an order fills 250 ms after its ack, so a cancel phase would race the fill and land a nondeterministic mix of Canceled and “too late to cancel” — and a bundled example must never run amber. Here the order is still resting when the cancel arrives, every time. Phase two reports a healthy count of duplicates: a cancel draws a PendingCancel and a Canceled, the first is the match and the second is counted and not judged, which is what a venue answering an order with several ExecutionReports looks like.

The Crypto Venue

A Crypto Demo Venue acceptor on localhost:19879, open to any CompID, playing a 24/7 spot venue in BTC-USD, ETH-USD and SOL-USD. It exists to answer a fair question about the other three: does this tool only know the instruments a bank trades?

It would have been easy, and worthless, to ship the equity venue with BTC-USD where AAPL is — a crypto venue sends 35=D and gets 35=8 back like everything else. What makes this a different example is the set of rules a crypto venue has and an equity venue has no use for:

What only a crypto venue doesThe rule
Never closes A Day order (59=0) is refused, 103=11, naming the two TimeInForces it does keep. There is no day to be good for
Sizes in satoshis A quantity finer than the base increment of 0.00000001 is refused, 103=13. 0.10000000 is eight decimals written long and rests
Has a dust floor A quantity below the product's minimum size is refused, 103=13, naming the floor in the base currency
Sells maker-only access A post-only order (18=6) that would take liquidity is refused rather than filled

Post-only is the one worth opening the cards for. 18=6 ParticipateDontInitiate is FIX's way of saying “I want the maker fee, so do not let me cross”. A client sending it is asking the venue to refuse a marketable order rather than execute it at a worse economic outcome — the opposite of what every other venue in this build does. It is also a rule you cannot write without knowing both the order's price and the venue's own touch, which is why the post-only rules sit above the IOC fills and the resting rule: below them, a marketable post-only order would be filled, which is exactly what its sender paid to avoid.

The names, the prices and the sizes are the real ones. Products are written BTC-USD, the hyphenated form a crypto venue uses, not the BTC/USD an FX desk would write. Quantities are fractional and carry eight decimals, and the minimums are a dust floor rather than a round number.

The Load Client

The Crypto Load Client is five sessions, CXLG1 to CXLG5. The shipped set, Crypto rest, cancel and refuse, rests 2,000 GTC orders, cancels all 2,000, and then has 2,000 post-only orders refused — a phase that measures the refusal path at volume, which is a thing a venue's operators actually want a number for.

  1. Buy Side 1 asks. A QuoteRequest for 10mm of T 4.25 08/15/36, CUSIP 91282CMF5, naming 54=1 because it is buying

  3. A dealer quotes one way, because the buy side disclosed a side: the offer, its size and OfferYield(634), firm (QuoteType(537)=1) for thirty seconds
  4. The platform shows the buy side that quote under the buy side's own QuoteReqID and a QuoteID of the platform's, with the dealer named as role 35, liquidity provider
  5. Buy Side 1 lifts it: a QuoteResponse, 694=1, naming the platform's QuoteID at the level it was shown
  6. Both sides are confirmed. Each gets an ExecutionReport and a TradeCaptureReport, with one OrderID(37) and one TradeReportID(571) between them and the other side named as contra firm, role 17. The dealer with the next best quote is told it was the cover (694=4), and every other dealer quoting that the trade was done away (694=5)

The level booked is the one the platform showed, read back from its own RFQ book, never the price in the lift. A lift at a level it did not show, a counter, a quote for an RFQ that has already traded, a request for an issue it does not list and a request from a dealer are each refused, by name, to whoever sent them and to nobody else. A buy side that passes (694=6) ends the RFQ, and every dealer quoting is told.

An RFQ nobody trades is ended after a minute — the platform's An RFQ expires after is 60 seconds, and a request's own ExpireTime(126) comes first. Each quote is ended by name with a QuoteStatusReport, 297=7 Expired: to the buy side under the id it was shown, and to the dealer under its own. An RFQ nobody quoted is refused to the buy side instead, 658=99. FI RFQ Request 10y, buying, open for 20s asks for one that ends sooner.

A bond desk's vocabulary

The mechanics of an RFQ are the same everywhere and the vocabulary is not. A desk that trades bonds does not recognise itself in a venue quoting EUR/USD to five decimal places.

A disclosed side is quoted one way. Two-way is what a dealer shows a buy side that withheld direction — that is what it is for. Ask for a price naming 54=1 and you are shown the offer and nothing else, with Side(54) on the quote saying which side it is. Ask without a side and every dealer quotes both.

Why the levels are stated, not drawn. A Treasury trades in thirty-seconds of a point, so 98-16+ is 98.515625 and the prices between grid points do not exist. The native ${random:…} generator quantises to decimal places and no power of ten is a thirty-second, so the Dealer Load Client quotes its axe: a stated level, firm for thirty seconds, at the size asked. A quote is carried in decimals, as FIX requires, with the same level in 32nds in Text(58) so it can be read aloud. The yields are what those prices yield for T+1 settlement, so a below-par issue yields above its coupon and half a 32nd moves the ten-year a fifth of a basis point.

The CUSIPs are illustrative. They are well formed, check digit included, and shaped like Treasuries, and they are not real securities. Nothing here should be pointed at one: a demo platform quoting a live ISIN is one somebody will eventually mistake for a price.

3. Managing Connections

Creating a Connection Profile

Connection profiles store your FIX session configuration for reuse:

  1. Click New Connection in the toolbar
  2. Fill in the connection details:
    • Profile Name: A friendly name for this connection
    • Host: FIX server hostname or IP address
    • Port: FIX server port number
    • SenderCompID: Your FIX session identifier
    • TargetCompID: Server's FIX session identifier
    • BeginString: FIX protocol version (e.g., FIX.4.2, FIX.4.4)
  3. Click Save Profile to save for later use
  4. Click Connect to start the session

Store and log

Under Advanced Settings, beside Reset Options, a profile chooses where QuickFIX/J keeps its state for the session:

  • Message store: File (the default) keeps sequence numbers and sent messages under store/ in the workspace, so they survive a restart and resend works. Memory keeps them on the heap: sequence numbers start at 1 on every logon and nothing is written.
  • Message log: File (the default) writes QuickFIX/J's per-session message and event log under log/. None writes nothing. The session pane and the run records remain the tool's own evidence either way.

Pick Memory and None for a load or soak run: the per-message file appends cap how fast a session can issue, and a store that grows for the length of the run is not wanted. A memory store needs Reset on Logon, and the panel says so: without it the next logon would start at 1 while the venue expects the number it last saw, so the connection is refused rather than fixed behind your back.

Multiple Sessions per Profile (Load Testing)

A profile can open several concurrent FIX sessions in one click - useful for market data load testing. Set the Sessions field (initiator connections only, 1-100) and click Connect: each session opens as its own tab, named Profile Name [1], Profile Name [2], and so on.

Each session needs its own identity. The identity fields (SenderCompID, TargetCompID, Username, Password) accept three forms, and a numbering pattern resolves at Sessions 1 as well, to slot 1:

Form Example Result (3 sessions)
Numbering pattern LOADGEN{n} LOADGEN1, LOADGEN2, LOADGEN3. Use {nn} for zero-padding: LOADGEN01, LOADGEN02, ...
Comma-separated list SESS_A, SESS_B, SESS_C Session 1 gets SESS_A, session 2 gets SESS_B, etc. The list must contain exactly 1 or N values - anything else is rejected before connecting.
Single plain value LOADGEN Shared by all sessions. A unique SessionQualifier is derived per session automatically so the sessions stay separate on the client side.

Each field resolves independently, so for example 10 sessions can share one password while having 10 different usernames. The panel shows a live preview of the resolved identities and the aggregated group status, e.g. Logged On (3/3).

Shared CompIDs: a single plain SenderCompID/TargetCompID only works if the server accepts multiple concurrent logons with the same CompIDs - many venues reject the second logon. If your server assigns distinct session IDs, use a numbering pattern or a list.
  • Disconnect stops every session in the group
  • Connect reconnects any sessions that are down and re-opens closed session tabs until the configured count is reached
  • Profile edits take effect when a session reconnects
Load test setup: configure the profile once (e.g. SenderCompID LOADGEN{nn}, Sessions 10), then copy ~/.fixtool/connection_profiles.json and ~/.fixtool/saved_messages.json to the other machines.

Fanning a scenario out over those sessions

Once a profile opens several sessions, a saved scenario can be run once per session, all at once — fifty clients driving the same flow at the server under test. In the Scenarios rail, Run ▾ → Fan out over sessions…; pick the scenario, the profile that opens the lanes, and — if the scenario drives more than one session — which leg is the one being spread.

Each lane knows which client it is. Four names are in its scope before the first step runs, the same four Bulk Send seeds:

NameValue
${sessionIndex}the profile slot — lane 7 is slot 7 on every run
${sessionSenderCompID}that lane's resolved SenderCompID, e.g. LOADGEN07
${sessionTitle}the session's tab name, e.g. LoadGen [7]
${sessionQualifier}the session qualifier, where one was derived

So 11=ORD-${sessionIndex}-${uuid} gives every lane its own ClOrdID with no extra authoring. Each lane writes its own record under ~/.fixtool/runs/, and the report is a distribution — p50 / p95 / max over the gap between the bytes that left and the bytes that answered — rather than fifty rows nobody will click through.

From a build box, with no window: fixtool run book-a-trade --fan-out LoadGen opens every session the profile declares, waits for logon, and runs one lane per session that came up. Add --over <session> when the scenario drives more than one leg, and --json or --junit to keep the report. The exit code is the verdict, as it is for every other fixtool run.

Limitations — read these before trusting the numbers
  • Point the lanes at the server under test. If the far end is FixTool's own acceptor, you are measuring FixTool: every session of an acceptor shares one QuickFIX/J event thread, and every reply goes out through one scheduled thread, so an authored reply delay becomes a floor and the p95 you read back is the tool's own ceiling. The fan-out dialog says so when it detects this. FixTool is a load generator; making its venue side a load target is a different job.
  • Latency is measured at the client, from the moment FixTool handed the bytes to the session to the moment it read the reply. It therefore includes FixTool's own send and ingest path, not only the network and the venue. This is the run report's figure, taken at the FIX engine; the Latency panel stamps at the socket instead and leaves that path out — see 10. Latency Measurement.
  • Template expressions are evaluated one at a time, process-wide. The Kotlin expression engine is not thread-safe, so anything needing it — ${uuid}, ${out.D.11}, date arithmetic — is serialised across lanes. A plain ${name} reference to a value already in scope does not touch it. A scenario heavy in expressions will cap its own throughput before the venue does.
  • A session ingests at a bounded rate and counts what it had to discard. A run that lost messages says so in its report rather than reporting a silent gap — but at very high message rates that limit, not the venue's, may be what you are seeing.
  • A leg that cannot be spread is refused, not shared. If the scenario drives a second session that has no multi-session profile behind it, every lane would share its message log and could bind another lane's reply — so the fan-out is refused with the three things that would fix it. Run that leg at concurrency 1, or give it a profile of its own.
  • Lanes must be logged on. If the venue admits 38 of 50, the run uses 38 and says so; it does not wait or retry.
  • Records are trimmed when the run finishes. Failed lanes keep their messages whole and one passing lane is kept as a reference; the rest keep their verdict, timings and counts while their messages are dropped, with the count recorded. Fifty copies of the same three messages is not evidence worth the disk.

Load runs

A fan-out answers does this flow hold with fifty clients. A load run answers how does the venue behave when several thousand messages arrive at once: it issues one message across a profile's sessions without waiting for replies, then accounts for every reply that lands on any participating session.

Two doors, one dialog. In the Editor, the ⚡ Load button beside Send and Send to All opens the Load run dialog with the editor's fields as the template. In the toolbar, the run widget's ▾ → Load run… opens the same dialog with a picker over the saved messages. The dialog is one row per decision: the template and which of its tags vary per message, the profile whose lanes issue, other logged-on profiles that only listen, burst or rate, the tag pair a reply is matched on, the settle window, the seeds, and the store and log for this run. Every refusal is a sentence on screen and Run is what refuses. The run opens as a document tab that updates live and has Stop, and Recent ▸ lists it with ⚡ beside the run sets, opening the same document over the record afterwards.

Where the doors are. Your saved load sets, your saved scenario sets, Load run…, Load sets… and Recent are all in the toolbar's run configuration widget: each of them names a saved configuration, and none of them has anything to do with which tool window is open. Picking one aims the ▶ at it and ▶ is what runs it. The Scenarios rail's own Run menu runs what its list is showing: what is starred, what the filter shows, what is ticked, which scenario has an examples table, and a fan-out over sessions. Save these as a set… there names the selection it saves, and is how a scenario set gets into the toolbar's run widget. From the command line:

fixtool load "NOS EUR/USD 1M" --profile LOADGEN --count 4000 --settle 60s --json reports/load.json
fixtool load "NOS EUR/USD 1M" --profile LOADGEN --rate 500/s --for 10m --seed run=c118
  • Burst or rate. --count 4000 issues four thousand as fast as the lanes carry them. --rate 500/s --for 10m issues on a schedule the run never skips: a message that could not go on time goes as soon as it can, and the report says where the run fell behind and by how much. Those are the two shapes a single run has. A phase of a load set has a third, reactive, which takes its volume from the phase it reacts to and so has nothing a single run could ever fire it with.
  • Per-message values. 11=ORD-${run}-${messageIndex} gives every message its own ClOrdID, with run seeded by --set run=b7f2 so a second run can address what the first created. ${uuid} and ${utcnow} render per message. ${sessionIndex} is the lane's slot, 1-based as in a fan-out, so a profile that opens one session issues on lane 1 and it is never 0. Anything else is evaluated once per lane, and the report lists its tag under fixed.
  • Matching. A reply is matched wherever it lands, on the lane that sent or on a --listen session such as a drop-copy. The first reply carrying the request's id is the match and the round trip; a repeat is a duplicate, reported rather than judged. Nothing is forgotten before the settle window closes.
  • Three verdicts. Completeness (anything unanswered fails), rate (held, or a shortfall, which exits 0 unless --strict-rate), and tool (whether FixTool itself discarded traffic or could not get a message onto the socket). Issued is three numbers for the same reason: requested, handed to the engine, left the socket.
  • The record. loads/<id>/load.json in the workspace, with the wire of every unanswered request beside it and fifty specimen pairs. --json and --junit write the report where a build wants it.

Load sets: several runs in order, under one seed. Most load proofs against a venue are two or three runs that depend on each other. Burst NewOrderSingle, then cancel the same ClOrdIDs. Ask for quotes, then order against them. A load set is that as a saved file: an ordered list of phases, each a complete load plan with its own template, profile, match tags, shape and settle window, and two things the set owns.

  • The seed. Rendered once when the set starts and shared by every phase, which is the whole mechanism: ${messageIndex} is 1-based per phase and independent of the lane, so ORD-${run}-${messageIndex} in phase 1 and 41=ORD-${run}-${messageIndex} in phase 2 line up for every message. A seed value may be a generator such as ${uuid:4}, so a saved set gets a fresh run id every night rather than replaying one machine's four hex characters at the venue. --seed run=… overrides it, which is how a build passes its own number in.
  • The store and log, applied once to every lane the set opens, because applying them per phase would put a logon and a sequence reset in the middle of the set's clock.
  • The lanes. Every profile a phase issues from is opened before phase 1 dials, with all the sessions its profile declares and their 1-based slots, so ${sessionIndex} on a phase's lane is that lane's own slot and never 0. A profile named only in a phase's listen list gets one session, because nothing is ever issued on it. A profile that issues in one phase and listens in another, which is what a two-sided set is, listens on its issuing lanes and keeps every one of them.
  • Where a phase starts counting. ${messageIndex} restarts at 1 in every phase, so a phase that should address the second half says from 2,001. That is what makes a three-phase RFQ set possible: ask for 4,000 quotes, hit the first 2,000, pass the other 2,000.
  • What a phase keeps for the next one. A shared seed only works against a venue built to be addressable from it. A real counterparty answers a QuoteRequest with a QuoteID you could not have guessed, and prices the quote itself. So a phase can capture named tag values off each reply it matches — quoteId ← 117, offer ← 133 — kept at that request's own message index, and a later phase reads them as 117=${quoteId} and 44=${offer}. Only an earlier phase's captures are readable, and the refusal says which phase should have kept it. If the venue answers without the tag, the later phase cannot address that message: it is not sent, counted by index and name, and the phase fails, because the bar is every requested message answered and a message nobody asked is a hole in the proof.
  • A phase can react to the one before it. Phases run in order by default: 200 QuoteRequests, then the whole settle window, then 200 Quotes, then 200 QuoteResponses. That is three blocks and it measures three legs separately. A reactive phase instead issues one message for each reply the phase it reacts to is given, as that reply lands, so the three blocks become 200 chains, each one running at the venue's own speed. Reactive does not make a set faster. With four of 200 QuoteRequests unanswered, phase 1's settle window still runs its full 60 seconds. What it changes is that the 196 chains that worked finish in the first 200ms instead of a minute later, and that the report can say what one whole journey cost: the chain block gives the round trip leg by leg, with the handover between them, which staged phases cannot measure because nothing in them is one journey.
  • What a reactive phase takes from its trigger. Its count and its message indices, both. It asks for no number of its own, and it has no from N, because the message it answers is at its trigger's index, which is what keeps ${messageIndex} lining up along the whole chain. Phase 1 can never be reactive, since nothing runs before it, so the volume of a whole chain is set once by the first phase and inherited from there. It reads only what its trigger kept and what its trigger could itself read, and never a sibling's captures: with two phases both reacting to phase 1, phase 1's match fires them at the same moment, so neither has answered for the other yet. A message whose trigger never fired is unaddressable: it is not sent, counted by index, and the phase is incomplete, exactly as a missing capture is.
  • A cap is a ceiling, never a schedule. A reactive phase can be held to a number of messages a second, aggregate across every lane, and the tick in the dialog says never above. Sitting under it is the normal, healthy case and is never a shortfall: it means triggers arrived more slowly than the ceiling, which is the venue's answer and not the run's failure. So a capped phase gets its own verdict, CAPPED, rather than being judged against the cap as a rate is judged against its schedule, the chart draws the ceiling and paints no second red for being under it, and Compare will not rank one capped run against another.
  • Authoring one. In Load sets…, open a phase from the second on and the Shape segment offers Burst, Rate and Reactive. Reactive swaps the count for two rows: Reacts to, a picker naming each earlier phase the way every refusal does, 1 · Ask for a quote, and Speed, whose never above tick is the optional ceiling. In the file it is "shape": { "kind": "triggered", "cap": 200 } with "after": 1 beside it, and fixtool load --set runs it with no flag of its own, because the shape is in the file and there is no count to pass.
  • A phase can be muted. The mute chip on a phase row parks it: it keeps its template, its profile, its shape and its place in the order, and the set skips it on every run, opening no lane of its profile and judging nothing about it. Any phase, not only the last, because the set knows the real dependency graph: the one case it can prove is broken, a later phase reading a name only a muted phase keeps, is refused before a lane dials, in the reading phase's voice and naming the muted phase. The report shows it as a skipped phase noted muted in the set, at its own number, with ⊘ in the rail and MUTED on its badge, and the set's verdict counts it apart, so a clean set reads 2 passed, 1 muted rather than 1 skipped. The flag is in the file, so fixtool load --set in a build honours it.
  • If a phase fails. By default the set stops and reports the rest as skipped, each carrying its plan and a note saying why. Carry on runs every phase and the set verdict names the first that did not pass. Either way the set exits 1.
  • One record. loads/<id>/load.json holds every phase, and the JUnit file is one <testsuites> with a <testsuite> per phase. A single run is the same record with one phase, so the document, Compare and Recent read a run and a set out of the same file rather than out of two shapes.

A run brings up the sessions it names. Which profiles a saved set needs is the one thing its name does not say, so running one used to mean opening the file, connecting them by hand, and finding out one refusal at a time which one you had missed. Every profile a live phase issues from or listens on that has no session logged on is now connected before phase 1 dials — acceptors first, so a port is bound before anything dials it — and the run waits up to ten seconds for the lanes to log on. It fires only where the run would have been refused: a profile already up is left exactly as it is, and a parked phase's profile is neither opened nor waited for. A profile that never arrives is the refusal it always was, no session of 'X' reached LOGGED_ON, so there is nothing to issue on, said after the wait rather than before it. This is what fixtool load --set has always done, and the window does it now too.

And the venue, when the venue is one of ours. A set names the profile that issues and never the endpoint it dials, because ordinarily that endpoint is somebody else's server and there is nothing here to connect. The bundled examples are the other case: the lanes dial a FixTool acceptor on loopback, so bringing up the client alone would leave them dialling a port nothing had bound. That acceptor is brought up too, and first. An acceptor already bound is left exactly as it is.

A port number is not an identity. Three things have to agree before a profile your set never named is dialled: the lanes dial loopback, a saved acceptor binds the port they dial, and that acceptor is the session they address — its SenderCompID is the counterparty they name, and it would accept who they say they are. If two saved profiles answer to all of that, neither is brought up. And if something already holds the port — a forwarded local port to a real venue is the usual reason your lanes look like loopback at all — nothing is brought up either: our acceptor could not bind it, and your lanes are already reaching the venue through it. This is what keeps a dev set off the UAT simulator saved on the same port number.

The run widget's ▾ row for a set says which profiles it runs on and which of them pressing it will connect, so you can read it before you press ▶.

The lanes are left up afterwards: the run borrowed them, it did not own them, and the next set that names them finds them there. ✕ Close all in the toolbar is how a box goes back to nothing: see Connect.

Sets live in <workspace>/load-sets/<name>.json, beside the records they produce, so a set checked in next to the code survives a fresh --home. From a build:

fixtool load --set rfq-round-trip --seed run=$BUILD_NUMBER --junit reports/rfq.xml
echo $?    # 0 every phase passed · 1 a phase did not pass, or the set was stopped · 2 it could not start

A reply that arrives while a later phase is running is credited to the phase that asked for it. Against a matching venue that is not a corner case: phase 1's orders keep drawing fills through the cancel phase, and a set counts them as phase 1's late replies rather than as phase 2 strays.

Pick Memory and None under Store and log for the load profile, or pass --store memory --log none, so the run measures the venue's keep-up rather than FixTool's file appends. A memory store needs Reset on Logon.

Connect

Connect in the toolbar is the shortcut past the Connection panel: it drops down every saved profile, and picking one connects it. Use the panel when you are authoring a profile; use this when you already have one and just want it up.

Connect is only about connecting: it lists the profiles in the open workspace, and picking one connects it. Changing which workspace you are in is the switcher at the top left — see Workspaces — because opening a workspace changes which profiles exist at all, and that is a different question from which one to connect.

Connect ▾, ⏻ Disconnect all and ✕ Close all are one group, and everything in it is about sessions: bring one up, take them all down, close every pane. Running things is a group of its own further along the row.

That group is the run configuration widget, and it is a name with a ▶ beside it. The name is the saved load set or scenario set the button will run, so the window always says what happens next; its ▾ lists every saved configuration and picking one aims the button rather than running anything. The choice is remembered between launches. ▶ runs it and becomes ■ while it runs, ⌃R (Ctrl+R off macOS) does the same from the keyboard, and a button that cannot run says why on hover. Load run… and Load sets… are in the same menu and still open their dialogs. On a workspace with nothing saved the chip reads Load sets…, the dialog a configuration is made in, because there is no configuration to name yet — not Load run…, which is not something the ▶ can run. The menu behind it is the same menu, so both dialogs and every run under recent are reachable from the first launch. A scenario set is saved from the Scenarios rail and joins the list as soon as it is. See Load runs.

⏻ Disconnect all is the second of the three, and it takes every session down at once, which is what putting a box back to nothing connected used to mean doing one profile at a time. The tooltip says how many sessions it will drop and over how many profiles. It asks no confirmation, because a disconnect loses nothing: Connect puts it all back in one click, and nothing is cleared on the way out. The venue's orders and quotes stay where Clear order book can reach them, and the message logs, the run records and the panes are untouched. The one case that would lose something is a live load run or set, and there the button is disabled with the reason in its tooltip: stop the run first. On the control surface the same action is POST /disconnect {"all": true}, which reports what it dropped and is refused the same way.

✕ Close all is beside it, and is the half Disconnect all deliberately leaves undone: it closes every session pane, disconnecting them on the way so the far end gets a Logout rather than a socket that stopped answering. A load set that opens fifty lanes leaves fifty panes, and putting the box back to nothing meant closing them one at a time. It counts panes rather than connections, because a pane left over from a run you have already disconnected is exactly what it is for.

This one does ask, and it asks in the button rather than in a dialog: the first click arms it — Close 50 panes? Click again — the second closes them, and it disarms itself after a few seconds so an armed button never sits waiting for somebody who has forgotten what it is armed for. It asks because the difference between the two buttons is exactly what cannot be put back: Connect returns the sessions, and nothing returns a pane's messages. Your profiles, workspace, scenarios, run records and load reports are untouched. A live load run or set refuses it in the same words. On the control surface it is POST /sessions/close, and the MCP tool is fixtool_close_sessions.

Workspaces

A workspace is a folder holding the profiles, saved messages, scenarios and run records you are working with, plus QuickFIX/J's own sequence store and message log. There is one kind of workspace and two ways to get one: New makes an empty one, Open opens a folder you already have — and the examples FixTool ships are folders already.

All of it is on the switcher at the top left, which shows the open workspace by name and holds New, Open, Recent and Close. It is deliberately not in Connect: that menu connects a profile, and opening a workspace changes which profiles there are.

Default is ~/.fixtool itself. It is a workspace like any other and it is where everyone starts, including everyone who installed FixTool before workspaces existed — so nothing had to move on upgrade, the directory just got a name. Default cannot be closed and never appears in Recent, because closing any other workspace is what comes back to it.

An example is not a third thing. It is a workspace we ship inside the application, which is why FixTool copies each one out into ~/.fixtool/workspaces/ when it starts: editing it in place would mean editing the installed app, and the next release would overwrite your work. Once copied it is an ordinary workspace with nothing example-ish about it — same files, same loaders, opened with Open and listed in Recent beside any other.

The copy happens once. A folder that is already there is never written over, so whatever you changed in it survives every start. Delete one and the next start lays it down fresh.

A copy remembers which example it came from, in a small .fixtool-origin file. That is the only thing distinguishing it from a workspace you made yourself, and it is there so Settings → Storage can offer Reset: the shipped example laid down again, in the same folder. Your current copy is renamed rather than deleted, to fx-venue-before-reset-<date>, so anything you want out of it is still there. That is why Reset needs no confirmation.

What does not move with a workspace is anything belonging to the person at the keyboard: the window layout, the rail's sort order and everything in Settings. Opening a second workspace gives you other profiles and other scenarios, not a fresh install.

The data dictionary moves only when a workspace names one. A dictionary decides where each repeating group starts, so it decides the order a venue's fields arrive in, and a scenario's rows are written in that order. Read in a different dictionary, the same scenario fails on rows that have only moved. So a workspace may name its dictionary in workspace.json — {"dictionary": {"fixVersion": "FIX_4_4"}} for a bundled one, or {"dictionary": {"path": "dictionaries/venue.xml"}} for a file, found beside the workspace when the path is relative — and while that workspace is open, its dictionary is the one loaded, whatever Settings → Protocol says. That page says so while it happens. A workspace that names none is read in the dictionary in Settings, as before. fixtool run --home and fixtool load --home choose the same way.

Every example names the bundled FIX 4.4. A copy laid down before examples did has no workspace.json, and is read in the dictionary its example names; write {} into workspace.json to have a copy use the one in Settings instead.

Logon passwords are kept in secrets.json beside the profiles rather than inside connection_profiles.json, so the interesting half of a workspace — CompIDs, hosts, acceptor rules — is a file you can commit or hand to a colleague without handing over a credential. This is a separation, not encryption: the two files sit in the same directory with the same permissions. A workspace opened from an example arrives with a .gitignore already covering the secrets, the store, the log and the run records.

Recent lists workspaces by their own path rather than the folder that holds them, because workspaces default to a single workspaces/ directory and a parent would read the same on every line. Default never appears there: it is where Close takes you, so it is always one click away.

Set FIXTOOL_WORKSPACE to move the whole installation, Settings included — what a build box wants when the profiles and scenarios under test are the ones checked in beside the code. A leading ~ is expanded, because a CI config file is not a shell. fixtool run --home still wins over it for the length of one run.

Environments

An environment is where a counterparty is, as distinct from who it is: a host, a port, a TLS flag. A profile answers both questions at once, which is how a desk ends up with UAT1-BuySide, QA1-BuySide and DEV1-BuySide — three profiles carrying one counterparty's CompIDs and differing only in an endpoint. Every rule change then has to be made three times.

With environments, a connection is a counterparty times an environment: pick a profile in Connect ▾ and it asks which environment to reach it in. The profile on disk is not touched, so choosing UAT does not rewrite it and leave the next person guessing where it was last pointed.

The session qualifier is the environment's name, and that is load-bearing: QuickFIX/J keys its sequence-number store on BeginString, SenderCompID, TargetCompID and the qualifier, so two environments reached by one counterparty would otherwise share a store and fight over sequence numbers. Naming the qualifier after the environment makes that impossible to get wrong by hand.

None of this is on until you ask for it. Settings → Storage offers Extract environments when your saved profiles already look like a grid, and shows exactly what it would produce first. Extracting adds the environments and changes nothing else: the profiles keep working exactly as they do now, and As saved stays in the menu for the endpoint a profile already names.

Example workspaces

For testing and learning, open one of the example workspaces (see Section 2). Each provides:

  • A venue acceptor, the FX venue on port 19876 or the RFQ venue on port 19877, whose behaviour is a list of rules you can read and edit
  • Client profiles already pointed at it, ready to log on as soon as the venue is up. The RFQ venue's include a five-session load client on a memory store
  • Message templates and scenarios that run green on a fresh install
  • No external dependencies required

Grouping by conversation

The tree icon in a session's own button strip folds that session's grid by business exchange — every message that shares a correlation id with another, transitively, becomes one group. The chain follows the ids themselves: a Quote carrying both QuoteReqID and QuoteID joins them, so the order placed off that quote lands in the RFQ's group with no configuration. Your venue's own correlation ids join the moment they are declared beside its dictionary — see Your venue's own correlation ids.

Each group gets a summary row in the grid's own columns: the id that opened the exchange and its instrument, what arrived (NewOrderSingle ×1 · ExecutionReport ×2), the last status any message stated — quoted in the dictionary's words, never computed — and the exchange's first-to-last elapsed time in the Latency column. Click a summary row to fold or open its group. Fold everything and the grid reads as an index of exchanges: one row per order, per RFQ, per subscription.

  • Off is off. The toggle starts off and the flat chronological grid is unchanged. Grouping trades global timeline for adjacency — the flat view is one click back.
  • Per session, like the filter. Each pane folds independently — a both-sides test legitimately shows the same exchange from both chairs, and folding it in one pane must not fold the other. Group by conversation in View ▾ on the toolbar is the bulk switch for every session at once.
  • Nothing is hidden. Messages carrying no correlation id — heartbeats, logons, anything the loaded dictionary cannot place — sit in an Ungrouped group at the bottom, counted, never dropped.
  • The summary only quotes. Filled appears because a reply said 39=2; a two-leg request with two Symbols shows no instrument rather than guessing one. What the header cannot point at, it does not say.

Opening the Editor

The RAW MESSAGE pane — type either side

Beneath the field grid is a RAW MESSAGE pane, and it is not a read-only preview: the two are bound both ways. Edit a field and the raw string follows; type or correct the raw string and the grid re-parses to match. So a message can be built whichever way is faster for the one you have — row by row when composing from scratch, as a single line when copying the shape of something that already exists.

  • Paste from Clipboard turns a message copied out of a log, a ticket or an email into fields, ready to edit and send — the usual way a support case becomes a reproduction.
  • Copy takes the raw string back out.
  • Clear All Fields empties the editor.

  • Sessions that are not logged on are skipped
  • A notification summarizes the result and names any sessions where the send failed

Send to All is one message on every session, once. To issue thousands and account for every reply, see Load runs.

6. Message Templates (Advanced)

What are Template Expressions?

Template expressions allow you to dynamically generate field values using Kotlin expressions. This is especially useful for:

  • Generating unique IDs automatically
  • Inserting current timestamps
  • Referencing values from previously received messages
  • Creating responsive message workflows

Template Syntax

Template expressions are enclosed in ${...} and evaluated when you send the message:

Basic Templates

Template Result Description
${UUID.randomUUID()} a1b2c3d4-e5f6-... Generate random UUID
${System.currentTimeMillis()} 1705419265123 Current Unix timestamp
ORDER-${UUID.randomUUID()} ORDER-a1b2c3d4-... Prefix with text

Timestamp Formatting

${LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMdd-HH:mm:ss.SSS"))}

Result: 20250116-14:32:45.123

Common patterns:

  • "yyyyMMdd" → 20250116
  • "HHmmss" → 143245
  • "yyyyMMdd-HH:mm:ss" → 20250116-14:32:45

Variable Assignment and Reuse

When you need to use the same generated value in multiple fields (like using the same UUID in multiple tags), you can assign the value to a variable and reuse it:

Assignment Syntax

${varName = expression}

The first time you use a value, assign it to a variable. Then reference the variable name elsewhere:

${orderId = UUID.randomUUID()}

Later in the same message, simply reference the variable:

${orderId}

Example: Reusing a UUID in Multiple Fields

Tag 11 : ${orderId = UUID.randomUUID()} (Assign and use in ClOrdID)
Tag 37 : ${orderId} (Reuse same value in OrderID)
Tag 41 : ${orderId} (Reuse again in OrigClOrdID)

Result: All three tags will have the same UUID value.

Example: Reusing a Timestamp

Tag 52 : ${ts = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMdd-HH:mm:ss.SSS"))} (SendingTime)
Tag 60 : ${ts} (TransactTime - same timestamp)

Result: Both timestamps will be identical.

Variable Naming Rules

  • Variable names must start with a letter or underscore
  • Can contain letters, numbers, and underscores
  • Examples: orderId, my_timestamp, id123

Multiple Variables

You can define and use multiple variables in the same message:

11=${orderId = UUID.randomUUID()}
37=${orderId}
52=${timestamp = LocalDateTime.now()}
60=${timestamp}

Template Expression Validation

FixTool automatically validates all template expressions before sending messages to ensure they evaluate correctly. This prevents sending messages with broken or invalid expressions.

What is Validated

When you click Validate or Send, FixTool checks all template expressions for:

  • Syntax Errors: Invalid Kotlin code that won't compile
  • Undefined Variables: References to variables that haven't been assigned
  • Null Evaluations: Expressions that evaluate to null (like accessing non-existent message fields)

What Validate checks against the dictionary

Validate also checks every field against the loaded data dictionary, and reports every problem it finds rather than the first: a value the field does not allow (54=X), a value without the field's format (38=1,000 is not a quantity), a field the message type requires and the message does not carry, and a tag the message type does not define. A value still written by an expression is left to Send, which judges what it resolves to. The rules are QuickFIX/J's own, applied to the dictionary you loaded, so they are only as close to the counterparty's as that dictionary is.

Where problems are shown

The count is beside Send (3 errors, or Valid), and the problems are in one row under the search box: how many errors and warnings, the worst of them, and how many more. Click the row, or the count, to open the list; it grows to six rows and then scrolls. Each problem goes to the field it is about, and a required field the message is missing offers Add. The rows it is about are marked down their left edge in the grid. Editing the message withdraws all of it, because it was about the message as it was.

The scenario editor shows the same row for the whole scenario, live: each Send that runs is checked the same way, a name that is read but never minted is a warning on the first step that reads it, and every step with a problem carries its count in the step list, so a bad Send is found without opening it.

Validation Errors

If validation fails, the row under the search box names the refusal and each problem after it:

Example Validation Errors

❌ Cannot send message - Fix template expression errors:
Field 11: Template error in '${badSyntax!}': Expecting an element
Field 38: Template error in '${undefinedVar}': Undefined variable: undefinedVar
Field 44: Template error in '${incoming["D"].valueOfTag(99999)}': Expression evaluates to null

Validate Button vs. Send Button

  • Validate Button: Checks expression syntax and variable definitions without message context. Use this to catch basic errors before receiving incoming messages.
  • Send Button: Performs full validation with access to all incoming and outgoing messages. This catches null evaluations and message-dependent errors. Messages will not be sent if validation fails.
Best Practice: Use the Validate button while building your template to catch syntax errors early. When you're ready to send, the Send button will perform a complete validation including message context.
Important: Messages with template expression errors cannot be sent. Fix all validation errors before attempting to send. Expressions that evaluate to null (like accessing non-existent fields) are blocked to prevent sending incomplete data.

8. Filtering Messages

There are two filters and they compose. The global filter in the middle of the toolbar applies to every session at once, and each session's own filter row applies to that pane alone. A message is shown only if it passes both, so you can narrow every pane to EUR/USD from the toolbar and still keep one pane on 35=8 of its own.

The global filter

It sits in the middle of the toolbar, between the workspace and the connect controls, and it is always there.

  • Regex: Filter all panes (regex), the box in the middle of the row. ⌘⌥F (Ctrl+Alt+F off a Mac) puts the keyboard in it with the pattern selected.
  • Both / IN / OUT: the three segments beside it, the grid's own IN and OUT in the grid's colours. The pressed one is what every pane shows: both directions, incoming only, or outgoing only. They keep their words at every window width.
  • Clear it by emptying the box, pressing Both, and dismissing the Following chip with its own ×.

It cannot narrow a pane without saying so. There is nothing to open and nothing to put away: the pattern is in its box and a direction segment is pressed, in the open, so a pane is never left filtered by a control nobody can see. Typing here never touches a pane's own filter: clear the toolbar and every pane is exactly as its owner left it.

A session's own filter row

Each pane's funnel icon opens a row with three controls, which are finer than the global ones:

  • Regex: a pattern (pattern…).
  • MsgType: a comma-separated list (R,S,AJ…) — matched against the message's type, so it cannot accidentally hit a payload that happens to contain the same characters. Prefer it to a regex whenever you are selecting by message type.
  • Dir: incoming, outgoing, or both, for this pane.

What the regex actually matches

The pattern is matched against the raw FIX message, so it sees tag numbers, not field names. 11=ORDER.* finds orders whose ClOrdID starts with ORDER; ClOrdID=ORDER.* matches nothing at all, because those characters are never on the wire. This is the commonest reason a filter looks broken.

Precisely, each row is matched as <time> <<|>> [<MsgType>] <raw message>, pipe-delimited, and the match is case-insensitive and unanchored. A pattern that does not compile is treated as no filter rather than as an error, so a half-typed regex shows everything instead of nothing.

When you want an exchange rather than a pattern, do not write a regex for it: Follow narrows every pane to one exchange by correlation value, so it grows as the venue mints new ids and can never match ORD-9 inside ORD-91. Following leaves both filters untouched and restores them when you stop.

10. Latency Measurement

Overview

FixTool can measure round-trip time (RTT) for FIX messages by correlating outbound requests with their corresponding inbound responses. This helps you analyze trading system performance and identify latency issues.

How It Works

Latency tracking correlates message pairs using standard FIX correlation IDs:

  • When you send a message, FixTool records the timestamp and correlation ID
  • When a response arrives with a matching correlation ID, the round-trip time is calculated
  • Latency is displayed on the outbound message in the grid view
  • Each session tracks its own latency statistics independently

Supported Correlation IDs

Tag Name Typical Usage
11 ClOrdID Order requests → Execution Reports
131 QuoteReqID Quote Requests → Quotes
117 QuoteID Quote responses
262 MDReqID Market Data Requests → Market Data responses
37 OrderID Order-related messages
17 ExecID Execution Reports
112 TestReqID TestRequest → Heartbeat. FIX's own ping: the venue's session engine must echo the id, before any order book or risk check and with nothing placed. Send 35=1|112=PING-1| from a template or a scenario for a safe probe of the network and the engine alone — the floor under every order round trip, and the part of an order's latency that is not the venue's business logic. The example brings both: a Session Probe template and a Session round-trip probe scenario, described under 2. The FX Venue Example.
— Logon The session handshake itself (35=A out → 35=A back) — how long the venue took to let you on. A Logon carries no correlation tag, so FixTool pairs it per session rather than by a field.

The seven tags are the defaults, not the limit: the list is edited under Settings → Latency → Correlation tags, any tag in the dictionary can be added, and a reply is paired with its request on the first tag in the list that both carry. A tag that is not one of the built-ins is shown in the panel under its dictionary name. A venue's own identifier declared under Protocol → Venue tag roles is read by scenario capture and the conversation grid, not by the latency tracker, so add it to this list as well to time it.   • Green - Normal latency (below warning threshold)

  • Red - Critical (above critical threshold)

Metric Description
Count Number of correlated message pairs
Min Fastest round-trip time observed
Max Slowest round-trip time observed
Mean Average round-trip time
Median (p50) Middle value - 50% of requests are faster

Tip: Percentiles are more useful than averages for understanding latency. A low p50 with a high p99 indicates occasional slow responses that averages would hide.

Where the Stamps Are Taken

Both ends of a round trip are stamped at FixTool's socket, by a filter in the network layer QuickFIX/J is built on:

  • Send — the instant the operating system has accepted the last byte of the message. Serialisation, the write queue and TLS encryption are all behind that point.
  • Receive — the instant one message has been framed out of the (decrypted) byte stream. QuickFIX/J's queue, parse and dictionary validation are all ahead of it.

So the number is network plus venue, and nothing of FixTool's own FIX engine on either side. What remains inside it is the kernel's socket handling and, on a TLS session, the decryption of the reply — single-digit microseconds on a warm JVM.

No setup. The stamps need no privileges, no packet capture library and no network interface to choose, and they work identically on a plain and on a TLS connection (a venue on port 443, say). Earlier versions offered a libpcap capture for this; it could not read an encrypted stream and has been removed.

The badge on the Latency Panel's header reads Socket; hovering it repeats the two definitions above.

Round trips only, never one leg. Both stamps come off this machine's clock, so a round trip is a difference on one clock and is sound: whatever that clock's offset from true time is, it cancels in the subtraction. A one-way time is not. Comparing a send stamp against the venue's own SendingTime(52) or TransactTime(60) differences two different machines' clocks, and the offset between them lands whole in the answer — on an unsynchronised desktop, routinely tens of milliseconds, which is larger than the latency being measured and enough to make it come out negative. So the panel answers how long the round trip took, and never how long the outbound leg took.
A run report's step latency is a different number. Where a scenario report shows a step latency, that figure is taken from the FIX engine's own capture stamps rather than the socket's, so it includes FixTool's own parse, validation and dispatch. The same exchange therefore reads higher there than it does here, by design and not by disagreement — see 12. Automated Verification & Scenarios.

Configurable Thresholds

On the Latency page you can configure thresholds:

  • Warning Threshold: entered in milliseconds, default 100 ms - round trips above this show in yellow
  • Critical Threshold: entered in milliseconds, default 500 ms - round trips above this show in red; Save is refused if it is not above the warning threshold
  • History Size: Number of samples retained for statistics (default 10,000)

Clearing Statistics

To reset latency statistics:

  • Open the Latency Panel (the Latency tab on the right stripe, ⌘6)
  • Click the Clear/Trash icon button
  • This resets all statistics, pending correlations, and history for the current session
Note: Clearing messages from the session (via "Clear All") does not clear latency statistics. They are tracked independently.

Troubleshooting

Latency column shows empty

  • Ensure latency tracking is enabled (Settings → Latency)
  • Reconnect the session after enabling
  • Latency only appears on outbound messages after a matching response arrives
  • Check that your messages contain supported correlation IDs

The number looks too small, or too large

  • Against the demo venue a round trip is its simulated latency (40–80ms by default) plus a few tens of microseconds of loopback; set the venue's latency to Off to see the floor
  • A round trip is stamped on this machine's clock at both ends, so it is unaffected by the venue's clock — but a single stamp compared against a venue timestamp is only as good as the two clocks' agreement
  • Nothing FixTool does after a reply is framed — queueing, parsing, validating, drawing — is in the number; a slow UI does not make a venue look slow

Statistics not updating

  • Ensure you're sending messages with correlation IDs (ClOrdID, QuoteReqID, etc.)
  • Verify responses contain matching correlation IDs
  • Check that both request and response occur within the same session

11. Automation & AI Control

FixTool can be driven by Claude (or any MCP client), curl, or CI scripts for automated FIX testing — connect to a gateway, send messages, wait for and verify responses, manage templates, configure acceptor auto-responses, and capture screenshots. An MCP server is built into the app (loopback-only, off by default), so there is nothing extra to install.

The quickest way in — the built-in terminal

The Terminal tab at the foot of the left stripe (⌘7) opens a shell in the bottom dock, across the whole width of the window: drag the grip at the top to grow it, and the same tab (or ⌘7 again) hides it. Hiding is all a minimize is here, and it leaves the shell running: a claude session survives being put away and comes back where you left it. It is a real terminal on a real PTY, so a full-screen TUI renders and reflows properly.

Its point is what it puts in the environment. The running control endpoint is injected into the shell, so a claude you launch in here already targets this FixTool over MCP — no port to look up, nothing to register, no second window to arrange beside the first. Enable automation control (below), open the terminal, type claude, and ask it to drive the app.

Not to be confused with the Terminal view in Viewing Messages, which is a way of rendering the message grid as raw text. This is a shell.

The steps below are the manual route — what to do when you want Claude Code running in your own project's directory, against your own codebase, driving FixTool from outside.

Step 1 — Enable automation control

  1. Open Settings (gear icon) and choose the Developer page.
  2. Tick Enable automation control.
  3. Choose a port (default 8765) and click Save.

The control + MCP server starts immediately, listening on 127.0.0.1 only.

Step 2 — Connect Claude Code

Register the built-in MCP server once (the Settings screen shows this exact command):

claude mcp add --transport http fixtool http://127.0.0.1:8765/mcp

This works from any project directory; add --scope user to make it available in every project. No Node, npm, or source checkout is required.

Step 3 — Ask Claude to drive FixTool

Describe the task in plain language and Claude picks the right tools. For example:

"Use the fixtool tools to connect to the demo server, send a NewOrderSingle for EUR/USD, then show me the ExecutionReport."

Claude can be working in a completely different codebase (your own FIX project) and still drive FixTool to test against your gateway.

Loopback & off by default. The server only accepts connections from this machine (127.0.0.1) and never starts unless you enable it. An optional shared secret (FIXTOOL_CONTROL_TOKEN environment variable) can be required on every request; developers can also enable the server with the FIXTOOL_CONTROL_PORT environment variable, which overrides this setting.

The full tool list and the HTTP API are documented in the Automation Guide. Acceptor auto-response rules have their own chapter here: §13.

12. Automated Verification & Scenarios

Instead of eyeballing a response to decide whether it looks right, you (or an agent) can machine-check a received message tag-by-tag against an expectation — an ordered list of per-tag matchers. The result is a green/red verdict per tag, so a wrong field is pinpointed immediately and a check can be repeated identically every time. This is the foundation for turning a manual test flow into a repeatable regression check.

Two automation tools drive it (available over MCP, the HTTP API, and curl once automation control is enabled):

  • fixtool_capture_expectation — take a received message and get back a draft expectation whose matchers are pre-seeded from the data dictionary (timestamps become time matchers, prices/quantities become numeric matchers, IDs become presence checks, volatile header tags are dropped). You edit the draft instead of writing matchers from scratch.
  • fixtool_assert — assert a received message against an expectation. It selects the message (by message type / direction / index) or awaits one for up to timeoutMs, then returns {passed, tags:[{tag, matcher, expected, actual, passed}]}.

Matcher types

MatcherChecks that the tag…
exactequals a literal value (the default for business fields)
notEqualis present, and is anything but a literal value — "the venue must not send me OrdStatus=Rejected". Not the same as absent: a tag that never arrived satisfies neither, because "not X" about a field the message does not carry is a question with no answer
presenceis present; its value is ignored (e.g. a venue-assigned OrderID/ExecID)
absentis not present (e.g. no reject Text)
oneOfis one of a set of values (e.g. OrdStatus in 1 or 2)
regexmatches a regular expression
numericequals a number within a tolerance (so 1.2345 = 1.23450; widen the tolerance for fuzzy price/qty checks)
rangeis above and/or below a bound — > 10000, <= 1.0850, or between two ([1.08, 1.09)). Either bound may be left open and either may be exclusive, so this covers all four comparisons and between. For the assertion a literal cannot make: CumQty <= OrderQty, or a price that came back inside the band
temporalis a timestamp near "now" (± N seconds) or a date equal to today — instead of a brittle literal time
referenceequals a ${…} expression resolved over the session, e.g. an ExecutionReport's ClOrdID echoes the order you sent: ${out.D.11}

The field's type decides which of these can be judged. numeric and range fail every value that will not parse as a number, and temporal every value that is not a timestamp or a date meaning today. Setting one of those on a text field is therefore not a loose assertion — it is a row that can never go green, not even against the message it was captured from. The matcher dropdown in the reconcile editor dims the types a field cannot carry and puts the reason in place of their description ("numeric — ClOrdID(11) is STRING, not a number"). They stay pickable, because asserting on a value your dictionary has never heard of is exactly what this tool is for, and a custom tag has no declared type at all — but you are told before you pick, not after the row reddens.

The one to watch is a tolerance on an enum-coded field. PartyRole(452) and OrdStatus(39) parse as numbers perfectly well, so nothing downstream objects — but 8 ± 3 over a vocabulary of codes quietly accepts six other meanings while reading like a tolerance. Use oneOf. Likewise a SettlDate or TradeDate is a fixed business date, not "today": assert it exact, not temporal.

Order is the address. An expectation is an ordered list of rows, and the k-th row for a tag asserts the k-th occurrence of that tag. A message with two party entries gets two 448 rows and two 452 rows; the second 452 row checks the second entry. There is no path and no group entry — an earlier design located a field by identity ("the entry whose PartyRole = 1"), which does not work, because one firm acting in two roles puts the same 448=FIRMA in both entries. Position identifies; identity does not.

Your rows must also be a subsequence of the reply — they must appear in the order you list them. If the venue sends 37 before 11 and you list 11 first, the step fails with status: moved. Capture seeds rows in the venue's real wire order, so a captured scenario is a subsequence of its own golden by construction; hand-write an expectation only when you know the order.

OPEN vs STRICT

  • open (default) — only the tags you list are checked, in the order you list them: your rows must be a subsequence of the reply. A tag you do not mention is ignored, so a venue adding an optional field doesn't fail the check. Use an absent matcher to forbid a specific tag.
  • strict — additionally asserts the message's shape: the same tags, the same number of times, in the same order. Any unexpected tag (besides the session envelope) fails the check. For contracts that must be exact.

Example

After sending a NewOrderSingle and receiving an ExecutionReport (35=8), assert it:

{
  "session": "Demo Client 1", "messageType": "8", "direction": "in", "timeoutMs": 5000,
  "fields": [
    { "tag": 11, "matcher": { "type": "reference", "expression": "${out.D.11}" } },
    { "tag": 37, "matcher": { "type": "presence" } },
    { "tag": 39, "matcher": { "type": "oneOf", "values": ["0","1","2"] } },
    { "tag": 60, "matcher": { "type": "temporal", "kind": "now_within_tolerance", "toleranceSeconds": 30 } },
    { "tag": 150, "matcher": { "type": "exact", "value": "0" } }
  ]
}

Or just ask an agent in plain language:

"Send a NewOrderSingle for EUR/USD to the demo server, then assert the ExecutionReport has ExecType=New, an OrderID, and a ClOrdID that matches the order I sent."

Repeatable scenarios (author once, run forever)

An assertion checks one message; a scenario chains a whole flow — a saved, parameterized sequence of sends and assertions that a deterministic runner replays identically every time, with no AI in the loop. Author it once (by hand or with an agent); re-run it as a regression test forever.

A scenario is an ordered list of steps over a single persistent variable scope:

  • send — a (parameterized) message; ${…} resolves at run time, and a value set in one step is visible in later steps.
  • expect — await the next matching message and assert it against an expectation (the same matchers as above). Successive expects walk successive messages, so a partial-fill sequence (two partials then a fill) is just three expect steps.
  • wait — block until a state (e.g. LOGGED_ON) or a matching message.
  • clearMessages / resetSeqNum — typical setup steps for a clean start.

setup steps run first; teardown steps always run, even after a failure. Each step can target a different session, so one scenario can drive an initiator and assert on an acceptor.

In the app they are rows of the editor's step list like any other, above and below the flow and badged SETUP or TEARDOWN, so they take the same mute, remove, re-order and session controls. That is where a captured scenario's Clear messages step lives, and that step is what erases the session's message log on every run: mute it or remove it there to keep the log between runs. A step's phase is changed with the runs in picker in its detail pane, beside the session, which is how a scenario with no setup gains one: insert the step, then set its runs in to setup. Numbering counts the flow, so Step 3 is still the run report's step 3 however many setup rows sit above it.

BINDING (the chip in the editor's header, binding in the file) says which messages an expect step may match. ANY, the default, lets a step match any message in the session log, including one that was already there before Run was pressed. On a session that is always full of the expected type that can pass on a reply to an earlier run, and the report flags it when it happens. THIS RUN ("binding": "this_run") lets a step match only a message that arrives after Run is pressed, so a step with no new reply times out instead of passing on an old one. It does not clear the log, which is what a setup Clear messages step is for. Its neighbour TRAFFIC is the other stream-level question, and about the messages no step bound rather than the ones a step may: OPEN ignores them, STRICT fails the run on them (session administration exempt).

Four tools manage them: fixtool_save_scenario, fixtool_list_scenarios, fixtool_run_scenario, and fixtool_delete_scenario. A run returns a per-step, per-tag pass/fail report; pass format:"junit" to get JUnit XML for CI.

Scenarios are stored as one JSON file per scenario under ~/.fixtool/scenarios/ — diffable, shareable, and easy to commit alongside your project.

The workflow in the app (capture → review → run → reconcile): scenarios live in the Scenarios rail — a docked pane in the main window you open with the Scenarios tab on the left stripe (⌘2, or with fixtool_panel "scenarios"), so the session grid, detail panel, and rail are all on screen at once. The rail is a test-runner tree: every scenario expands to its steps, each carrying live ✓ / ✗ / ▸ running / – not run status, with Run, edit, duplicate, and delete per scenario.

Its header carries the ways in and out. Run ▾ and the sort (⇅), collapse-all (⊟) and select-all (☐) controls are covered below; the … menu holds the rest:

  • Capture from sessions… — record a live flow into a scenario.
  • Paste wire… — build one from pasted FIX lines instead (a server log fragment, a message out of an email).
  • New blank scenario — start from nothing.
  • ⇆ Diff messages… — the plain diff viewer, with two empty slots to fill.
  • Open scenarios folder — reveals ~/.fixtool/scenarios/, for when the answer is git rather than the app.

Scenario documents (the flow editor, capture review and a run set's record) open as tabs in the one dock across the foot of the window, full width between the stripes and beneath the sessions. Everything that opens at the bottom is a tab in it: the terminal, the Ledger, pinned search results and every open document, one height and one tab strip. Drag its top edge to resize.

There is no minimize chevron. The stripe tab is the minimize: the Documents tab at the foot of the left stripe hides the dock and brings it back, and nothing is torn out of composition while it is away, so the scroll position and the field you were typing in survive a glance elsewhere. Opening or focusing any document, by clicking a step in the rail, following a failure or opening a capture, shows the dock on that document, at that step. The Documents tab is on the stripe only while a document is open, and ⌘9 does what it does: shows the dock on the document you were last in, or hides it.

The point of the dock is what it is not: it is no longer a pane inside the session split, so the editor no longer moves or resizes as a side effect of the view mode you happen to be in. The trade is that one bottom thing shows at a time: the Ledger and a scenario editor are two tabs of one area, not two areas.

  1. Work a flow normally — connect and send/receive messages across one or more sessions (e.g. an RFQ: QuoteRequest out, Quote back; or an order and its ExecutionReport).
  2. Click Capture from sessions…. Nothing saves blind: a capture-review tab lists every business message across all sessions in time order, each row carrying its session color badge and direction, and selecting a candidate highlights its source row in the session grid. Untick noise, or trim the flow with the From / To range dropdowns. The right pane previews what the selected message becomes: outgoing → a parameterized send (fresh ClOrdID/QuoteReqID + TransactTime each run), incoming → assertions with smart-seeded matchers (timestamps→temporal, prices→numeric, IDs→presence, else exact). Echoed ids are auto-correlated and drawn as ●id badges: filled where the id is minted, hollow where it must echo back — even across sessions. If a value came back that isn't a correlation id FixTool knows, the review offers it — see Your venue's own correlation ids. Name it, save.

    Second source — pasted wire. Capture review also takes a paste box (one FIX message per line — a server log fragment, a message from an email). The lines become candidates in the same review, with a per-row direction toggle and a session dropdown. The bytes are read, never guessed: a |-inside-a-value line whose own checksum disproves the reading is refused with the evidence, and a message whose direction cannot be settled blocks the save. Anything built from a paste carries a visible pasted badge — a hand-pasted message has none of a live capture's guarantees.

  3. Run a saved scenario (from the rail). It replays deterministically and the results appear in two places: the rail's step tree turns green/red, and in the session grid the matched message rows are tinted — selecting one shows each asserted tag in the detail panel with expected vs actual, red where it failed. A tag that appears more than once shows one row per occurrence, so the second party entry's PartyRole is checked and reported separately from the first's.

    Running several at once. The rail's rows can be picked: hover a row and click its tick, or use the ☐ button in the rail's toolbar to take everything on screen (Ctrl/⌘A). Once anything is picked every row shows its box, so the next one is one click away — shift-click a row for a range from the last one you picked, and Ctrl/⌘-click a row to add or drop it without opening it. A bar above the list says how many are picked and offers ▶ Run, Save… (as a named set CI can run), ★ (promote them all to favourites) and ✕ (Esc). Because "all" means what is on screen, the filter box doubles as a bulk selector: type QUOTE, take all, clear the filter — the picks stay. They also survive the run they start, so re-running the ones you just fixed is one click.

  4. Reconcile the failure — the message viewer diagnoses; the diff window authors.

    The message viewer tints the failed message red and shows expected against actual, so you see what broke without going anywhere. It does not fix, and that is deliberate: it renders the message that arrived, so it has no row for anything that did not — a tag the venue stopped sending, the most ordinary way a venue regresses, has nothing to click. It gains one action: Reconcile assertions → (and the rail's failed step carries the same Reconcile →, or the reason it cannot).

    That opens the diff window — a dedicated, task-scoped window beside the grid, the way an IDE opens a diff, so the failure's surroundings stay visible. It shows the failed step as a two-sided diff: your expectation on the left (directly editable — each row's matcher is a dropdown, its value a field), the message that arrived on the right (read-only, the venue's own bytes), aligned by the engine's own pairing with repeating-group entry bands. Every kind of failure carries its fix in the centre gutter:

    • The value changed — Accept actual (which re-seeds the row, keeping it numeric or exact as it was, rather than flattening it), Loosen (presence, one-of, a numeric tolerance, a regex), or Drop.
    • The venue sent a tag you don't assert — Assert it, seeded from its type and inserted where it pairs, or ignore it.
    • A tag you assert didn't arrive — Assert absent, or drop the row.
    • An entry moved — the reordered block is bracketed as one unit with a single Accept new order. Never per-row arrows: moving one row of a repeating group would silently swap which occurrence two rows refer to, which is the assert-the-wrong-field failure this model exists to make impossible.
    • This environment sends one fewer entry — the band's ✕ drops the whole entry in one edit, and the entries below move up one occurrence — the deliberate mirror of a move. (A per-row Drop stays whole-tag for the same reason arrows are per-entry: deleting a lone row of a repeated tag would silently re-aim its survivors.)

    When the venue has moved the same way everywhere — a reordered repeating group, a tag it now sends on every message, one it has stopped sending — repairing row by row is the wrong unit of work. Three controls work on the whole step at once:

    • Accept all shape changes — the reorder, the tags the venue added and the ones it dropped, in one click. Never a value mismatch: those are the rows that mean something, and they stay for you to judge. Offered only when there is shape churn to take.
    • Re-seed from reference — rebuild the expectation from the other side wholesale, for when the message has changed past the point of patching.
    • Revert this step — undo this step's whole pass, leaving the window standing. It is not called Cancel on purpose: beside a strip of five repaired steps, “Cancel” reads as “cancel all of that”.

    You can also edit directly — change a matcher, type a value, or drag a row or a whole entry into place — and every edit re-judges live: you watch the step go green as you resolve it, and a fix that does not fix shows red before you save. ⌘Z / ⌘⇧Z walk undo/redo. Nothing is written until you press Save — repairs are staged, not saved, so a pass you think better of costs nothing; Save & re-run writes and replays in one click, and the rail verdict answers on the spot.

    The pass carries you to the next failure. The runner stops at the first failing step, so adapting a scenario to an environment that diverges in several places would otherwise mean returning to the rail to hunt for each “Reconcile step N →” in turn. Instead, when Save & re-run lands red at a different step, that step's diff opens automatically (or this window re-raises, when the repair didn't take), and on it goes until the run is green — a green run ends the pass by doing nothing, and the rail's ✓ is the announcement. Only Save & re-run chains like this; a plain rail Run pops no windows. A failure with no diff to open — a timed-out Expect, a failed Send — pauses the pass with its refusal sentence instead of leaving you guessing.

    The right side is a slot, shown as a chip in the header: swap it between this run, the golden, a second instance of the same message, a message you pick from a grid, or one you paste — and every row re-judges instantly against it. Two rows are deliberately not offered Accept actual: a timestamp (~now ±60s), because accepting it pins the scenario to a moment that will never come again, and an echoed id (${out.D.11}), because accepting it deletes the correlation check. Loosen or drop those instead.

    When the slot holds this run's message, a VARIABLES strip above the diff shows the run's scope — every ${id0} the run minted, its actual value, and the step that minted it. Reference rows are judged with it: ${id0} shows a real ✓/✗ against the run's own bytes instead of an unjudged ◌. Click a chip to highlight every row that references the name or carries its value — the fastest answer to “why did this step bind to the wrong message”. Against a golden or a paste there is no scope that corresponds, so reference rows stay honestly unjudged. The editor shows the same strip for the whole scenario, and warns there about a ${name} that is referenced but never minted — a typo the engine would otherwise send literally.

    The scope also makes correlations authorable from the diff. A row whose actual value is one of the run's variables — the venue echoing an id this run minted — gets a $ Track offer in the gutter: one click swaps the pinned literal for reference ${id0}, judged green on the spot. It appears on green rows too, deliberately: an exact pinning a freshly minted id passes today because it was minted today, and is red on every run after. And with a scope in hand the matcher dropdown offers reference as a picker over the run's variables (each shown with its value), so a correlation can be written by hand without typing — or mistyping — a name.

    The reverse direction — the venue chooses a value your later sends must echo (QuoteReqID, OrderID) — is a capture, not a matcher. On a green row the gutter offers ↧ Capture as ${name} (named from the dictionary): the row's assertion is untouched, but when the step binds, the value it paired with is written into the scope, and a later send or bind predicate says ${name}. The capturing row wears the same filled ● badge a minting send does, in the diff and in the editor's flow list. And in the editor's send grid, any literal field has a ● mint button: 55=EURUSD becomes 55=${sym = "EURUSD"} — identical bytes on the wire, but the value now has a name an expect can reference-check.

    Authoring is the same window. A never-run step opens the identical diff against its golden — same rows, same gutter, same undo — so building an expectation and repairing one are one surface, not two. And the flow editor points you at it: a step's ASSERTS rows are doors — click a row and the diff opens scrolled to that tag, ready to edit.

Each step keeps its own session (a dropdown in the step detail), so one scenario can span multiple sessions — drive an initiator, assert on an acceptor, correlate a quote and a trade conversationally across both. Scenarios are stored one file per scenario under ~/.fixtool/scenarios/.

Your venue's own correlation ids

Capture parameterizes the correlation ids standard FIX defines — ClOrdID, QuoteReqID, MDReqID and a dozen more — so every replay is fresh and each reply is matched against this run's id. Most venues also define their own: a proprietary BatchID, a leg-level request id, a deal handle in the 20000s. FixTool cannot know those, and it must not guess: a FIX dictionary records a field's name and type, never who mints its value. ClOrdID(11) and OrderID(37) are both STRING fields whose names end in ID, and treating one as the other costs either a duplicate rejection at the venue or a scenario asserting that a field equals a freshly-generated uuid.

Left undeclared, a venue id is replayed verbatim: the same value every run — a duplicate at any venue that enforces uniqueness — and the matching expect binds to the first message of that type rather than the reply to your ids. So you tell FixTool once, and the answer lives with the dictionary it describes.

Settings → Protocol → Venue tag roles… (just below the data dictionary path, on the page that holds everything the venue owns rather than this machine) opens on the tags nobody has answered for whose names read like identifiers — the venue's own and the standard ones FixTool has no opinion about. TradeLinkID(820) is standard FIX, is minted by the venue on plenty of flows, and is in none of FixTool's built-in sets: being standard never meant being decided. Show all has the rest, including the tags FixTool does answer for — shown with its answer, so you can see what it already assumes before deciding your venue differs. Rows are in tag-number order throughout, and the search box finds a tag by number or by name whether or not the current view holds it. Give each one a role:

  • we mint it — fresh per run. The send gets a new value every run (20001=${legRefID = uuid:20}), the reply's echo becomes a reference check, and the expect gains a bind constraint so it waits for the response to your id even on a busy session.
  • the venue mints it. Asserted for presence, never its value — a fresh handle on every reply is what a venue is, and pinning one is a scenario that fails its own first replay.
  • a lifetime stamp. Replayed a short way into the future rather than verbatim (stale on arrival) or at now (already expired).

“We” and “the venue” here name the two ends of the relationship, and a declaration is about the tag, not about which chair you happen to be sitting in — so one sidecar serves both. On an acceptor session FixTool applies these answers inverted, because there it is the venue; see Scenarios from the venue's chair.

The answer is saved as <your-dictionary>.roles.json beside the dictionary file — a dozen lines, meant to be committed next to it so a team shares one answer instead of each author re-deciding. It is a sidecar rather than an edit to the venue's XML on purpose: they ship you that file, and their next release would overwrite anything you added to it. Standard FIX needs no entry; the file only ever adds.

Or let a capture find them for you. Reading a dictionary can only guess from names. A captured flow carries proof: you sent this value, and it came back. Capture review offers what it saw — “your 35=R carried 20050=LEGREF-A7F3C201, and 35=S came back with it” — with the evidence printed and every row unticked, because the test is deliberately wider than certainty and the decision is yours. Tick one and it is declared in the same sidecar, and the capture on screen re-seeds immediately.

Which direction the value travelled first decides what you are offered, and the second case is one no dictionary could ever answer:

  • you sent it and it came back → mint it fresh each run;
  • the venue sent it and you quoted it back → read the value from this run's reply into ${name}, and send that. Without this a scenario that cancels by OrderID re-sends the id the venue issued on the day you captured it. This one applies to standard FIX too, with no declaration at all.
Load your venue's dictionary before capturing. Everything above — and the ordinary business of knowing that a field is a timestamp, a price, or an enum — is a question put to the dictionary. A tag it cannot name is classified blind: a timestamp among them replays the captured moment for ever. Capture says so when it happens, naming the tags it could not place.

Scenarios from the venue's chair (acceptor sessions)

The roles above name a party, not a side of your screen. Run a profile as an acceptor and FixTool is the venue: the counterparty dials in, their orders arrive, and your replies are the ones under test. Every consequence of a role inverts with that, and FixTool inverts them for you — the side is read from the profile's connection type, per session, so nothing needs declaring and a both-sides flow can capture an acceptor session and an initiator session in the same act.

Concretely, capturing your half of an order from the venue's chair:

  • Their ClOrdID(11) is now theirs. The expect asserts it for presence — a client mints a new one per order, and pinning the captured literal is a step that passes once and is red every run after — and reads this run's value into ${clOrdID}.
  • Your reply echoes it: the send carries 11=${clOrdID}, so the ExecutionReport answers the order that actually arrived. Minted fresh instead, it would answer no order at all — and nothing asserts a send step, so that mistake never shows as a red run.
  • Your OrderID(37) and ExecID(17) are now yours: parameterized fresh per run, like ClOrdID is on an initiator. Replayed verbatim they are the duplicate handle the parameterization exists to prevent.

Everything else — matcher types, ordering, OPEN vs STRICT, reconcile — is unchanged. So is the initiator behaviour: a session FixTool dials out on is captured exactly as it always was.

Start an acceptor scenario with a Wait. Before any step runs, a scenario checks that its sessions are LOGGED_ON, and it will try to connect one that isn't. An acceptor cannot dial out — only the counterparty can start that logon — so a scenario whose first step is a Send or an Expect fails preflight whenever nobody happens to be connected. Put a Wait for state LOGGED_ON on that session first: preflight then leaves the logon to the scenario, and the run blocks until the counterparty arrives.

One place the side cannot be worked out is the plain diff viewer: it compares two messages that may both be pastes, and a paste has no session to ask. It seeds as the venue only when every open session is an acceptor; where they disagree there is no answer available and it seeds as the client, so check the id rows before filing such an expectation into a scenario.

Same flow, another environment

A flow recorded against dev-buyside/dev-sellside should run against the QA pair without re-authoring every step. The ▾ beside a scenario's Run opens Save as scenario for other sessions…: choose where each step's session should re-aim (targets come from your saved profiles — the other environment is usually not connected yet — and from open sessions), and it saves a copy of the scenario with the sessions swapped. A target that isn't connected is fine: the run's preflight auto-connect brings its profile up first.

A copy, deliberately — not a shared mapping. Environments diverge in their data, so each environment's scenario has to evolve and reconcile on its own: a QA Accept actual lands in the QA copy, and the original's expectations never hear about it. The copies sit side by side in the rail, filterable by session and git-diffable against each other. (For a throwaway run that persists nothing — CI, or an agent — the control surface keeps the old form: POST /scenarios/run takes sessions as {from: to} to re-aim a single run, same preflight auto-connect, no copy saved.)

Running many at once — run sets

A scenario answers “does this flow still work?”. Four questions need more than one run, and they are all the same machinery:

  • Is it flaky? One scenario, twenty times.
  • Does the suite still pass? Twelve scenarios, once each.
  • Does it work for every case? One scenario, once per row of a table — see the examples table.
  • Does it hold under load? One flow, fifty clients at once — see fanning a scenario out.

A run set is an ordered list of run requests, planned up front so the queue is visible before it starts. A single run is a set of one, which is why nothing downstream — the report, the reconcile view, the JUnit output — had to learn a second shape.

The record on disk is the artifact

Entry 2's setup calls Clear messages, so the moment the second scenario starts the first one's messages are gone from the grid — and even without a clear, a session is a ring buffer. Eleven of twelve reports would point at messages that are not there.

So each entry writes its own record to ~/.fixtool/runs/<set>/NN-<scenario>.json — the report verbatim, the bytes, the scenario as it ran, and which message each step judged — as it lands, not at the end, because the run this exists for is the one that gets killed at entry nine. An overnight suite is read in the morning, from an app that may have been closed since.

Which is why a set survives a restart, and why a headless run on a build box leaves exactly the same thing to read as a run you started with a click.

The set report, and reading an entry back

While a set runs, the set report takes the single run's place in the rail: label, progress, failures, elapsed, ⏹ to stop it, and a dismiss when it is done (the records stay on disk — this is a view, not a delete). Under it, one row per entry with its mark, its name, its duration, and for one that never ran, the reason. Finished sets are listed under Recent runs with their verdict and score.

Clicking an entry is what publishes it. Entries run publishing nothing — a set of twenty would re-aim your open reconcile window twenty times while you were reading it — so focusing an entry is the deliberate act that says “this is the run I am looking at now”. It republishes the verdict from the record, so an entry focused an hour later says exactly what one focused a second later said.

An entry opens as a run set document: entries down the left, and for the focused one its verdict, its steps with their latencies, its variables, and its own message grid, re-parsed from the bytes the record kept and tinted by what that entry decided. Its header says which entry you are looking at — book-a-trade · entry 2 of 12 · 5 messages — because a record's grid that looked identical to the live one would be worse than none. Any entry can be re-run as it ran.

Reconcile works from an entry that ran an hour ago, because the record carries the scenario as it ran. Without that, you could edit an assertion, click Reconcile, and be shown the old bytes against the new expectation — with Accept actual writing a repair for a run that never happened.

Isolation, and the run slot

Entries isolate by default: each runs under THIS_RUN binding scope so iteration 2 cannot bind iteration 1's reply and report that the venue answered when it has not — which on a twenty-times repeat would be a false green by construction, in the one feature whose whole purpose is catching flakiness. Isolation is an in-memory copy; the saved scenario is never rewritten.

The run slot is claimed once per set, not once per entry, because two runners would race each other's consumed-message cursors. A single run started during a set is told the slot is taken rather than quietly interleaving with it.

The run boundary. A repeatable scenario that drives a FixTool venue also needs the venue's memory reset, or the second 35=D on a fixed ClOrdID is read as a move rather than a birth. Clear order book is a scenario step for exactly that, aimed at the venue side; capture writes one beside Clear messages for every pane that owns a book. Aimed at anything else the run is refused in preflight, by name — a setup step that quietly does nothing is worse than one that will not run, because the run then goes green on state it never reset.

The examples table — one scenario, once per row

A scenario was already a Scenario Outline and nobody had noticed: every step resolves ${…} against one scope, and that scope already works in both directions — a Send puts ${symbol} on the wire, an Expect's reference matcher asserts ${symbol} came back. What was missing was the table.

The examples table sits across the foot of the editor, under both panes, behind a ▸ Examples header. Collapsed it is a single line summarising itself — 3 rows × 2 columns · 1 parked, or no table — this scenario runs once — so a scenario with no table pays nothing for the feature existing.

+ column and + row grow it. Columns are variable names edited in place; a rename that is blank or collides is refused on the spot with name needed or name taken, and stays local until it is neither — applied per keystroke, a rename passing through a sibling's name would merge the two columns' cells for good. A row can be named (name this row), muted — parked, kept, skipped on every run — or dropped, and renaming or dropping a column takes its cells with it.

The columns are seeded into the scope before setup runs, and a cell is resolved as it is seeded — so a row may say ${uuid} and give each of its runs a fresh id, which is what makes an outline safe to run twice.

Getting the first table written

Nobody hand-writes one. A capture bakes literals into its sends, so the ▦ beside each Send value extracts it to a column: 55=EURUSD becomes ${symbol}, named through the dictionary's own field name, and every existing row gets the literal as its cell. Every row, not just the first — those rows were already sending that literal, and filling only row 1 would leave the others quietly sending nothing.

Each column carries a badge derived from the steps that read it — ↑ out (the row drives the flow), ↓ in (the row asserts the reply), ↑↓ for both. A column no step reads at all is named under the table — No step reads ${spread} — which is not an error, but not something to discover by watching a run pass while proving nothing about the column. And the variables strip no longer reports a table's own columns as never-minted typos: a column is a mint, written by the row before the first step runs.

What a row is called, and what happens when one fails

An entry names itself book-a-trade [EUR/USD partial fill], so the JUnit XML, the build log, the rail and the document cannot come to disagree about it. Run one row by name to debug the row that failed without re-running the other seven.

On an outline, the reconcile gutter's plain Accept actual is a trap, and is treated as one: the expectation belongs to all the rows, so writing this run's literal into it repairs row 3 and silently breaks the other seven. The offer that tracks the examples column is drawn first and wins any tie, and it says why it is the one.

Comparing two messages — the plain diff viewer

Sometimes you just want to see how two messages differ, with no scenario and no assertion in sight: UAT vs PROD replies for the same order, pre- vs post-upgrade ExecutionReports, “why did clearing reject yours and accept mine”, two fills that should be twins. 13. Acceptor Auto-Responses

Everything above assumes the venue is somebody else. When your profile's Connection Type is Acceptor, FixTool is the venue: the counterparty dials in to your port, and their orders arrive as incoming messages. Auto-Responses are the rules that answer them — a venue simulator you author on a form, so a client team can be tested against acks, fills, rejects and timing that you control exactly, including the behaviour a real venue only produces on a bad day.

This is not the Demo FX Server. That is a fixed, built-in venue for trying FixTool out; this is your own acceptor, answering the way you wrote.

The rules engine

Learn these four sentences and the rest of the section is detail.

  1. A rule is a trigger and a reply. The trigger is a MsgType plus zero or more conditions on tags; the reply is one or more messages to send back.
  2. Every condition must hold. Conditions within a rule are ANDed — there is no OR inside a rule, and none is coming: an OR is a second rule.
  3. First match wins. Rules are tried top to bottom and exactly one fires. A rule's position is part of what it means, which is why the card has up/down arrows.
  4. The reply is a sequence. Each step carries its own delay, and that delay is measured from the step before it — not from the trigger.

An incoming message that matches no rule gets no reply. That is not an error and nothing is logged about it: an acceptor with no rule for 35=F simply does not answer cancels.

Where the rules live

Open the Connection panel and select a profile. Below the connection fields is a collapsible Auto-Responses section, with the rule count beside its title, and already expanded if the profile has any. An acceptor answers by its rules; an initiator answers by them too as soon as it has one — a dealer that quotes the RFQs a venue relays to it, by itself — and with none it behaves exactly as it always has. An initiator's rules answer only the counterparty it is connected to. (A profile whose acceptor answers orders on its own should never look, at a glance, like one that stays silent.) The header line summarises the whole list: "3 rule(s), first match wins · 1 off".

Rules are stored on the profile, so Save is what commits them, and they travel with the profile when it is copied or exported.

Saving reaches a session that is already up. A rule you save while the counterparty is logged on applies to that session from its next trigger — no reconnect. Only the rules and the latency travel that way: CompIDs, ports and SSL are the session's identity and still need a reconnect to change.

Reading the list

Rules are numbered, and a card arrives closed. The number is the one every other surface already names a rule by: the shadowing warning below says "rule 1 answers every 35=D", a reply's reason line says "sent by rule 7", and /acceptor/rules addresses rules by index. The card was the one place that knew its own position and did not print it, so a reader told which rule answered them counted cards to find it.

Closed, a card is the rule in a line — what has to be true, and what goes back: 55 oneOf [EUR/USD,GBP/USD,USD/JPY] · 40 exact 2 · 3 steps over 500ms. The trigger is written in the same matcher vocabulary the open card, §12's expectations and /acceptor/test use, so there is one vocabulary rather than a second wearing the first one's clothes. The reply is a count and a span rather than its templates, that span being the claim a sequence makes about time and the one thing about a rule that is invisible in the raw FIX the steps are made of. A rule with no conditions reads any 35=D, because a catch-all is not a rule doing nothing — it is the reason every card above it has to be read in order.

Click the line or the chevron to open the fields, or the fold button in the header to open and close the whole list at once. What is open is a position, so a move or a delete closes every card rather than leaving one open over its neighbour's fields; a rule you add by hand arrives open, since it says nothing until it is filled in. Warnings stay outside the fold: a rule that can never fire has to say so whether or not anybody opened it.

The rule that just answered marks itself — fired 09:14:22.418 on the card, in the wash the grid gives a message it has just sent, reading the clock the reply's own reason line prints. It follows the venue's port and not one client, so a rule tripped by DEMO_CLIENT2 marks the same list as one tripped by DEMO_CLIENT1.

The mark is withheld rather than guessed. The number is a position in the ruleset the session is running, which is the one last saved — so while the list on screen differs from the saved one, and after a rules reload, no card is marked at all. An unsaved insert or reorder moves what lives at that position, and a confident wrong answer to "which rule answered me?" is worse than no answer. Save, and the mark comes back.

Starting from a preset

An empty acceptor answers nothing, and writing the first ExecutionReport by hand means knowing which tags it owes. + preset in the Auto-Responses header offers the common order flow ready made — acknowledge, fill, partial fill, reject, cancel accept and reject, replace, business reject — and, while the list is still empty, a Starter venue button that inserts the four rules making a plausible venue in one click. Hovering an entry shows exactly what will be inserted, and nothing is written until you click.

An inserted preset is an ordinary rule from that moment: edit it, reorder it, switch it off, delete it. Nothing on disk records where it came from.

Where a preset lands is part of it. Because first match wins, a preset that carries conditions goes above the first rule already answering its MsgType — otherwise the size-limit reject added to a venue that already fills orders would sit below the fill, and a two-million-share order would fill rather than reject. One with no conditions is appended, since it answers everything of its type. The card says where it went until your next edit, and the up/down arrows are still yours.

Editing a step in the message editor

A reply step is a raw FIX string, and reading one is the same problem writing one was. The ↗ button beside a step's number opens it in the message editor — the same panel you compose anything else in, so its tags carry dictionary names and its values carry the enum menus. Apply writes the step back; Cancel leaves the rule alone. Send is not offered while a step is loaded: a template has no session to go to.

Applying is not saving. The step lands in the form exactly as typing into its raw field would, so Save is still what commits it. And a half-written message you were composing is not the price of looking at a rule — it comes back when you apply or cancel.

Two edits are refused rather than written, and named by tag: a value containing |, which is the separator between fields and would come back as two of them, and a tag left with no value, which goes on the wire as 31= — a malformed message your counterparty gets blamed for.

Two habits worth copying from the presets when you write your own:

  • ${req.uuid} for OrderID and ${uuid} for ExecID. The first is drawn once for the whole reply, so every step of a sequence carries the same OrderID; the second resolves as each step is sent. An ack and its fill carrying different OrderIDs are two unrelated orders to a client tracking tag 37.
  • Never read a tag the trigger does not guarantee. ${req.44} against a market order substitutes nothing and puts 31= on the wire — a malformed message your client gets blamed for. That is why the fill presets ask for 40 = 2 first.
⚠ never fires on a card means an earlier rule already answers every message of that type, so this one is unreachable. Move it earlier, or give it a condition. The warning is only shown when it is certain — an earlier enabled rule for the same MsgType with no conditions. Two rules that both have conditions are left alone, because whether they overlap cannot be settled by looking at them.

The trigger

Every rule starts When 35= and a MsgType — D for NewOrderSingle, F for OrderCancelRequest, R for QuoteRequest. That alone is a complete trigger: it fires on every message of that type.

+ condition adds a constraint on a tag, and the constraint is edited by the same matcher chip the scenario workbench uses — deliberately the same one, so there is a single vocabulary rather than a second one wearing the first one's clothes. Everything in §12's matcher table works here, including the dimming of types the field cannot carry, with two differences:

  • reference is not offered. It resolves a ${…} expression against a scenario run's scope, and a trigger has no run. A rule that arrives carrying one (by hand-edited JSON) is refused by name on the rule card — because the alternative is a matcher that quietly never matches, and a rule that never fires looks exactly like a rule whose trigger has not come up yet.
  • absent and notEqual are worth keeping straight here, since a trigger is where the difference bites. absent fires when the tag is not there; notEqual fires when it is there and holds something else. A message without the tag satisfies absent and fails notEqual.
When 35=D
  and tag 55  exact    EUR/USD
  and tag 38  range   > 1000000
  and tag 40  notEqual 1

… is "a EUR/USD order over a million that is not a Market order" — the shape of a rule that simulates a venue rejecting large limit orders. To also cover GBP/USD, write a second rule; there is no OR.

The reply

+ step adds a message to the reply. Each step is a delay and a raw FIX template:

1. +   0ms → 0ms    35=8|150=0|39=0|37=${uuid}|17=${uuid}|11=${req.11}|38=${req.38}|14=0
2. + 400ms → 400ms   35=8|150=F|39=1|37=${uuid}|17=${uuid}|11=${req.11}|38=${req.38}|14=${req.38 / 2}
3. + 400ms → 800ms   35=8|150=F|39=2|37=${uuid}|17=${uuid}|11=${req.11}|38=${req.38}|14=${req.38}

An ack, a half fill 400ms later, and the rest 400ms after that. You write the gap; FixTool does the accumulation — the number after the arrow is the running total from the trigger, shown on every row precisely because "delay from the previous step" is the one thing about a sequence that is easy to read the other way. If the two numbers ever disagree with what you meant, the row tells you before the counterparty does.

A template is raw FIX — application fields only, pipe- or SOH-delimited. Do not write the header or the checksum; QuickFIX stamps the session envelope itself.

That matters because it used to cost about 60 ms: the shorthand became a Kotlin expression and the script engine compiled it, once per reply, on the one dispatch thread every acceptor reply shares. A venue with a single shorthand in its quote answered fourteen requests a second because of it. Anything that is not a pure generator (arithmetic, an assignment, a book reference) still goes to the engine.

The per-step timing of ${uuid} and ${now} is the point of the split: a fill sent a second after the ack carries its own ExecID and its own TransactTime. A sequence whose steps all shared one timestamp would report zero latency in exactly the data a latency test reads.

The computed form is what makes one rule serve every order size — 14=${req.38 / 2} fills half of whatever quantity arrived, instead of the one quantity its author happened to hardcode. The value is substituted raw, which is what makes the arithmetic work and what keeps this to numbers; read a string field with the plain ${req.11} form, which needs none of it. Expressions are scoped to the message that fired this rule, so two orders in flight cannot read each other's quantities.

Ordering, and switching a rule off

Because the first match wins, put the specific rule above the general one. A catch-all When 35=D with no conditions placed first means no rule below it will ever fire on a D. The up/down arrows on each card are how you fix that.

The checkbox at the left of a rule switches it off without deleting it. A disabled rule is dimmed but still fully readable and editable, and the message falls through to the rule after it — which is exactly what you are asking to see when you turn one off to find out what happens without it. Narrowing down a venue's behaviour means asking that a dozen times, and the answer should never cost you the rule.

When the reply actually goes out

Replies always leave after the incoming callback has returned, on a dispatch thread of their own — including a zero-delay one. This is deliberate and it matters: a reply sent inline can reach the counterparty before their own send() has returned to them, which would let a client with wrong ordering assumptions pass against FixTool and fail against a real venue. There is one answer to "when does the acceptor reply", not a fast path and a slow path that can drift apart.

The steps of one sequence keep their order. Sequences triggered by different incoming messages interleave — which is what a real venue does with two orders in flight. Anything still queued for a session is dropped when that session logs out.

The ■ Stop button in the Auto-Responses header (shown only while a session is live) drops every reply still queued on that session. A sequence is a claim about time — "and then, four seconds later, the fill" — so the moment you see it is the wrong claim, you need it to stop now, not after it has finished being wrong.

One venue, many clients

An acceptor normally names its counterparty: one TargetCompID, one client, and a logon from anyone else is refused. That is a test result, not a limitation — so it stays the default.

Set TargetCompID to * and the acceptor becomes a venue: it binds the port once, accepts a logon from any counterparty addressed to your SenderCompID, and gives each client its own session and its own pane. Your own SenderCompID is never wildcarded — a venue answers to its own name.

This is the topology a venue actually has. The alternative was a port per client, which forces the client under test to be reconfigured away from its real settings — so you end up testing a configuration nobody ships.

  • Refused logons are reported — a notification, a line on the venue pane, and a counter on GET /sessions. Nothing else records them, and without them a wrong CompID, a wrong port and a firewall look identical from both ends.
  • A client's pane outlives its session, marked disconnected, and a reconnect from the same CompID reuses it — because what explains a drop is the traffic just before it. One client logging out never stops the port.
  • The acceptor's own tab is a venue overview — port, client list, refused logons, rule status, and a per-client roll-up of the order book. It shows no message grid, because every message belongs to one of the clients.

Rules stay profile-wide, so one set of rules serves every client.

What the venue remembers — the order book

A rules engine with no memory answers the same message the same way forever. That is wrong in a way clients notice: a cancel for an order nobody ever placed comes back “canceled”, and a duplicate ClOrdID is accepted as a new order.

So the venue keeps an order book: one book per counterparty, holding what it is currently holding for that client. Two sentences govern it, and they are worth learning because every other behaviour follows from them:

  1. The book records; the rules decide. Nothing about the book changes what your venue answers unless a rule you can read asks it to.
  2. An order is its own trail, folded. Every number on a row — CumQty, LeavesQty, the state — is computed on read from the list of messages that touched that order, never accumulated as they arrive.

If you would rather see it than read it, Watching it work at the end of this chapter drives all of it against the bundled example, one message at a time.

The book is fed from the wire, not from the rules engine, so a reply you typed by hand moves it exactly as a rule's reply does. And where a report you sent carries 14 or 151, those are the values booked — the fold never prefers its own running total to what the venue told the client, which is what makes a bust (150=H, restating quantities downward) work.

Identity is stated, never inherited. A replacement's OrderID comes from tag 37 on a message, or from that order's own earlier events — never from the order it supersedes. Venues genuinely disagree here: many keep one id across a chain, several crypto and futures venues mint a new one, so 37=${order.orderId} and 37=${uuid} must produce different books. Quantities do carry across a replace: how much of a chain has traded is a fact about the chain, while which id it wears is a fact the venue states.

The panel

The right stripe's Order book tab (⌘5) opens a side panel showing what this venue is holding, per counterparty. It is headed Orders, against the active session — for a venue, the client pane you are already reading, since a book belongs to a counterparty and the pane is what names it. Its title bar names the session and counts what it holds (FX Demo Venue ← DEMO_CLIENT1 · 1 order · 0 working), and its position and visibility persist across launches.

One row per order: ClOrdID, OrderID, Symbol, Side, OrderQty, CumQty, LeavesQty, AvgPx and Status — an order that was replaced reads replaced → <the id that superseded it>.

A row is a claim; expanding it shows the evidence — the trail, captioned “every number above is this, folded”. Each line is one message that touched the order, labelled by what it did (order received, ack, fill 500000) and carrying what the order looked like after it (cum 500000 · leaves 500000) — so CumQty 1000000 is not something you are asked to believe, it is two fills you can count. Clicking a trail line selects that message in the grid, because the next question a trail raises is always “what exactly did we send them?”.

The footer says the three ways the book may be wrong, which is the other half of the same stance:

  • Unattributed reports — the count opens to the list and the reason, because “2 unattributed” says something is broken and nothing about what.
  • Evicted orders — the book is capped (see Settings → Sessions → Order book), finished orders evicted before working ones. An evicted order answers a cancel “unknown”, which is a venue behaviour nobody configured, so it is counted rather than silent.
  • Cleared, or never filled — an empty book otherwise reads identically as “nothing has happened here” and “somebody pressed clear thirty seconds ago”, which send a tester in opposite directions. So the empty state never just says “no orders”: it is either “No orders yet — this venue has not been sent one” or “Cleared 16:37:59.412 — the control surface”.

An initiator session says so rather than showing an empty book: a client's own view of the orders it sent is a different feature, deliberately not this one.

Rules that read the book

A trigger can carry one whenOrder constraint, ANDed with its tag conditions, taking one of four words:

35=F and the order is unknown → 35=9, 102=1 — unknown order
35=F and the order is working → pending cancel, then canceled
35=F and the order is done → 35=9, 102=0 — too late to cancel

The constraint reads the state held before this message. The book is fed from the wire and the wire is read first, so by the time any rule is asked, the message's own arrival has already been booked — a new 35=D would read pending, and a rule conditioned unknown on 35=D could never fire. Read before, unknown means “a new order” and anything else means “we already hold this id”, which is the whole of what a duplicate is. The reading is taken once per incoming message, so every rule in the list is judged against the same answer.

There is deliberately no word for “pending or working”. Rejecting a duplicate ClOrdID is two rules, and inventing a fifth word would cost the other four the property that earns them.

Every reply now carries the reason that chose it, shown in the detail panel beside the bytes:

sent by rule 3 — 35=F matched, and the book said ORD-9 was unknown at 09:14:22.418
sent by hand — “Fill the remainder” against ORD-5000, working, 2500 leaves

The reason is written when the decision is made, not re-derived afterwards, and that is a requirement rather than an optimisation: a cancel rejected at :22 because the order was unknown would re-derive as accepted at :25, so a tool that reconstructs after the fact states the wrong reason confidently.

Reading the book in a reply

A reply template can read what the venue is holding, standing alone or inside arithmetic, exactly as ${req.…} reads the triggering message:

ReferenceWhat it resolves to
${order.orderId}The OrderID this venue gave the client.
${order.clOrdId}The client's own id for the order.
${order.symbol}, ${order.side}As the order was placed.
${order.orderQty}The quantity ordered.
${order.cumQty}, ${order.leavesQty}Filled so far, and left to fill.
${order.avgPx}, ${order.price}Average fill price, and the order's limit price.
${order.state}pending, working or done.

Names, not tag numbers, because half of them are facts the venue computed rather than fields of any message — ${order.14} would send a reader looking at the wire for something that was never on it.

They resolve per step, as that step is sent. That is the whole difference from ${req.…}, which is a fact about the triggering message and cannot change. The book can, and it changes inside a single reply, because each step reaches the wire and is recorded before the next is built:

14=${order.cumQty + order.leavesQty / 2} → 500, then 750, then 1000

Read once at trigger time instead, all three report 500, and a client tracking CumQty watches each fill undo the last.

A reference that cannot resolve is never sent as an empty field, refused at three levels: the rule refuses to validate, Reply With… greys out the shape with the reason, and a step whose references cannot resolve is not sent and says why. The last is a backstop for what defeats the other two — a book cleared mid-sequence, an eviction — not the mechanism.

Resetting between runs. A scenario run twice meets its own history: the second 35=D on a fixed ClOrdID routes as a move rather than a birth, and a venue that rejects duplicate ClOrdIDs rejects the very order it acknowledged a second earlier. The Clear order book scenario step is the run boundary that fixes it — see Automated Verification & Scenarios. Capture writes one for you when it authors a both-sides flow.

Watching it work — one order, end to end

Everything above in one sitting, against the bundled FX Venue example, so you can replay it rather than read it. Open the example, connect Demo Client 1, select the FX Demo Venue ← DEMO_CLIENT1 pane — the book belongs to the counterparty, so that pane and not the venue's own tab — and switch the Order book toggle on.

1. Place an order. Send from the client:

35=D|11=DEMO-A1|55=EUR/USD|54=1|38=1000000|40=2|44=1.08990|60=…|

One rule matches and answers in three steps: an ack, then two fills 250ms apart. Expand DEMO-A1 in the panel and its trail reads:

What touched the orderThe order after it

150=0 sent — ackworking · cum 0 · leaves 1000000

None of those numbers was accumulated as it arrived: the row is the four lines beneath it, folded. Click a trail line to select that message in the grid and read the bytes that produced it.

2. Cancel it. The order is finished, so of the venue's four cancel rules the done one matches:

35=F|11=CXL-2|41=DEMO-A1|… →
35=9|11=CXL-2|37=7d0b9cb2…|39=2|41=DEMO-A1|58=Too late to cancel|102=0|

Tags 37 and 39 came out of the book, through ${order.orderId} and ${order.ordStatus}. A venue with no memory has nothing to put in them, which is exactly why a stateless rule has to answer every cancel the same way.

3. Cancel an order nobody placed. The same message shape against a different book state picks a different rule:

35=F|11=CXL-1|41=GHOST-1|… →
35=9|11=CXL-1|37=NONE|39=8|41=GHOST-1|58=Unknown order|102=1|

Now watch the panel footer: it reads 1 unattributed. That reject names an order the book has never held, so the book files it — “names 11=CXL-1, which this book has never seen” — instead of dropping it. Here that is correct, because there really is no such order; the value of the counter is that it reads the same way when it is not.

4. Replace one, twice. Send an order, wait for its ack, then a 35=G naming it in 41. Then do it again on a fresh order, sending the 35=G immediately so it arrives before the ack. Two replace rules, read by the book, answer differently:

The order wasThe rule sendsWhat the client sees
working37=${order.orderId}the replacement keeps the same OrderID
pending37=${req.uuid}the replacement gets a new one

Both chains link either way — the superseded row reads replaced → <the new id> and the new row carries the quantities forward. Only the identity differs, and only because a rule you can read said so.

Why a canceled order can still fill. A reply's later steps are scheduled when its trigger matches, so a cancel or a replace arriving afterwards does not retract fills already queued: cancel DEMO-B1 a moment after placing it and its trail reads canceled and then two fills. That is the example's rules rather than the book — and the book showing it is the point. It records what the venue really sent, including where the venue contradicted itself, because the client's view is the view under test.

What the venue remembers: the quote book

Beside the order book, and shaped like it with one thing reversed. An order is born by a message the client sends and moved by the venue's replies. A quote is the other way round: the venue sends the 35=S that creates it, and the client's 35=AJ answers it. So a quote book is not the order book with different tags in it, and this is a second small book rather than a setting on the first.

It is fed from the wire, exactly as the order book is, and it keeps four facts about each quote it has sent: the id, the instrument, both prices and their sizes, and the ValidUntilTime. What it does not keep is whether the quote has expired, because a quote does not become stale at a moment anybody sends a message. That is a clock comparison, made when a rule asks.

One indirection is forced by FIX 4.4 itself. A client's QuoteResponse carries its own QuoteRespID (693) as well as the QuoteID it is answering, and the venue's reply (an ExecutionReport for a booked hit, a QuoteStatusReport for a refusal) echoes 693 and not 117, because a 4.4 ExecutionReport has no QuoteID field at all. So the book remembers each response by its own id and resolves the venue's answer back to the quote through that. The QuoteResponse itself moves nothing: whether a quote is spent is the venue's decision, and that lives in the reply.

An ExecutionReport that books a quote hit is not offered to the order book. It carries a ClOrdID the venue never saw on an order, so the order book could only file it as an unattributed report, which is noise at the bottom of every RFQ run.

Clear order book, the button and the scenario step alike, empties both. They are one venue's memory, and a venue that had forgotten the orders but still refused a quote as spent would be the most confusing possible half-answer.

Rules that read the quote

A trigger can carry one whenQuote constraint beside its whenOrder, ANDed the same way, taking one of four words:

WordWhat it means
unknownThis venue never sent that QuoteID, or the message names none.
openSent, unanswered, and still inside its ValidUntilTime.
expiredSent and unanswered, but its validity has passed.
doneAlready hit or already passed on.

Which is the difference between a venue and a message echo. Nothing on the incoming message distinguishes these four cases, so without the constraint a venue either honours every hit or none:

35=AJ and the quote is open → 35=8, a trade at the price the quote carried
35=AJ and the quote is expired → 35=AI, 297=7, too late
35=AJ and the quote is done → 35=AI, 297=5, already answered
35=AJ and the quote is unknown → 35=AI, 297=9, we did not send that quote

The constraint reads what the venue held before this message, exactly as whenOrder does. A hit has to be judged against the quote as it stood when the hit arrived, not against the quote its own reply is about to close.

There is one more thing a quote rule can do that no whenOrder rule needs: compare a tag against the quote's own value. Pick quoteField as a condition's matcher and choose which field: 44 equal to the quote's offer is how “the client hit the price we quoted” is written. No literal can express it, because every quote carries a different price, and no tag on the incoming message can either: the price the client sends is precisely the claim under test. A quoteField with no quote to resolve against is false, which is what lets the unknown-quote rule sit below the hit rule and answer instead.

It is offered only on an acceptor trigger, and refused in a scenario by name, because a scenario replays against a counterparty and has no venue book to ask. That is the mirror image of reference, which names a scenario variable and is refused in a trigger for the same reason.

Reading the quote in a reply

A reply template reads the quote the same way it reads the order:

ReferenceWhat it resolves to
${quote.quoteId}The QuoteID this venue minted.
${quote.quoteReqId}The QuoteReqID the client asked with.
${quote.symbol}The instrument, as the venue quoted it.
${quote.bid}, ${quote.offer}The two prices this quote carried.
${quote.bidSize}, ${quote.offerSize}The sizes quoted on each side.
${quote.validUntil}The ValidUntilTime, as epoch milliseconds.
${quote.state}open or done.

31=${quote.offer} is how a hit is booked at the price the venue actually quoted rather than the price the client claimed. As with the order book, a reference that cannot resolve is never sent as an empty field: the field here is a price, so an empty substitution would put 31= in a trade confirmation and the client would be blamed for it. The structural answer is that a rule whose reply reads ${quote.…} will not validate without a whenQuote of open, expired or done. Unlike an order, no trigger can mint the quote it reads, because a rule never answers the venue's own send, so the constraint is the only way to be sure there is one.

Trying it without a counterparty. POST /acceptor/test takes quoteState (unknown, open, expired or done) and a quote object of the venue's own names, so “what would this venue do with a hit that arrived too late” is answerable without waiting thirty seconds for one. It reports assumedQuoteState back, and each conditioned rule reports whenQuote with what it asked for, what it read and the verdict.

Relaying between counterparties

Every rule above answers the counterparty that sent its trigger. A venue that sits between two kinds of client — a platform carrying a buy side's RFQ out to its dealers and their quotes back — also has to send to somebody else, in that somebody's own ids. Three things make it possible: the venue says who its counterparties are, a trigger can ask about the sender and the RFQ, and every step says who it goes to. The Fixed Income RFQ Platform is built out of nothing else, so its cards are the worked example of everything here.

Counterparties

On an acceptor open to any client (TargetCompID=*), the Connection panel has a Counterparties section: a CompID and the part it plays. A requester raises a request, as a buy side does; a responder answers one, as a dealer does. A CompID ending in * is a family, so FIDLRLG* covers every lane of a load client. A logon from a CompID nobody listed is still accepted, and is unlisted: the venue's pane names it, and a rule can refuse it. Beneath the list, An RFQ expires after sets how many seconds an RFQ stays open when its request names no ExpireTime(126); blank never expires one.

The RFQ book

A relaying venue keeps an RFQ book beside its order and quote books, and draws it on its own pane rather than a client's, because an RFQ spans counterparties: one row per RFQ, a leg under it per responder, and each id shown the way each side knows it (D1-Q-88 ↔ V-Q-1). It is fed from the wire like the other two. A rule becomes a trade the moment one of its steps sends the quoter an ExecutionReport, so a second lift already on its way reads the RFQ as done and is refused.

When the RFQ expires

An RFQ nobody lifts, passes or refuses still ends. A rule card on a relaying venue offers or when the RFQ expires beside its MsgType, and a rule chosen that way fires when an RFQ's time runs out, with nothing having sent the venue anything: at its request's ExpireTime(126), or when the venue's An RFQ expires after has passed. The clock starts when the RFQ is first relayed to a dealer, so a request refused before anyone was asked is never later told it expired. It stops if the RFQ trades, passes or is refused first, and it does not stop when the requester logs out: its dealers are still owed the end.

Nothing sent it, so there is no sender: every step needs a to, and the card does not offer and the sender is or and the RFQ is, which could only say what is always true. ${req.55} reads the request that opened the RFQ. and quotes standing is the question that matters, and on an RFQ that has expired quotes and quoted mean the last quote each dealer showed, lapsed or not, because every quote ends with the RFQ. The reason on each message says so: sent by rule 24 — the RFQ expired at 09:15:21.002 → quoted FIDLR1, on FIBUY1's RFQ.

The other side, by rule

A dealer that quotes relayed RFQs by itself is an initiator with rules (see Where the rules live). It answers only the one counterparty it is connected to, so it has no counterparties, and a rule on it that addresses anyone, asks a role or an RFQ state, or asks who is online is refused on its card.

Trying a relay without the parties. POST /acceptor/test takes from, the CompID the trigger comes from, and dry-runs the venue as that sender: which rule answers, and for each step who it would reach, not delivered included.

Replying by hand — Reply With…

Rules answer what you anticipated. Reply With… answers what you did not. Select a message on a venue's client session and the button appears first in the Message Details header (it is drawn only where a reply makes sense — never on an initiator's session). It offers the venue's own shapes — acknowledge, fill, partially fill, reject, cancel — already filled in from that message and from the book, so a one-off reply does not mean composing an ExecutionReport from memory.

Picking a shape sends nothing. It loads the resolved reply into the message editor, where you can read it, change it, and then press Send — the improvised reply gets the same review as any other message. It also makes the session that received the message active first, because on a venue with several clients logged on, the one whose order this is is the only right answer; you may still change it in the editor, but it will never silently default to whichever tab you last looked at.

A shape that cannot work is shown greyed with its reason rather than hidden: filling a market order at a limit price it never carried, or quoting an OrderID for an order the venue does not hold. Once sent, a hand-typed reply moves the order book exactly as a rule's does, and carries its own recorded reason — the client cannot tell which of them sent it, and neither should the record.

14. Tracing an Exchange Across Sessions

One business exchange rarely lives in one session. An RFQ arrives on the client leg, a quote request goes out to the liquidity provider on another, the provider's quote comes back, and the client is filled — four hops, four panes, four different ids for what everyone involved would call one thing.

The usual answer was a regex typed into the search box, and it fails in both directions: it misses a hop the moment the venue mints a new id, and ORD-9 matches inside ORD-91.

Following one exchange

Follow is on a conversation header, on a message row's right-click menu, and on any correlation-id field in the detail panel. One click narrows every session pane to that exchange at once, and a chip in the toolbar's filter names what is being followed:

Following RFQ-A1 · 4 sessions · 14 messages

The set grows live as the venue mints new ids — a quote id that appears two minutes in joins the trace without you doing anything. Esc, or the chip's ×, stops following, and every pane's own filter comes back exactly as you left it.

Hops are joined by the ids messages actually carry: a reply echoing the request's id, a venue's own id quoted back on the next message. Which is why a trace is only as good as what your venue declares — see Your venue's own correlation ids.

The Trace panel — the Ledger

The Trace tab at the foot of the left stripe (⌘8) opens the Ledger in the bottom dock, which is every exchange across every session: the grouped grid run over every session at once. Its header counts the whole picture — 8 traces across 2 sessions · 68 ungrouped — and Expand all / Collapse all open every trace or shut them.

Columns are Session, Time, Dir, SeqNum, MsgType, Summary, Elapsed (per hop, on one clock) and then the correlation ids themselves — ClOrdID, QuoteReqID and the rest — one column each. A group header names the exchange and what it is about (VRF-ORD-1 · EUR/USD 1000000), summarises its composition (NewOrderSingle ×1 · ExecutionReport ×3), and counts sessions as well as messages — so which RFQs touched more than one session is read straight off the headers.

Every column resizes. Drag the right edge of its header; double-click the header to fit the column to its widest value, and double-click again to put back its usual width. Every row, the group headers included, ends where the header does. Widths hold while you switch dock tabs and reset when FixTool restarts.

Nothing is hidden. Ungrouped messages come last and are counted rather than dropped, and a trace whose first message has already left a session's buffer says so rather than presenting a partial exchange as a whole one.

A trace that stubbornly stays in one session says so on its own header, with the remedy in it:

one session only · if the far side echoes this under its own tag, name that tag in the dictionary's .roles.json sidecar and the trace joins

That needs no code — see Your venue's own correlation ids. A venue that answers under a tag FixTool has no opinion about leaves no edge to follow, and joining the legs anyway would be the tool inventing one.

Lanes

The Trace panel's second rendering: one column per session, time running down, each message a chip in its lane pointing out of FixTool or into it. Initiator sessions sit left of a dashed rule and acceptors right of it — read from the profile, never guessed from a CompID.

The venue under test is the space between the lanes. That is the whole idea: when FixTool holds both ends of a hop, the same bytes leaving one lane and arriving in another are drawn as one arrow carrying the hop time, so the latency you are reading is the thing in the middle rather than anything FixTool did. Six messages across two sessions therefore draw three rows, not six.

The first column is elapsed: an absolute time on the first row, then +48 ms, +318 ms against the hop before it. The panel header carries the whole trip — Following VT-89c4053a · 2 sessions · 6 messages · 367 ms — and Ledger / Lanes in its top right switch the rendering.

Every lane resizes the same way as a Ledger column: drag the right edge of its header, or double-click the header to fit its widest message. A session's lane keeps its width from one followed exchange to the next.

Driving it from an agent or CI. GET /traces lists them; GET /trace?id= returns the merged exchange with a session and an elapsed time per message (an id is matched whole — a substring never matches). POST /panel {"panel":"trace","follow":…,"render":"lanes"} opens and switches it. MCP tools: fixtool_traces, fixtool_trace.
