What the regex does. The dashed rows are LP-1's order leg. It is on screen only because this mockup draws it; in the app those rows are filtered out, and nothing says so. The QA concludes LP-1 never received the order. The red rows are a second, unrelated order that matched because ORD-9 is a substring of ORD-91.

Each of these is a separate way to be wrong, and they compound:

must know every id

The regex only finds what the QA already typed. A venue that mints per hop (V-2291, V-ORD-8813) adds ids as the flow runs, so the regex is stale by the time the order leg arrives.

silent omission

A missed id does not look like a mistake. It looks like the venue dropped a message.

substring match

Filtering runs over the display string, not field values. ORD-9 matches ORD-91, ORD-9X, and any OrderID that happens to contain it.

clobbered filters

The global filter box writes the same regex into every pane, overwriting whatever each pane had. setGlobalFilterRegex

tabs mode

In tabs view the filter button shows a panel that never applies. Only split view filters. App.kt:389 passes the unfiltered list.

order in the head

Even when every pane is right, which pane's row came first is read off timestamps across four grids.

The tool already knows the answer to all of this. The grouped grid joins messages by shared correlation values, and that relation does not care which session a message came from. Fed all four logs at once, the same union-find joins RFQ-A1 to Q-LP1-77 on the client, Q-LP1-77 to V-2291 on LP-1, and V-2291 to every other LP, with no rule written anywhere.

The gesture: Follow

Every conversation header, message row and correlation-id field grows one action: Follow across sessions. It replaces the regex with the set of ids the tool computed, and it keeps computing as messages arrive.

Try it below. Follow the RFQ-A1 group in the client pane. Every pane narrows to that exchange, a chip names what is being followed, and the Trace panel opens underneath.

Follow, then read. The chip is the whole filter: no text, nothing to keep in sync, and it grows as the venue mints. Stop following and every pane's own filter comes back untouched. The Trace panel sits where pinned search results already live.

Ledger: every trace, every session, one grid

The Ledger is the grouped grid the app already draws, run over all sessions at once. Two things change. A Session column says where each row happened, and the group header counts sessions as well as messages, so which RFQs touched more than one session is read off the headers.

Elapsed is the time since the previous message in the trace, whichever session it was on. Every timestamp in the ledger comes from the same clock, because FixTool held every one of these sessions. So +31 between the client's request going out and LP-1's copy arriving is a real measurement of the venue, not a guess reconciled across two machines' logs. The tool states the gap. It does not say what caused it.

Nothing is hidden. Heartbeats and anything without a correlation id land in Ungrouped, last and counted, as they do today. A trace whose first message has already left the session buffer says so in its header rather than pretending to have started later.

Lanes: the same rows, as the picture QAs draw

Switch the panel to Lanes and each session becomes a column, time runs down, and each message sits in its lane pointing out of FixTool or into it. Initiator sessions sit left of the dashed rule, acceptors right of it. That split is read from the profiles, not inferred.

The venue under test is the space between the lanes. Nothing is drawn there, because FixTool holds no session with itself. What it does hold is both ends of every hop, which is why the request leaving the client lane and arriving in three acceptor lanes a few milliseconds later is the one view a venue's own logs cannot give.

In a both-sides test, where FixTool plays the client and the venue in one instance, the same bytes appear as an OUT in one lane and an IN in another. Lanes draws those as one arrow when the wire bytes are identical, which is a fact about the bytes, not a claim about the venue.

Where the chain breaks

A trace only crosses a session boundary where some value crosses it. A venue that mints a fresh id per hop and echoes nothing leaves no edge, and no tool can join those honestly. Two remedies, neither of which guesses:

  • Declare the tag. Most venues carry the originating id somewhere on the far side, often in a proprietary tag. Naming that tag in the dictionary's roles sidecar makes it a correlation id everywhere, and the trace joins with no further work. The header hint above is the tool saying so at the moment it matters.
  • Link by hand. A QA who knows two traces are one exchange says so, and the ledger draws them joined with a dotted rule labelled as linked by them. Never joined by time proximity, which would be the tool inventing an edge.

Three treatments, one recommendation

A · Follow only

The chip, no new panel

Every pane narrows to the followed trace; reading stays in the panes QAs already know.

Removes every failure in the list above. Order across panes still lives in the reader's head, and in tabs view they still flip tabs.

A + B · Follow and Ledger

The chip opens the Trace panel

One grid, all sessions, all traces, in time order with a Session column and elapsed gaps. Reuses the grouped grid and its columns unchanged.

Answers every question the regex was trying to ask, for every trace at once, with the same columns and folding the grid has today.

C · Lanes

The panel's second rendering

Swimlanes for one followed trace: the whiteboard diagram, drawn from the ledger's rows.

Most readable for one exchange; not a view of many at once. Ships after A + B is live-verified, as a toggle inside the same panel.

Follow with the Ledger first, because it changes what a QA can be wrong about. Lanes second, because it changes how fast they read. Manual linking and the roles-sidecar hint ride with the Ledger, since the header is where the break shows.
