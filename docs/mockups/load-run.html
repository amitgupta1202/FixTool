FixTool · design note · issues #42 and #43

Load runs, and the store under them

A load run issues a message thousands of times across a profile's sessions without waiting for a reply, then accounts for every reply that lands anywhere. The store and log choice is the small change that has to land first, so the run measures the venue and not FixTool's own disk. This note answers whether the two make sense, how they relate, and in what order to build them, then draws the screens and the mechanism.

status: proposal 2026-09-05 builds on #41 fan-out lanes, #39 headless run, the 2026-09-03 socket stamps plan: docs/load-run-impl-plan.md sibling: docs/mockups/multi-run-scenarios.html

Two issues, one design, four landings on main

Do they make sense?

Yes, both. #43 makes FixTool the load harness the venue proof is currently written by hand around. #42 is a two-field change that a soak run needs on its own, and that #43's issue rate depends on.

Separate, or related?

Related by dependency, separate in code. #42 sits under #43: the load dialog and the fixtool load command expose the store and log choice per run. But #42 touches the connection manager and the profile, #43 touches the headless runner, a new service and the rail. They do not share a file.

One at a time, or together?

Design together, land in order. #42 first, as one small landing on main. Then #43 in three landings: the engine with its command, the app surface, the control surface. Main stays usable after every commit of every step.

One correction to the premise of #42 is worth stating before anything else, because it changes what the change is for. Since the socket stamps landed on 2026-09-03, a round trip is measured between the bytes leaving the kernel and the bytes arriving at the codec. QuickFIX/J's store and log writes happen before the outgoing stamp and after the incoming one, so on the client side they are not inside the stamped round trip at all. What they do is sit on the issue path, where they cap how fast a lane can carry messages, and on the engine's single inbound thread, where they decide whether it keeps up with a reply stream. When FixTool is the venue under test, its own acceptor's writes are inside the number. Section 3 draws this.

#42  The store and the log

Where the writes sit

Decisions

  1. Two fields on the profile, enums, additive on disk: messageStore: FILE | MEMORY and messageLog: FILE | NONE. Default FILE for both, so a saved profile reads exactly as it did. A profile is a way of using a counterparty. A LOADGEN profile with fifty sessions is a load profile all day, and a soak profile is one too. The setting belongs where the session count already lives.
  2. A per-run override in the load dialog and on the command line (--store memory --log none), applied to the sessions that run opens and never written back. The issue asks for "per profile or per run". Both, because an interactive profile borrowed for one load run should go back untouched.
  3. Memory store requires Reset on Logon. The dialog and the CLI refuse with a named reason rather than flipping the profile's flag behind the user's back. A memory store starts at 1 on every logon while the venue expects the number it last saw. That is the classic first-run-after-restart failure the issue names. Refusing is the codebase's own habit ("refused rather than guessed").
  4. The no-op log is a twelve-line class, NoopLogFactory, returning a Log whose methods do nothing. The run record and the pane are still the evidence. QuickFIX/J ships no null log. Its ScreenLogFactory with everything off still formats the line before deciding not to print it.
  5. Both factories are chosen once, in FixConnectionManager's init, and passed on to VenueSessionProvider unchanged. clearStoreFiles() is skipped for a memory store. The venue path already takes the factories as parameters. Choosing them in one place means an acceptor profile set to MEMORY gets it for every client session it creates.

#43  The load run

One feature, two parameters

A scenario step sends and then expects. A load run issues, and the accounting happens afterwards over the whole population. Burst and sustained rate are the same run with a different pacer: a burst is "issue N, as fast as the lanes carry", a rate is "issue at R per second for D, on a schedule". Everything downstream of the pacer is identical, which is why this is one feature.

Where I would sharpen the issue

The acceptance criteria hold. These are the places where the implementation should differ from the obvious reading, each with the reason.

  1. Per-message resolution is string substitution, not the expression engine. A template is compiled once into literal segments and slots. Slots for ${messageIndex}, seeded values, ${uuid} and ${utcnow} are filled per message. Kotlin expressions are evaluated once per lane at prepare time, and the report names which tags were per-message and which were fixed. The JSR-223 engine is one shared object, not thread-safe, and costs milliseconds. At 500/s it is the whole budget. The acceptance criterion about "an expression in every field" is met by making the per-message path cheap by construction.
  2. ${sessionIndex} is the profile slot, as a fan-out lane defines it, not the position in the logged-on list that Bulk Send uses. Two-phase runs address what the first run created. That only works if lane 12 is the same client on both runs.
  3. "Issued" is three numbers. Requested, handed to the engine (sendToTarget returned true), and left the socket (SEND stamps carrying the request tag). Completeness is judged over the last one. The gap between them is FixTool's, and the issue's last criterion asks for exactly that gap to be visible rather than hidden in a flattering total.
  4. The pacer never skips a scheduled message. It runs late, catches up, and the report gives the lag spans: when it fell behind, for how long, the minimum achieved rate, the maximum lag. Holding rate by issuing fewer would put a second unknown into every downstream count. Lag is tool-owned and round trip is venue-owned, so they are reported side by side and never summed.
  5. The record does not keep every message. It keeps the report, the wire of every unmatched request (capped at 1,000 with a count of the rest), and fifty specimen pairs. A 300,000-message record is the disk problem #42 removes, moved one directory over. The unmatched requests are the evidence anyone actually opens.
  6. The correlation tag is inferred from the template when --match is not given: the first standard correlation tag the message carries, on both sides. A NewOrderSingle with tag 11 wants 11 to 11. Making the common case say nothing keeps the CLI to the two lines the issue proposed.
  7. A load run is not a run set. It has no steps and no ScenarioResult. It gets its own record under loads/, its own document, and Recent lists both kinds by time. Wrapping the counts in a fake step would make every downstream reader special-case it. What is shared is shared as functions: Distribution, the JUnit helpers, openLanes, Lane.seed, the far-end notice.
  8. Two doors, one dialog. The Message Editor gets a Load button beside Send to all, because the template lives there. The rail's Run menu gets "Load run…" beside "Fan out over sessions…", because that is where people look for run modes. Both open the same dialog. The rail's menu is scenario-typed and a template-typed item is a small impurity. It is worth it: fan-out is the feature people will reach for first and be disappointed by.

How the template is compiled

Today every ${…} in a message takes the same road. The shorthand expander rewrites ${uuid} into UUID.randomUUID().toString() and ${utcnow} into a LocalDateTime call, then the evaluator looks at what is left: a bare name is a map lookup, and anything else, including those rewritten generators, is handed to one process-wide Kotlin script engine inside a synchronized block. The file's own KDoc has the costs: about 140ms to construct the engine, about 1.4s for its first evaluation while 11,000 classes load, and 44 to 82ms for every evaluation after that. A compiled-script cache was tried and refused because a cached script returns the bindings it was compiled with. An engine per thread was refused because it multiplies the start-up cost by the lane count and still costs 50ms per call.

For a click that is invisible. For a load run it is the whole budget. A burst of 4,000 with one generator per message would spend four minutes preparing a message that should leave in under a second, and a rate of 500 per second allows 2ms per message with everything queued behind one lock. So the load run reads the template once, before the clock starts, and sorts every field into one of four kinds.

A template whose per-message need is anything other than an index, a seed, an id or a timestamp is asking for something a load run should not be doing.

Where the report shows up

One record, three ways to read it. Every run, however it was started, writes load.json under loads/<id>/ in the workspace. The screen, the files and the control surface are all views over that one record, so a run started from the command line overnight is the same document in Recent the next morning, provided both point at the same workspace.

The command

fixtool load <template> --profile <name> (--count <n> | --rate <r>/s --for <d>) [options]

  <template>             a saved message's name or id, or a path to a .fix file holding one message
  --profile <name>       the multi-session initiator profile whose lanes issue
  --count <n>            burst: issue n messages as fast as the lanes carry them
  --rate <r>/s --for <d>  sustained: issue r per second for d (90s, 10m)
  --settle <d>           wait this long for replies after the last send (default 60s)
  --listen <profile>     also match replies landing on this profile's sessions (repeatable)
  --match <req>=<rep>    request tag to reply tag (default: the template's first correlation tag, both sides)
  --reply-type <35>      count only replies of this MsgType as answers
  --set <k>=<v>          seed a value into every message's scope as ${k} (repeatable)
  --store file|memory    message store for this run's sessions (default: the profile's)
  --log file|none        message log for this run's sessions (default: the profile's)
  --strict-rate          exit 1 on a rate shortfall, not only on unmatched replies
  --json <file>          write the load report
  --junit <file>         write one <testsuite> with three cases: completeness, rate, tool
  --home <dir>           read profiles and templates from <dir> instead of ~/.fixtool

Exits 0 when every message that left the socket was answered and the tool stayed out of the way.
Exits 1 when anything was unmatched, when the tool limited the run, or on a shortfall under --strict-rate.
Exits 2 when it could not be run: no lane logged on, memory store without Reset on Logon, template not found.

Open questions, each with a recommendation

  1. May a load run use a profile whose sessions are already open in the app? Recommend: yes, and it claims them the way a fan-out claims its lanes. A scenario on those sessions is refused while the run holds them, with the run named in the refusal.
  2. What happens when one pacer thread cannot prepare fast enough for the requested rate? Recommend: preparation runs ahead on its own thread into a bounded queue of ready messages, about two seconds deep. If the queue runs dry the pacer records lag like any other cause, so the report still says where the tool fell short.
  3. Do the listen-only sessions' own outgoing messages count as issued? Recommend: no. Only the issuing lanes' SEND stamps count. A drop-copy session's heartbeats and any manual send during the run stay out of the total.
  4. Should a burst be allowed to exceed the pane queue's floor of 20,000? Recommend: allow it and say so. A burst of 40,000 will discard from the pane on a slow drain, which the tool block reports, while the matcher stays exact because it never went through the pane. That is the point of putting the matcher on the stamps.
