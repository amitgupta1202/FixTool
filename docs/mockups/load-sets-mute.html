Muting a Phase

A phase of a load set can be parked: it keeps its template, its profile, its shape and its place in the order, and the set skips it on every run. Any phase, not only the last, with one refusal for the one case the tool can prove is broken.

A three-phase set is authored once and then run for weeks, and for stretches of that time one of its phases is in the way. The venue leg it issues on is down. The failure being chased is in phase 2, and phase 3's sixty-second settle window is noise. The set has to be run without the phase and then with it again, and today the only way is to delete the phase and author it back, or to keep a second copy of the set that drifts from the first.

The word already exists. A scenario step is muted (ScenarioStep.muted, Scenario.kt:171: "parked, not deleted"), and so is an example row. The runner skips a muted step entirely, the editor dims it and marks it MUTED, the rail draws ⊘ where the verdict glyph would go, and the file carries "muted": true only on the step that is. A phase is the third thing that can be parked, and it takes the word, the glyph and the file key as they are.

One worked example throughout. The bundled RFQ round trip, as it ships in load-sets/rfq-round-trip.json. Phase 1 asks for 4,000 quotes and keeps two values off each one, quoteId (117) and offer (133). Phase 2 hits the first 2,000 at 117=${quoteId} 44=${offer}. Phase 3 passes the other 2,000, counting from 2,001, at 117=${quoteId}. Phases 2 and 3 both read what phase 1 kept, and neither reads the other.

Any phase, not only the last

The obvious rule is "only the last phase can be muted, because nothing depends on it". It is safe and it is wrong twice. It forbids muting phase 2 of the RFQ set to bisect a failure, which is harmless because phase 3 reads phase 1 and not phase 2. And it does not make muting phase 1 safe in a set that addresses by derived id (${run}-${messageIndex}), because the tool cannot see that dependency at all, position or no position.

Position is a proxy for dependency, and the set already knows the real dependency graph: captures. A phase that reads ${quoteId} depends on whichever earlier phase keeps it, and LoadSet.problems() already walks that graph to refuse a read before its capture. So the rule is the set's existing rule, applied once more. Nothing dials until every phase is fine, and a set of six must never fail on phase five for something that could have been said before phase one.

The editor

A phase row in the Load sets dialog is a row of text chips: ↑ ↓ edit duplicate. It gains one more, mute, which reads muted and turns amber while it is on. That is the toggle the examples table already uses on a row (ScenarioExamplesTable.kt:224). A muted row keeps its number, its plan line and every other chip, dims its label, and carries the MUTED tag the step editor carries. The footer sentence counts it.

What is checked on a muted phase

The line is resolve, do not judge. The record has to carry the muted phase's plan so a reader can say what would have run, which means the phase has to be a phase. Nothing about how it would have behaved is judged, because it will not behave.

Still refused

  • a label used twice in the set, because the report names phases by label
  • a profile nothing answers to, a template that is not a file and not a saved message
  • a template with no MsgType, or with no tag a reply is matched on, because a plan cannot be built without a match
  • every phase muted: Every phase is muted. Unmute one, or the set has nothing to run.

Not judged

  • the names its template reads, so a muted phase may read a name nothing seeds and block nothing
  • the store sentence for its profile, and its profile does not count toward "every phase already runs a memory store"
  • its own capture claims: a live phase may keep the same name without the duplicate-claim sentence
  • whether its profile has a lane logged on: its lanes are never opened, which is what "the venue leg is down" needs
  • whether its template compiles: the runner stubs it with the template's name and MsgType and moves on

Captures of a muted phase leave the set of names a later phase may read, and they do not claim the name. The precedence is what a reader would guess: seeded, or kept by an earlier live phase, means no refusal at all. Only when neither holds and an earlier muted phase keeps the name does the sentence above fire. A name kept by muted phase 1 and again by live phase 2, read by phase 3, is fine.

The report, at every door

A muted phase is a SKIPPED phase whose note says muted in the set. No new LoadStatus, no schema bump: the note is the distinction, the way STOPPED_NOTE already tells a stopped set from a failed one. Every door already draws a skipped phase, so each one learns one word. The phase keeps its number, so phase 3 is phase 3 in the heading, in the evidence file names and in Compare, which pairs phases by position.

The file

// <home>/load-sets/rfq-round-trip.json, phase 3 parked
{
  "schema": 1,
  "name": "rfq-round-trip",
  "label": "RFQ round trip",
  "seed": { "run": "${uuid:4}" },
  "storeAndLog": { "store": "MEMORY", "log": "NONE" },
  "onFailure": "STOP",
  "phases": [
    { "label": "Ask for a quote", "template": "RFQ Load QuoteRequest", "profile": "RFQ Load Client",
      "shape": { "kind": "burst", "count": 4000 }, "settleMs": 60000, "capture": { "quoteId": 117, "offer": 133 } },
    { "label": "Hit the first 2,000", "template": "RFQ Load QuoteResponse", "profile": "RFQ Load Client",
      "shape": { "kind": "burst", "count": 2000 }, "settleMs": 60000 },
    { "label": "Pass the other 2,000", "template": "RFQ Load Pass", "profile": "RFQ Load Client",
      "shape": { "kind": "burst", "count": 2000 }, "indexFrom": 2001, "settleMs": 30000,
      "muted": true }                                                        // only a parked phase writes the key
  ]
}

Additive and default-omitting, the same bargain as a step's muted (ScenarioCodec.kt:172): a file that never parked anything never grows the key, absent reads as false, and the set file's schema stays 1. Because the flag is in the file, fixtool load --set in a build honours it, and a set checked in beside the code says on its face which of its phases is parked and since which commit.

Not in this work

  • A per-run override. fixtool load --set rfq-round-trip --mute 3, or {"set": "rfq-round-trip", "mute": ["Pass the other 2,000"]}. About thirty lines at the planning door with the same refusals, but it multiplies across the CLI, the API and the Run menu, and nothing asks for it yet. The editor covers the interactive case, and a build that wants a different shape saves a different set.
  • "Run only phase 3 against last night's quotes." Captures live in memory for one run, so a phase alone can never address what an earlier run kept. That is a replay feature, not a mute.
  • A MUTED status. Schema 4 across every reader for a distinction the note already carries. If a reader ever needs it as a field, "muted": true on the phase object is one line in the codec.

Order of work

  1. The flag. LoadPhaseSpec.muted, LoadPlan.muted, the codec's one key each way.
  2. The refusals. LoadSet.problems(): resolve a muted phase, judge nothing about it, drop its captures from the readable set, the two new sentences.
  3. The runner. Open lanes for live phases only, stub a muted phase as skipped with its note at set start, size the capture table over live phases, skip it in the loop before the policy does.
  4. The verdict. MUTED_NOTE, a muted count, and the three places the verdict must look past a muted stub: the first skipped phase, the "nothing judged" test, the phase a STOPPED or FAILED outcome names.
  5. The doors. One word each: terminal, document rail and badge, the list row on GET /load-sets. JUnit and the phase JSON need nothing.
  6. The editor. The chip, the tag, the dimmed row, the footer count, and the refusal under the reading phase.
  7. Words. Help, changelog, a row in the load sets note's Decisions.

Decisions

decidedWhich phases can be muted?
Any of them. Position is a proxy for dependency and the set knows the real dependency graph. The one case the tool can prove is broken, a later phase reading a name only a muted phase keeps, is refused before a lane dials, in the reading phase's voice, naming the muted phase. A dependency through the derived seed is invisible to the tool and the run's report is the answer.
decidedWhat is it called?
Muted, as a step and an example row are. Same word, same MUTED tag, same ⊘ in the rail, same "muted": true written only when set. "Disabled" and "skipped" were both considered: disabled is the acceptor rule's word for a different thing, and skipped is what a failure does to the phases after it.
decidedHow much of a muted phase is validated?
It has to resolve, and it is not judged. Profile, template, MsgType and match tag, because the record carries its plan. Not its template's reads, its store, its captures or its logon, because it will not run. A muted phase whose venue is down blocks nothing, which is the point.
decidedHow does the record carry it?
SKIPPED with the note muted in the set, at its own position. The same stub a policy skip writes, made at set start rather than when reached, so the live document shows it from the first tick. No new status, no schema bump. The verdict counts it apart from skipped so a passed set never reads "1 skipped".
decidedIs the mute in the file or on the run?
In the file. The editor's Run set saves first, so a mute made there is a mute saved. A set checked in beside the code carries it, and a build honours it, the way a disabled test lives in source. A per-run override is cheap to add later and is not added now.
assumedOne refusal sentence per muted phase a template reads, not one per name.
"Reads ${quoteId} and ${offer}, and the phase that keeps them, phase 1, is muted" is one mistake with one remedy. If the existing seed sentence turns out to be one per name, this one follows it, and the mockups above change by a line.
