Load Sets

Several load runs in order, under one seed, with one report. What a set is on disk, how it runs, what it prints at every door, and where it lives in the app, the command line and the control surface.

Most load proofs against a venue are two or three runs that depend on each other. Burst NewOrderSingle, then cancel the same ClOrdIDs. Ask for quotes, then order against them. Today the second run is a wrapper script around fixtool load, and the script owns the seed, the stop rule and the combined report, which are the three things the tool already does well for one run.

Two prerequisites have landed. load.json is already a set with one phase (LoadRecord.kt:17, phases: List<LoadReport>, schema 2), and the refusal sentences live in LoadPlan.problems() with a Surface for the dialog, the CLI and the API (LoadPlan.kt:80). Compare reads the record shape. The previous note sketched an editor and a document to prove the redraw would not have to be undone for sets. This note is the build's spec, and it answers what the sketch did not: how a set runs (lanes, seed, and replies that arrive in the wrong phase), what it reports at each of its five doors, and the two names that have to move before any of it is written.

One worked example throughout. The RFQ round trip against the bundled RFQ venue, five lanes on RFQ Load Client. Phase 1 bursts 4,000 QuoteRequests (35=R, answered by 35=S, matched on 131 QuoteReqID). Phase 2 hits the first 2,000 of them (35=AJ 694=1 naming 117=Q-RFQ-${run}-${messageIndex}, answered by 35=8, matched on 11 ClOrdID, because a FIX 4.4 ExecutionReport carries neither 117 nor 131). Phase 3 passes the other 2,000 (35=AJ 694=6, counting from 2,001, matched on 117 because a QuoteStatusReport carries no 11). Every id is RFQ-${run}-${messageIndex}, so phases 2 and 3 address what phase 1 minted without anything being passed between them. Whether that holds for RFQ in general has its own section.

What a set is

A load set is a named, ordered list of phases. Each phase is a complete load plan except for two things the set owns: the seed and the store choice. Between phases sits one policy: stop when a phase did not pass, or carry on and report every phase.

A phase keeps its own template, issuing profile, listen profiles, match tags, reply type, shape and settle window, because the RFQ example changes four of those between phases and a cancel storm is often shorter than the order storm it follows. The seed is set-level because sharing it is the whole point. The store choice is set-level because ViewModelLoadHost reconnects the lanes to apply it, and applying it per phase would put a logon and a sequence reset in the middle of the set's clock.

A set is a file, like a scenario run set (sets/<name>.json, RunSetStore.kt:57) and like everything else the workspace keeps. It lives beside the records it produces:

Templates and profiles are named, not identified, for the same reason a scenario run set names its scenarios: a set checked in beside the code has to survive a fresh --home. Names resolve at plan time through LoadTemplates.resolve (a path, then a saved message by id or name) and the profile picker the CLI already has, and a name nothing answers to is a refusal that says which phase asked for it. In Kotlin the set is small, and a phase is LoadPlan with the two set-level fields taken away:

data class LoadSet(
    val name: String,                          // also the file: load-sets/<name>.json
    val label: String,
    val seed: Map<String, String>,             // values may be generators; rendered once per run
    val storeAndLog: StoreAndLogOverride?,
    val onFailure: OnFailure = OnFailure.STOP,  // STOP | CONTINUE
    val phases: List<LoadPhaseSpec>,           // never empty
) {
    /** Every phase through LoadPlan.problems(surface), each sentence prefixed by its phase, plus the set's own. */
    fun problems(resolve: Resolver, surface: Surface): List<Problem>   // Problem(phase: Int?, sentence)
    /** One LoadPlan per phase, the seed rendered and shared, ids reserved under one record. */
    fun plan(resolve: Resolver, seedOverride: Map<String, String>, now: Long): PlannedSet
}

data class LoadPhaseSpec(
    val label: String,
    val template: String,                      // as LoadTemplates.resolve reads it
    val profile: String,
    val listen: List<String> = emptyList(),
    val match: LoadMatch? = null,               // null: infer from the template, as today
    val shape: LoadShape,
    val indexFrom: Int = 1,                       // ${messageIndex} starts here: "the other 2,000"
    val settleMs: Long = LoadPlan.DEFAULT_SETTLE_MS,
    val strictRate: Boolean = false,
)

The seed is rendered once, and that changes one thing in the dialog

Today a seed value is a literal. The dialog's "mint a new one" chip writes four hex characters into the field when clicked (LoadRunDialog.kt:680), and the CLI needs run=c118 spelled out or LoadPlan.problems() refuses. That is right for a one-off run and wrong for a file: a saved set with "run": "b7f2" would give every execution the same ids, and the venue would see duplicate ClOrdIDs on the second night.

So a seed value in a set may be a generator, and the set renders its seed once at start with the shorthand renderer the templates already use (${uuid:4}, ${now} and their patterns). A literal renders to itself. The rendered map is what every phase's LoadPlan.seed carries and what every phase's report records, so load.json says "run": "b7f2" and the file that produced it says "${uuid:4}". In the set editor the mint chip therefore writes ${uuid:4} rather than the four characters. The CLI and the API can override a value, which is how a build passes its own number in: --seed run=b4412 makes the build id the run id, and the venue's logs and the build log then agree on it.

What the shared seed does and does not guarantee is worth one paragraph, because it is the whole mechanism. ${messageIndex} is 1-based per phase and independent of the lane (CompiledTemplate.kt:156), so ORD-${run}-${messageIndex} in phase 1 and 41=ORD-${run}-${messageIndex} in phase 2 line up for every message, whatever the lane count. A phase that should address "the other 2,000" says indexFrom: 2001, and its ${messageIndex} counts from there. An id built from ${sessionIndex} lines up only when both phases run on the same lanes, because the pacer deals messages to lanes round-robin. The editor says so under a phase whose addressing tag reads ${sessionIndex} when its profile differs from the phase before it. Nothing else is checked, and nothing needs to be: a set that addresses 4,000 ids the venue never saw is a legitimate test, and the previous note decided that on purpose.

How a set runs

Nothing dials until every phase is fine
LoadSet.problems() runs every phase through LoadPlan.problems() and prefixes each sentence with its phase ("Phase 2 · Hit the first 2,000: the template reads ${desk} and nothing seeds it. Add desk=… under Seed."), then adds the set's own: no phases, a phase label used twice, a template or profile no name answers to, and the store sentence once rather than once per phase. The CLI exits 2 with the list, the API returns it as the error object, the editor shows each under its row. A set of six phases must never fail on phase five for something the tool could have said before phase one.
The lanes are held across phases
LoadRunner.run() opens its lanes at LoadRunner.kt:67 and releases them at :152. The set runner opens the lanes for every profile any phase names before phase 1, with the store override applied once, and hands each phase a host view whose openLanes returns the held lanes and whose release() does nothing. The set releases after the last phase. Opening lazily per phase would put a logon inside the set's clock and draw it on the timeline as phase time. A phase whose profile has no lane logged on is refused before the set starts, with today's sentence.
A phase passes when its exit code is 0
That is COMPLETE and CLEAN, and HELD when the phase is strict about rate. It is the rule fixtool load already exits on, so a set and a wrapper script agree on what "failed" means. Under STOP the phases after a failure are SKIPPED with a note saying which phase failed. Under CONTINUE they run, and the set verdict names the first phase that did not pass.
Stop by hand stops the phase and skips the rest
The running phase ends as STOPPED exactly as a single run does today, the remaining phases are SKIPPED with "stopped", the set is STOPPED and exits 1. LoadReport.verdict already returns 1 for a stopped run and two tests pin it, which the redraw kept for the same reason: a build cannot pass on a run somebody ended by hand.
The record is written after every phase, and every 250ms during one
A set killed at phase three leaves phases one and two complete on disk and phase three as the store already heals it, RUNNING with no live process becoming STOPPED (LoadRecordStore.kt:136). The morning after an overnight set, the answer is in loads/<id>/load.json whether or not the app is still open.
Late replies go to the phase that asked
Against a matching venue this is not a corner case. Phase 1's orders keep drawing fills while phase 2 cancels them, and each fill carries 11=ORD-b7f2-17. Phase 2 matches on 11 and issued 11=CXL-b7f2-17, so today's one-matcher-per-run design would count every one of those fills as a phase 2 stray. The router above offers the reply to phase 2 first (not pending there), then to phase 1, where it is a duplicate of a matched order or a late reply to an unanswered one. StampMatcher gains offer(stamp): Boolean beside the listener it is today, and the set owns the one listener per session. One map lookup per finished phase per reply, on the thread that already does one.

Does it pass for RFQ?

Yes against the bundled RFQ venue, and the reason is worth stating exactly, because it is the reason it would not pass against a production one. The venue was built to be addressable from the seed. Its proposal says so in as many words (docs/rfq-venue-proposal.md:55): "a load run's second phase has to address the quotes the first phase created without having seen them, and a client can only do that if the QuoteID follows from the QuoteReqID it chose." Four choices in that venue do the work the seed cannot:

the venue choseso phase 2 cana production venue
117=Q-${req.131} write 117=Q-RFQ-${run}-${messageIndex} and name the quote it never saw. mints an opaque QuoteID. Phase 2 has to read it off phase 1's Quote.
fixed prices per pair write 44=1.09010 as a literal, and the hit rule accepts it. prices every quote. The hit needs 133 (or 132) off the Quote, and a wrong price is rejected, which the bundled venue also does.
expiry not enforced hit a quote whose 62 passed a minute ago. rejects it. Phase 1's settle window plus phase 2's issue time has to fit inside the venue's validity, and a settle that runs its full 60s on a 60s quote fails phase 2 for the wrong reason.
rejects as 35=AI match on 11 and count a refused hit as unanswered, since a FIX 4.4 QuoteStatusReport carries no ClOrdID. Reply type 8 says the same thing on purpose. the same. This one holds everywhere.

So the honest sentence is: the derivable seed covers the RFQ set against our own venue, and the first two rows above are the "received values" issue. That issue is not a someday. It is what makes an RFQ set run against anything but FixTool's acceptor, and it should be the issue after this one. Nothing in this design has to change to make room for it, and the next paragraph says why.

How the file would grow. A phase gains an optional capture: tags to keep off each matched reply, by name ("capture": {"quoteId": 117, "offer": 133}). The set runner already holds phase 1's matcher for the whole set, and that matcher already pairs every request id with its first reply (it keeps fifty specimen pairs today, StampMatcher.kt:308). Capture keeps two strings per matched index instead: 4,000 × 2 strings, in memory for the set and in the phase's evidence on disk. A later phase reads them as per-message names, ${phase1.quoteId}, resolved by the same ${messageIndex} the id is built from, which is a table lookup in the slot CompiledTemplate already renders per message. The one real design question that issue owns is the missing capture: phase 1 never got a quote for index 1,187, so what does phase 2 send for 1,187? Skip it and report it, most likely. The seed, the phases, the runner and every report in this note stay as they are.

What the RFQ flow changes in this note. Two things, both now in the worked example above.

  • Phase 2 is a QuoteResponse, not an order. The shipped template is RFQ Load QuoteResponse: 35=AJ 694=1 with 117=Q-RFQ-${run}-${messageIndex}, 11=RFQ-${run}-${messageIndex}, 693, the pair, side, size and the quoted price. The venue books it as 35=8 150=F echoing 11 and 693, and the match infers as 11 to 11 (rfq-venue-proposal.md:243). An earlier draft of this note wrote 35=D, which is the FX venue's flow, not this one.
  • A phase can start counting where another left off. There is no cancel in an RFQ flow. What a three-phase RFQ set does is hit some quotes and pass the rest, and with ${messageIndex} restarting at 1 in every phase there was no way to say "the other 2,000". So a phase gets an optional indexFrom (default 1): phase 2 hits indices 1 to 2,000, phase 3 passes 2,001 to 4,000. One integer added to the pacer's counter before LanePrototype.render(messageIndex) (CompiledTemplate.kt:156), shown in the phase row and the report. The order-then-cancel set wants the same thing for "cancel the second half". The pass phase needs a template the example does not ship yet, RFQ Load Pass (35=AJ 694=6 with 117 and 693), matched 117 to 117 because a QuoteStatusReport has no 11, and answered 297=11.

One more thing the RFQ set exercises that the order set does not: the venue has no quote state in its first slice, so it would book the same quote twice and pass a quote it has already booked. The set cannot know that and should not try. It is the second slice of the venue, whenQuote, and when it lands a phase that hits a quote twice gets an AI back and the report shows it as unanswered on 11, which is right.

Two names that have to move first

todaythe problemthe move
--set <k>=<v> Seeds a value on fixtool load (HeadlessLoad.kt:98). fixtool run --set <name> runs a saved set. #45 wants the second grammar on load, and --set nightly would parse as a malformed seed. --seed <k>=<v>, which is what the dialog calls the field and what LoadPlan.seed is named. --set <name> then means the saved set on both commands. For one release --set with an = in its value is still read as a seed, with one line on stderr saying to write --seed. Set names are slugs and cannot contain =, so the two never collide. Surface.CLI's remedy sentence (LoadPlan.kt:67) and the dialog's "Copy as fixtool load" line (LoadRunDialog.kt:700) change with it.
LoadPhase The run's lifecycle: PREPARING, ISSUING, SETTLING, DONE (LoadReport.kt:259), written as "phase" in every phase object and in every GET /loads row. The record's array of set members is phases[]. So phases[1].phase is a sentence nobody should have to read. LoadStage, key "stage". A set member is a phase, because that is what load testers call one and what the issue, the sketch and the on-disk array already say. The reader accepts "phase" for records written before, and GET /loads rows say stage. This is schema 3, with the skipped state and the evidence file names below, and schema 2 has only ever been written on one machine.

The report, at every door

A set's report is the record, and the record is load.json grown by the fields a set has and a run does not: the set's name and policy, the rendered seed, a set verdict, and phases that may be SKIPPED. Five doors read it, and this section shows each one on the worked example with phase 2 failing, because what a set does when a phase does not pass is the interesting part.

The doors

A load run has three doors and a set has the same three. The command line and the control surface are above. The app gets the editor, and the Run menu gets a load group so "Load sets…" has somewhere to be.

The editor is the run-configurations dialog

The sketch drew "Load set…" as a bare editor, which leaves the question of where the saved sets are chosen, duplicated and deleted. IntelliJ answers that with one dialog: configurations down the left, the selected one's editor on the right, Run in the footer. A load set is a run configuration in every sense that matters, so that is the idiom.

The command line

fixtool load <template> --profile <name> (--count <n> | --rate <r>/s --for <d>) [options]   # one phase, as today
fixtool load --set <name> [--seed <k>=<v>]… [--on-failure stop|continue] [--strict-rate] [--json <file>] [--junit <file>] [--home <dir>]

  --set <name>             run a saved load set (<home>/load-sets/<name>.json)
  --seed <k>=<v>           seed a value into every message's scope as ${k} (repeatable);
                           with --set it overrides the file's value, so a build can pass its own run id
  --on-failure stop|continue   after a phase that did not pass (default: the file's, then stop)
  --strict-rate            every phase exits 1 on a rate shortfall
  --junit <file>           one <testsuites> with a <testsuite> per phase; a one-phase run keeps writing one <testsuite>
  --json <file>            the record, the same JSON as loads/<id>/load.json and GET /loads/<id>
  --set <k>=<v>            still read as a seed this release, with a note on stderr to write --seed

$ fixtool load --set rfq-round-trip --home ci/fixtool --seed run=$BUILD_NUMBER --junit reports/rfq.xml
$ echo $?    # 0 every phase passed · 1 a phase did not pass, or the set was stopped · 2 it could not start

Not in this work

Addendum, 2026-09-08. The first two items below moved into the build the same day this note was reviewed. Captured values are what an RFQ set needs against any venue that mints its own QuoteID, and the bundled RFQ venue is being changed to be that venue, so both are in docs/load-sets-impl-plan.md as parts 2 and 3 of one build prompt, after the eight steps here. Their design lives in that file. Nothing in this note changes to make room for them.
  • A later phase reading values an earlier phase received. Its own issue, and the next one: the RFQ section above shows it is what an RFQ set needs against any venue that mints its own QuoteID or prices its own quotes. The capture sketch there is how the file grows without anything here moving.
  • "Only the ids the previous phase matched." Decided against as a default, and when wanted it is a checkbox on the phase, not a redesign. Not built here.
  • A shareable report file. A load proof ends in a document sent to the venue or the desk, and today that is a screenshot of the document or the JSON. The record now holds every number the document draws, so an "Export report…" that renders a record to one HTML file is a renderer and not a schema change. Worth its own issue, and worth doing after this one rather than inside it.
  • A pause between phases. The settle window is the gap, and the case for a second one has not come up. A field is cheap to add if it does.
  • A per-phase store override, for the reconnect reason above. Concurrent phases, because a set is sequential by definition and two things at once is a fan-out.

Order of work

Eight steps, each a commit or a few, on main. Steps 1 to 5 give a build box the whole feature and can be verified with the RFQ venue and no window. Steps 6 to 8 give the app its doors. The order encodes dependencies: the names move before anything is written against them, the record shape before the doors that read it, the runner before the command that drives it.

Decisions

Decided here

decidedHow does --set stop colliding with itself?
The seed flag becomes --seed. It is the field's name in the dialog and in LoadPlan, and it frees --set <name> to mean the same thing on load as on run, which is the grammar a CI author already knows. The old spelling is tolerated for one release when its value carries an =. The alternative, a new spelling for the set (--plan, load-set), would leave the two commands disagreeing about what --set means forever to avoid one release of a stderr note.
decidedWhat is a "phase", given LoadPhase already exists?
A set member is a phase. The lifecycle becomes LoadStage. "Phase" is what load testers call a warm-up or a burst, what the issue and the on-disk phases[] array already say, and what a reader of phases[1].phase would otherwise have to untangle. The rename is small, the reader accepts both keys, and schema 2 has been written on one machine.
decidedHow does a saved set get a fresh run id each time?
A seed value may be a generator, rendered once at set start. ${uuid:4} is the shorthand that already exists, so no new syntax and no "mint" flag. The dialog's mint chip writes the generator into a set rather than four hex characters, the rendered value is what the record carries, and the CLI and API override it so a build can use its own number.
decidedAre the lanes opened per phase or per set?
Per set, the union of every profile any phase names, before phase 1. A logon between phases would be drawn on the timeline as phase time, and the store override reconnects to apply. The phase runner is given a host view whose openLanes hands back what is held.
decidedWhose stray is a reply that belongs to a phase that has ended?
Nobody's. It is offered to the live phase, then to the finished phases, and only then counted as a stray. Against a matching venue, phase 1's fills keep arriving through phase 2, and one matcher per run would count every one of them as a phase 2 stray, which is the number the "nothing matched" diagnosis reads. StampMatcher.offer() beside the listener it is today, and the set owns the listener.
decidedWhat is the JSON a set writes?
The record, at all three doors. --json and GET /loads/<id> move from the bare report to recordToJson, so a set and a run have one shape and the file, the flag and the route agree byte for byte. It breaks a reader of --json's top-level .verdict, one release after it appeared, and the changelog says so.
decidedWhat does the editor look like?
The run-configurations dialog. Saved sets down the left with new, duplicate and delete, the selected set's editor on the right, Run set in the footer. The sketch's bare editor would have needed a second dialog to choose a set. The phase editor is the load run dialog's body in a phase mode, reached by a breadcrumb, so a phase is the thing you already know how to fill in.
decidedDoes a saved set run straight from the Run menu?
Yes, one Load set ▸ item per saved set, because that is what Run set ▸ nightly (12) does and a menu that behaves two ways for two kinds of set is worse than either. A set that would be refused opens the editor on its refusals instead.
decidedCan a phase address part of an earlier phase?
By index range, with indexFrom. The RFQ set forced it: hit the first 2,000, pass the other 2,000, and ${messageIndex} restarting at 1 could not say the second half. One integer on the phase, added to the pacer's counter. Addressing by outcome (only the ids phase 1 matched) stays out, as before.
decidedDoes a one-phase run's JUnit file change?
No. One phase writes one <testsuite> as today, several write <testsuites>, mirroring fixtool run for one scenario and for a set. A 1.17 pipeline keeps its shape.
decidedCan a phase be parked without deleting it?
Yes, any phase, and it is called muted. It keeps its template, its profile, its shape and its place in the order, and the set skips it on every run. Position decides nothing, because the set already knows the real dependency graph: the one case the tool can prove is broken, a later phase reading a name only a muted phase keeps, is refused before a lane dials. Same word, same MUTED tag and same "muted": true written only when set as a scenario step's. See Muting a Phase.

Assumed, cheap to change

assumedNo pause between phases.
The settle window is the gap. A pauseMs beside onFailure is a field, not a design change, if a venue turns out to need one.
assumed--strict-rate on the CLI applies to every phase.
A per-phase strictRate stays in the file for the case where only the soak phase should gate the build.
assumedThe set store is read and written by file, plus two GET routes.
Like sets/. A PUT /load-sets/<name> validated through LoadSet.problems() is cheap if an agent-authored set turns out to be wanted, and is not in the eight steps.
assumedPhases pair by position in Compare.
Sets from the same file always pair right. Two different files pair by position and the deciding rows catch a mismatch, which is the refusal Compare already has.
