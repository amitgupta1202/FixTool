Multi-run scenarios

Yes, it is possible — and three of the four are nearly free in the runner. "Multi-run" is four needs wearing one phrase, and they collapse into a single primitive: a run set that leaves a record.

doc docs/multi-run-scenarios-proposal.md status proposal · revised 2026-08-28 against main @ 21ee1c1 issue #41

The runner is already pure, deterministic and re-entrant: it allocates a fresh variable scope, a fresh consumed-set and a fresh watermark on every call. Running it twenty times in a row is a for loop. What is not a for loop is everything that consumes one verdict — the rail's report, the grid tint, the route into the reconcile viewer, the HTTP call that waits for it — and everything that has to be left behind when twenty verdicts land overnight. That is where the design work is.

Phase 4

They are the same object. A run set is an ordered list of run requests — (scenario, iteration, row, lane) — executed by a scheduler, producing a list of the ScenarioResult that already exists, each written to disk as a run record the moment it lands. Repeat is one scenario N times; a suite is N scenarios once; an outline is one scenario over N rows of a table; fan-out is one scenario over N lanes with concurrency above 1. A matrix is the product, and needs no new concept.

A single run is a set of one. That is the property that makes the whole feature cheap: today's behaviour is the degenerate case of the new one, so no second reporting stack is built and the reconcile viewer keeps working untouched.

// The whole model. ScenarioResult grows two additive timing fields; the per-tag engine does not change.
data class RunSet(
    val id: String,               // also the record directory: ~/.fixtool/runs/<id>/
    val label: String,            // "nightly — 12 scenarios" / "book-a-trade ×20"
    val source: RunSource,        // Saved | Favourites | Filtered | Selected | Repeat | Examples | FanOut
    val entries: List<RunEntry>,  // planned UP FRONT: the queue is visible before it runs
    val policy: RunPolicy,
)

data class RunEntry(
    val scenarioId: String,
    val iteration: Int,                          // 1-based; always 1 for a suite entry
    val row: ExampleRow? = null,                 // the examples row, when it has one
    val lane: Lane? = null,                      // the fan-out lane: slot, title, CompID
    val state: RunState,                        // PENDING | RUNNING | PASSED | FAILED | SKIPPED | STOPPED
    val result: ScenarioResult? = null,        // exactly today's shape (+ durationMs)
    val record: Path? = null,                   // the entry's file, once written
)

data class RunPolicy(
    val stopOnFirstFailure: Boolean = false,
    val pauseBetweenMs: Long = 0,
    val concurrency: Int = 1,          // > 1 only under the disjointness rule
    val isolateIterations: Boolean = true,  // binding = this_run for the run's duration
)

The rail, running a suite

The rail keeps its shape. The header gains a Run ▾ control; the per-row hover Run button is unchanged, because a single run is a set of one. RunStatusLine — which sits above the list today, under the rail's bounded-height rule — becomes the set report while a set runs or is focused: a set line with live progress, a compact click-to-focus list of entries, and today's report for the focused entry.

Selecting a row publishes that entry's result, which is how one report surface serves twelve verdicts. A set publishes nothing global until an entry is focused — a set of twenty must not re-aim the author's open reconcile window twenty times. Where the messages behind a verdict live is a separate question, and the one that decides the design.

The run record — where the evidence livesrevised

This is the question a suite actually asks. Entry 2's setup calls ClearMessages, so the moment the second scenario starts the first one's messages are gone — and even without a clear, a session is a ring buffer of 1,000. By the time a twelve-scenario suite lands, the grid holds the last entry's traffic and nothing else. Eleven reports would point at messages that are not there.

The first draft answered this with references: hold each entry's message objects in memory, in the tab. Review found three things wrong with that, and they point the same way. The overnight suite is answered in the morning, from an app that may have been closed since — references die with the process. Headless runs are the other primary case, and they have no tab. And the references were never as cheap as they looked: the runner keeps no snapshot between polls, and the class the map would key on does not actually promise identity.

So the evidence goes to disk as it is produced, and the tab is a viewer over the record. Three facts from the code make that a serialization of things already in hand:

The report is already JSON. The record's result block is ScenarioReport.toJson(result), verbatim.

Wire already round-trips. wireRaw is on every captured message, and capture-paste already turns pasted wire back into messages the grid can show. The record's grid is that path, over the record's bytes.

Reconcile needs stepId and wireRaw, nothing else. The record's bound index plus the message's raw is the same pair.

Messages are accumulated while the entry runs, by a subscriber on each session's message flow — not by the runner's polls, which keep nothing between them. The flow conflates, which is fine: the buffer evicts one message per arrival, so the recorder loses nothing as long as it looks at least once per thousand arrivals, against an ingest ceiling of about a thousand a second.

Retention is a directory, not a tab. The runs directory keeps the most recent twenty sets and any the author pins; closing a tab releases nothing on disk, and Recent runs ▸ reopens a set the app has since restarted out of. Headless writes the same directory, so a build box leaves the same records a click would.

The run set is a document

ScenarioDoc is the sealed list of what a centre-pane tab can be — an editor or a capture review today. A run set is a third: a viewer over one record directory. Entries down the left, and for the focused entry its steps, its verdict, its variables, and its own message grid re-parsed from the record — tinted exactly as the live grid would have tinted it.

Two surfaces, two jobs, neither lying:

Reconcile, from an entry that ran an hour ago

It works the way it works today, with today's gates stated rather than assumed. The route needs the message with its bytes, the run attributed to a scenario, the scenario still on disk with that step in it, and the step unchanged since the run. A record supplies the first two; the last two are checked against the saved file when the entry is focused, and an entry whose scenario has been edited since says so rather than reconciling bytes against an expectation that no longer exists. Save & re-run from there re-runs that scenario alone, as a new set of one — the old set is a record, and records do not mutate.

What the cap drops

The cap is per entry, in messages, a setting beside the message buffer size. It drops the right ones: every message the report references is kept (bound messages, strays a STRICT verdict named), and the cap falls on the unbound remainder, oldest first. An entry that lost anything says so on its grid header and in dropped.

The rail, repeating one scenario

Twenty rows carrying the same name is not a report. A repeat set collapses to one row per scenario with an iteration strip beneath it, and the numbers that matter to a flake hunt — median, slowest, which iterations failed — sit on the row itself.

Two timing lines, because they answer different questions. The flow line says whether the scenario is drifting: passing twenty times while going from 1.9 s to 8.4 s is something no pass/fail will tell you. The step line — Send to bound reply, measured by the runner — says whether that drift is the venue's or the flow's own.

Starting one

No new taxonomy on the scenario. A set is built from what the rail already has — ★ favourites, the current filter text, an explicit multi-select — and any of those can be saved as a set: a file in ~/.fixtool/sets/, like a scenario, a profile and the view state. A saved set is what the Run ▾ menu lists by name and what CI selects, because CI selects by a name in a checkout, not by a local star file. The repeat dialog carries the one decision an author must see — iteration isolation — and says what isolation does not reset.

Examples — a table, not a second engine

A scenario is already a Scenario Outline. Every step is parameterized, and the single variable scope the runner threads through a run already covers both directions you'd want columns for: a Send puts ${symbol} on the wire, an expectation's reference matcher asserts it came back, and bindAs writes the venue's own choice into the scope for later steps.

What's missing is the table, one runner parameter — and revised two places that must learn about it:

// ScenarioRunner.runIdentified, today (:120, :128)
private fun runIdentified(scenario: Scenario): ScenarioResult
    val scope = mutableMapOf<String, String>()

// with a seed — a row's cells, or a lane's four names
private fun runIdentified(scenario: Scenario, seed: Map<String, String> = emptyMap()): ScenarioResult
    val scope = seed.mapValues { host.resolve(it.value, mutableMapOf(), null) }.toMutableMap()

host.resolve (sends), resolveMatch (bind predicates) and referenceResolver (reference matchers) all read that map already. A cell can itself be an expression, so ${uuid} in a column gives every row its own fresh id. The two things that do not know about a seed: ScenarioResult.variables credits every name to the step that minted it, so a seeded name would be credited to whichever step ran first — ScenarioVariable gains source = ROW | LANE | STEP; and ScenarioAnnotations.unminted() is a regex pass over the steps, so it would flag every column as never minted — it takes the column names as a second input.

From a capture to an outline

Nobody hand-writes the first table. A captured scenario has literals baked into it, so the door is "Extract to example column…" on any value in the editor: the literal becomes ${symbol}, a column appears named through the same mintName capture uses (so it reads symbol, not col1), and the value it replaced becomes row 1's cell. Capture once, extract three values, add rows.

The one thing that must not be allowed

Row 2 fails, the author clicks Accept actual, and the actual carries 55=EUR/USD. Writing that literal repairs row 2 and silently breaks the other seven — the expectation belongs to all of them.

The fix is where the problem is: the run reports its final scope, the diff window shows it as the variables strip, and the gutter already offers $ TRACK where an actual equals a variable's value. On a row entry that offer becomes the default — revised but keyed by the right thing. This table has a row where qty and expectCumQty are both 17; an actual 14=17 equals two cells, and matching by value alone would offer the wrong column. So the repair is chosen by the column the failing expectation referenced (${expectCumQty} on tag 14), with value equality as the fallback for an expectation that referenced nothing. The literal stays available as the deliberate alternative.

Together, or separate?

One run set, two pieces of work. Examples are a third source of entries — a repeat produces N identical ones, a suite N different ones, a table N seeded ones — and past that point every surface is shared. Building a separate data-driven runner would give you a second run report that disagrees with the first about what a failure looks like.

The authoring is genuinely separate work — the table, the editor grid, the extract door, the lints — and none of it blocks the suite. So: shared model, its own phase, and ahead of fan-out, because a QA team gets more from eight instruments through one flow than from fifty sessions through one.

Fan-out: preflight already does this

The substrate is already built and shipped. A profile's sessionCount (initiators only) opens that many sessions on one Connect, and SessionIdentityResolver gives each slot its own identity from a {n}/{nn} numbering pattern or a comma-separated list across SenderCompID, TargetCompID, Username and Password. Where two slots would resolve to the same sender/target pair it derives a distinct SessionQualifier, which is what keeps QuickFIX session ids and message store files from colliding — the genuinely hard part of running fifty clients, already done.

The sessions come out titled LoadGen [1] … LoadGen [50], each carrying its profileSlot. Scenario steps target sessions by title, and withSessions remaps by title. So one lane is literally:

scenario.withSessions(mapOf("QUOTE1" to "LoadGen [7]"))

The connection half is done too, and it works on exactly the principle a fan-out wants. Every run's preflight resolves each session as:

  1. There and ready → use it, touch nothing.
  2. Down, or not there at all → one recovery attempt. connectSession reconnects it through its own profile, or — for a session that doesn't exist — the host strips the [n] slot suffix and connects the profile carrying its name, which creates every slot.
  3. All attempts start before any wait, so slow logons overlap under one deadline; each success becomes a passing connect row in the report, each failure a named, actionable refusal.

And connectProfile is per-slot reuse-or-create in its own right: it revives the group's sessions that are down and fills only the free slots. Connect a 50-session profile that already has 30 up and you get the missing 20 — a top-up, not a duplicate set.

So fan-out gets no connection logic of its own. The one rule that survives from the first draft: never invent a session outside a saved profile. A session is a visible object — identity, connection state, message log, a pane in the grid. A lane conjured outside a profile would be one you can't see, inspect, tint or disconnect.

The one new question

Everything beyond preflight is a capability check on a single field: can this profile open more than one session?

val lanes = when {
    profile == null                        -> Unavailable("no saved profile behind '$session'")
    profile.config.connectionType != INITIATOR -> Unavailable.acceptor(profile)   // binds one port
    profile.config.sessionCount <= 1          -> Unavailable.singleSession(profile)
    else                                       -> Available(profile, profile.config.sessionCount)
}

The second leg, and where disjointness still bites

A one-leg scenario needs nothing more: lanes spread over the group, and that's the dialog. A second session is where a choice appears, because it may have no multi-session profile behind it — fifty client lanes against one shared back-office session.

That pinning is exactly what breaks the licence for running lanes at once: fifty lanes sharing TRADE1 share its message log and its consumed cursor, so lane 12 can bind the reply to lane 30's order, and the report becomes indistinguishable from a venue bug. Refused, with the remedy named — give TRADE1 its own multi-session profile, fan out only the QUOTE1 leg, or set concurrency to 1.

Three things fall out of following today's rule

  • Lanes must be logged on, like Bulk Send's targets — which already takes every LOGGED_ON session, whatever profile it came from. Two different answers in one app to "which sessions does many sessions mean" would be a defect.
  • A shortfall runs, it doesn't refuse. Preflight tops the group up and waits; if the venue lets only 38 of 50 on, the set runs 38 lanes and says so. A load test that won't start because it's twelve short of a round number is one nobody runs.
  • null means this lane's session, and disjointness is checked after that is resolved. revised ScenarioStep's doc says "null = the active session"; resolveSession returns list.firstOrNull(); and runSessions() returns null as its own element beside the named ones. So two lanes whose named sessions are disjoint can both clear and read session 0 through a null-session step — and every scenario captured on an unnamed session has one. withSessions cannot rescue it; it short-circuits on null. So the fix is not a remap: each lane's host carries a default session that null resolves to, and the licence is computed over the sessions the steps will actually touch.

A lane already knows what to call itself

Bulk Send seeds four names per target — sessionIndex, sessionQualifier, sessionTitle, sessionSenderCompID — so 262=MD-${sessionIndex} distinguishes sessions with no ceremony. A lane seeds those same four, into the same scope an examples row seeds — with one correction: Bulk Send's sessionIndex is the target's position in the logged-on list, which changes when a session drops. A lane's sessionIndex is its profileSlot, so lane 7 is LOADGEN07 on every run and in every record. A lane carries its session's identity, a row carries the table's values, an iteration carries neither. One seeding mechanism, one seed argument.

The far end is addressable — it is not freerevised

If the other side is FixTool in acceptor mode, it already opens a pane per connecting client, titled <profile> ← <client CompID>, with its own order book. Fifty LOADGEN{nn} initiators against a FixTool venue produce fifty named panes and fifty books on the other side — so both ends of a lane are addressable by name. What is not free is the venue's throughput: all fifty sessions of one acceptor share QuickFIX/J's single event-handling thread, and every reply goes through AcceptorDispatch's one scheduled thread. Under fifty concurrent lanes an authored delay becomes a floor, and the p95 a lane measures against FixTool's own venue is FixTool's. The dialog says so.

Fifty lanes changes the report, and the evidence policy

Nobody clicks through fifty rows, and keeping every lane's record whole is a different order of magnitude from a twelve-scenario suite's. So a fan-out set flips both: the report is a distribution over step latency, and after the set completes the records are trimmed — failed lanes kept whole, the first passing lane as a reference specimen, the rest reduced to their result and timings.

Automation and CIrevised

POST /scenarios/run given an id alone returns exactly what it returns today — synchronous, unchanged. Given set, ids, repeat, rows or concurrency, it starts a job and returns at once. Every record is the report shape an agent already knows how to read and reconcile from, plus the bytes.

Phase 0 is small and every item in it is a defect or a missing measurement today. Phase 1 makes a set run and leaves a record; Phase 2 makes the record readable in the app — and a suite is not much use without it, so the two ship together or the feature is half a feature. Phase 3 is where the model starts paying for itself. Phase 4 is a load-testing feature that happens to share the model, and should be judged on its own merits when it is wanted — including whether the venue side is meant to be measured or merely present.
