Multi-run scenarios

Yes, it is possible — and two thirds of it is nearly free. "Multi-run" is three needs wearing one phrase, and they collapse into a single primitive: a run set.

branch claude/multi-run-scenario-49qplu doc docs/multi-run-scenarios-proposal.md status nothing implemented

The runner is already pure, deterministic and re-entrant: it allocates a fresh variable scope, a fresh consumed-set and a fresh watermark on every call. Running it twenty times in a row is a for loop. What is not a for loop is everything that consumes one verdict — the rail's report, the grid tint, the route into the reconcile viewer — and that is where the design work is.

Phase 4

They are the same object. A run set is an ordered list of run requests — (scenario, row, sessionMap, iteration) — executed by a scheduler, producing a list of the ScenarioResult that already exists. Repeat is one scenario N times; a suite is N scenarios once; an outline is one scenario over N rows of a table; fan-out is one scenario over N session maps with concurrency above 1. A matrix is the product, and needs no new concept.

A single run is a set of one. That is the property that makes the whole feature cheap: today's behaviour is the degenerate case of the new one, so no second reporting stack is built and the reconcile viewer keeps working untouched.

// The whole model. ScenarioResult, ScenarioReport and the per-tag engine do not change.
data class RunSet(
    val label: String,            // "★ Favourites — 12 scenarios" / "book-a-trade ×20"
    val entries: List<RunEntry>,  // planned UP FRONT: the queue is visible before it runs
    val policy: RunPolicy,
)

data class RunEntry(
    val scenarioId: String,
    val iteration: Int,                          // 1-based; always 1 for a suite entry
    val sessionMap: Map<String, String> = emptyMap(),  // the fan-out lane
    val state: RunState,                        // PENDING | RUNNING | PASSED | FAILED | SKIPPED
    val result: ScenarioResult? = null,        // exactly today's shape
    val durationMs: Long? = null,
)

data class RunPolicy(
    val stopOnFirstFailure: Boolean = false,
    val pauseBetweenMs: Long = 0,
    val concurrency: Int = 1,          // > 1 only under the disjointness rule
    val isolateIterations: Boolean = true,  // binding = this_run for the run's duration
)

The rail, running a suite

The rail keeps its shape. The header gains a Run ▾ control; the per-row hover Run button is unchanged, because a single run is a set of one. What is new sits between them: a set line with live progress, and a compact list of entries above the report that already exists.

The report below the list is the focused entry's report — the same RunStatusLine, reading the same scenarioResult. Selecting a row republishes that entry's result, which is how one report surface serves twelve verdicts. Where the messages behind that verdict live is a separate question — and the one that decides the design.

Where the evidence lives

This is the question a suite actually asks, and the first draft of this design got it wrong. It said focusing an entry retints the live grid. That holds for a set of one and nothing else: entry 2's setup calls ClearMessages, so the moment the second scenario starts the first one's messages are gone — and even without a clear, a session is a ring buffer that evicts at bufferSize. By the time a twelve-scenario suite lands, the grid holds the last entry's traffic and nothing else. Eleven reports would point at messages that are not there.

So the evidence does not stay in the grid. It travels with the entry. Three facts from the code make that cheap rather than a storage project:

FixMessageSession.kt:399
clearMessages

A clear does not destroy messages. It empties the session's deque and publishes an empty snapshot. A FixMessage referenced from anywhere else survives it whole — wireRaw, timestamp and all.

FixMessageSession.kt:397
_messages.value

The published snapshot is already immutable — retained.toList(). Holding a run's messages is holding references, not copying bytes.

FixMessageViewModel.kt:2726
rebindSlot

Reconcile never reads the grid. It finds the failing step's message by scanning _assertionResults for its stepId and takes wireRaw off the key. The only reason reconcile dies after the next run is that runScenarioBlocking wipes that map on the way in.

The whole fix is therefore: stop wiping the map, and keep one per entry. Accumulated during the run, not swept at the end — a sweep after the last step loses whatever the ring buffer evicted mid-run.

data class RunEntry(
    …,
    /** Every message this run saw, accumulated as it ran. References, not copies. */
    val evidence: List<FixMessage> = emptyList(),
    /** What today is ONE global map, wiped by the next run. Per entry, it is the entry's tint. */
    val assertions: Map<FixMessage, StepResult> = emptyMap(),
    val truncated: Int = 0,   // dropped by the cap — reported, never silent
)

The run set is a document

The rail's rule is that everything clickable opens a document tab, never a window, and ScenarioDoc is the sealed list of what a tab can be. A run set is one: entries down the left, and for the focused entry its steps, its verdict, and its own frozen message grid — tinted exactly as the live grid would have tinted it.

Two surfaces, two jobs, neither lying:

SurfaceShowsTint
Session gridnow — live traffic, still arrivingthe last entry that ran on that session, for the messages still in it
Run set tabany entry, from its own evidencethat entry's own assertion map

Reconcile, from an entry that ran an hour ago

It works, and it works today's way. rebindSlot needs a stepId and a FixMessage with wireRaw; the entry's own assertion map has both. So "Reconcile step 3 →" on entry 3 of 12 opens the diff on the bytes entry 3 actually judged, long after entries 4–12 cleared the sessions twice over. Save & re-run from there re-runs that scenario alone, as a new set of one — the old set is a record, and records do not mutate.

What it costs, and what the cap drops

Evidence is references into memory the session was holding anyway; once the session clears, the entry is the only owner. A twelve-scenario suite of ordinary order flow is a few hundred objects. A twenty-times repeat over a quote stream is not — so there is a per-entry cap, and it drops the right ones: every message the report references is kept (bound messages, strays a STRICT verdict named), and the cap falls on the unbound remainder, newest first. An entry that lost anything says so on its own grid header.

Retention is the tab. A set opens a document, the set is held as long as its tab is, and closing it releases the evidence. Nothing goes to disk in Phase 1 — an on-disk run archive under ~/.fixtool/runs/ is the obvious follow-on, and a strictly additive one once the entry owns its evidence.

The rail, repeating one scenario

Twenty rows carrying the same name is not a report. A repeat set collapses to one row per scenario with an iteration strip beneath it, and the numbers that matter to a flake hunt — median, slowest, which iterations failed — sit on the row itself.

That timing line is half the reason to repeat at all: a flow that passes twenty times while drifting from 1.9s to 8.4s has told you something no pass/fail ever will.

Starting one

No new taxonomy. A set is built from what the rail already has: ★ favourites (a local view-state file), the current filter text, or an explicit multi-select. The repeat dialog carries the one decision an author must see — iteration isolation — rather than hiding it in settings.

Examples — a table, not a second engine

A scenario is already a Scenario Outline. Every step is parameterized, and the single variable scope the runner threads through a run already covers both directions you'd want columns for: a Send puts ${symbol} on the wire, an expectation's reference matcher asserts it came back, and bindAs writes the venue's own choice into the scope for later steps.

What's missing is the table — and one line of runner:

// ScenarioRunner.runIdentified, today
val scope = mutableMapOf<String, String>()

// with examples: seed the row instead of starting empty
val scope = params.mapValues { host.resolve(it.value, mutableMapOf(), null) }.toMutableMap()

That's the whole engine change. host.resolve (sends), resolveMatch (bind predicates) and referenceResolver (reference matchers) all read that map already. A cell can itself be an expression, so ${uuid} in a column gives every row its own fresh id.

From a capture to an outline

Nobody hand-writes the first table. A captured scenario has literals baked into it, so the door is "Extract to example column…" on any value in the editor: the literal becomes ${symbol}, a column appears named through the same mintName capture uses (so it reads symbol, not col1), and the value it replaced becomes row 1's cell. Capture once, extract three values, add rows.

The one thing that must not be allowed

Row 2 fails, the author clicks Accept actual, and the actual carries 55=EUR/USD. Writing that literal repairs row 2 and silently breaks the other seven — the expectation belongs to all of them.

The fix is already within reach: the run reports its final scope, and the diff window already shows it as the variables strip. So an accept on a row entry compares the incoming value against that row's own cells and, on a hit, writes ${symbol} — offering the literal as the deliberate alternative rather than the default. It's the same judgement the reference-matcher mint already makes; it just has to be made here too.

Together, or separate?

One run set, two pieces of work. Examples are a third source of entries — a repeat produces N identical ones, a suite N different ones, a table N seeded ones — and past that point every surface is shared. Building a separate data-driven runner would give you a second run report that disagrees with the first about what a failure looks like.

The authoring is genuinely separate work — the table, the editor grid, the extract door, the lints — and none of it blocks the suite. So: shared model, its own phase, and ahead of fan-out, because a QA team gets more from eight instruments through one flow than from fifty sessions through one.

Fan-out: preflight already does this

The substrate is already built and shipped. A profile's sessionCount (1–100, initiators only) opens that many sessions on one Connect, and SessionIdentityResolver gives each slot its own identity from a {n}/{nn} numbering pattern or a comma-separated list across SenderCompID, TargetCompID, Username and Password. Where two slots would resolve to the same sender/target pair it derives a distinct SessionQualifier, which is what keeps QuickFIX session ids and message store files from colliding — the genuinely hard part of running fifty clients, already done.

The sessions come out titled LoadGen [1] … LoadGen [50]. Scenario steps target sessions by title, and withSessions remaps by title. So one lane is literally:

scenario.withSessions(mapOf("QUOTE1" to "LoadGen [7]"))

The connection half is done too, and it works on exactly the principle a fan-out wants. Every run's preflight resolves each session as:

  1. There and ready → use it, touch nothing.
  2. Down, or not there at all → one recovery attempt. connectSession reconnects it through its own profile, or — for a session that doesn't exist — strips the [n] slot suffix and connects the profile carrying its name, which creates every slot.
  3. All attempts start before any wait, so slow logons overlap under one deadline; each success becomes a passing connect row in the report, each failure a named, actionable refusal.

And connectProfile is per-slot reuse-or-create in its own right: it revives the group's sessions that are down and fills only the free slots. Connect a 50-session profile that already has 30 up and you get the missing 20 — a top-up, not a duplicate set.

So fan-out gets no connection logic of its own. The one rule worth keeping from my first draft is narrower than it was: never invent a session outside a saved profile. A session is a visible object — identity, connection state, message log, a pane in the grid — and the evidence design holds references into that log. A lane conjured outside a profile would be one you can't see, inspect, tint or disconnect.

The one new question

Everything beyond preflight is a capability check on a single field: can this profile open more than one session?

val lanes = when {
    profile == null                        -> Unavailable("no saved profile behind '$session'")
    profile.config.connectionType != INITIATOR -> Unavailable.acceptor(profile)   // binds one port
    profile.config.sessionCount <= 1          -> Unavailable.singleSession(profile)
    else                                       -> Available(profile, profile.config.sessionCount)
}

The second leg, and where disjointness still bites

A one-leg scenario needs nothing more: lanes spread over the group, and that's the dialog. A second session is where a choice appears, because it may have no multi-session profile behind it — fifty client lanes against one shared back-office session.

That pinning is exactly what breaks the licence for running lanes at once: fifty lanes sharing TRADE1 share its message log and its consumed cursor, so lane 12 can bind the reply to lane 30's order, and the report becomes indistinguishable from a venue bug. Refused, with the remedy named — give TRADE1 its own multi-session profile, fan out only the QUOTE1 leg, or set concurrency to 1.

Three things fall out of following today's rule

  • Lanes must be logged on, like Bulk Send's targets — which already takes every LOGGED_ON session, whatever profile it came from. Two different answers in one app to "which sessions does many sessions mean" would be a defect.
  • A shortfall runs, it doesn't refuse. Preflight tops the group up and waits; if the venue lets only 38 of 50 on, the set runs 38 lanes and says so. A load test that won't start because it's twelve short of a round number is one nobody runs.
  • null must mean this lane's session. ScenarioStep.session's doc comment says "null = the active session"; resolveSession returns list.firstOrNull(). A footnote today — under fan-out, a scenario captured without naming a session would pin all fifty lanes to session 0, and withSessions deliberately leaves null alone, so the remap couldn't rescue it.

A lane already knows what to call itself

Bulk Send seeds four names per target — sessionIndex, sessionQualifier, sessionTitle, sessionSenderCompID — so 262=MD-${sessionIndex} distinguishes sessions with no ceremony. A lane should seed those same four, into the same scope an examples row seeds. That's where the readings stop being separate features: a lane carries its session's identity, a row carries the table's values, an iteration carries neither. One seeding mechanism, one params argument.

The far end comes free

If the other side is FixTool in acceptor mode, it already opens a pane per connecting client, titled <profile> ← <client CompID>. Fifty LOADGEN{nn} initiators against a FixTool venue produce fifty named panes on the other side — so both ends of a lane are addressable by name, by a step, by a capture, by this dialog. Nothing to build.

Fifty lanes changes the report, and the evidence policy

Nobody clicks through fifty rows, and keeping every lane's messages is a different order of magnitude from keeping a twelve-scenario suite's. So a fan-out set flips both: the report is a distribution, and evidence is kept for failed lanes whole, the first passing lane as a reference specimen, and counts only for the rest.

Automation and CI

/scenarios/run stays byte-compatible: given an id alone it returns exactly what it returns today. Given ids, tag, repeat, stopOnFailure or concurrency, it returns a set — and each element is the report shape an agent already knows how to read and reconcile from.

POST /scenarios/run
{ "ids": ["smoke-nos", "book-a-trade"], "repeat": 3, "stopOnFailure": false }

{ "passed": false,
  "summary": { "total": 6, "passed": 5, "failed": 1, "durationMs": 21840 },
  "runs": [ { "scenario": "smoke-nos", "iteration": 1, "passed": true,
              "durationMs": 1180, "steps": [ … ] }, … ] }   // each = today's report

The CLI closes a gap its own source names: HeadlessRun calls the batch sweep "the strongest driver" and then supports one scenario per process.

fixtool run --all --junit reports/            # every saved scenario, one file each
fixtool run --tag nightly --stop-on-failure
fixtool run book-a-trade --repeat 20 --pause 500ms
echo $?    # 0 all passed · 1 something failed · 2 could not run

Phasing

PhaseContentTouches
1 — Repeat + Suite RunSet / RunEntry / RunPolicy, set-owned run slot, rail Run ▾ and set report, /scenarios/run set mode, CLI --all / --repeat / --tag, a <testsuites> wrapper ViewModel, rail, control, headless. No disk format, no scenario file change.
1a — Watermark fix STRICT's stray scan excludes what predates the run Runner. It is a bug today; ship it with or before phase 1.
2 — The run set document Per-entry evidence and assertions (stop wiping the global map), ScenarioDoc.RunSet with the frozen grid, reconcile from any entry, the per-entry cap ViewModel, rail, documents.
3 — Examples Scenario.examples, the seeded scope, the editor's table and "Extract to example column…", the column lints, row-aware reconcile Model, codec, runner (one line), editor, reconcile.
4 — Fan-out Run slot becomes a per-session-set claim under a disjointness check; the spread/pinned lane dialog over the profile's sessions; percentile summary; failed-lanes-only evidence ViewModel, runner host, rail dialog. No change to profiles or the identity resolver.

Phase 1 makes a set run. Phase 2 makes it inspectable — and a suite is not much use without it: if all a twelve-scenario run leaves behind is twelve verdicts and one session's worth of messages, the eleven failures nobody can look at send the author straight back to running scenarios one at a time. The two ship together or the feature is half a feature. Phase 3 is a load-testing feature that happens to share the model, and should be judged on its own merits when it is wanted.
