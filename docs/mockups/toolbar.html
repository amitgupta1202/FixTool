FixTool · design note · 2026-09-10

Every Button in Its Place

Why the toolbar reads as a list of features rather than a set of controls, and where each of its twenty-four buttons goes: to a tool-window stripe, to the panes it modifies, to a filter row, to a menu bar, or stays.

The toolbar grew one feature at a time. The message editor came first, then scenarios, then the latency panel, then load runs, then the order book, then the trace, and each of them added a button at whichever end of the row happened to be free. The result is a row where the button for a panel that opens on the right sits far left, where Settings sits between two panel toggles, and where Clear all sessions sits between Add blank line and Layout with nothing separating it from either. Every control is a grey icon with a tooltip, so the only way to learn what is a toggle, what is a one-shot action and what is a view setting is to click it and watch what happens.

The kind rule. There are three kinds of control and they must not look alike. A tool window toggle sits on the edge its window opens from and shows open as a pressed tab. A view modifier sits on the thing it modifies. An action on the whole workspace sits in the toolbar. A filter is a fourth thing, a query, and gets its own row that is never hidden while it is narrowing anything.

As built (2026-09-13), redrawn above. The first drawing of this tree had drifted from the app before it was built, and the code is the fact, so the tree now shows what shipped. Quick Connect is Connect and "sessions" is "panes", per the vocabulary sweep. ⌘F became the pane's search and Search all sessions is ⌘⇧F, per the pane grammar. The Filter row went with the amendment that put the filter on the toolbar, so View has no row for it. About FixTool is the system's own on a Mac and is not a row of ours. What was added: the Session menu carries the active pane's actions in the pane header's words, headed by the pane's name because nothing in the split layout says which pane is active; Close all and Close session arm the way their buttons do, and it is one question whichever door asks; Hide all tool windows puts back what it hid, as IntelliJ's does; Add blank line got ⌘B beside its all-panes twin's ⌘⇧B, and Hide protocol tags got ⌘⇧H, not ⌥⌘H, which every Mac application menu spends on Hide Others. The Run menu's first row runs what the chip names, so ⌃R has a row. Every shortcut the window answers is a row's now: the key handler reads the catalogue rather than keeping its own list.

Amended after the first build

Steps 1 to 3 were built and the user ran the app. Two rows had appeared above the panes: the pane bar with the view controls in split layout, and the filter row while anything was filtering. On a tool whose panes are the product, two rows was the wrong trade, and the toolbar's middle, emptied by those same three steps, was the zero-row home the note had walked past. The bottom stripe hung under the window without a frame around it and did not know about the other bottom docks. And a stripe tab is a minimise, so the docks' own minimise chevrons had become a second way to do one thing. Six amendments follow, the sixth from a second review.

The toolbar takes the filter and the view controls back.

No bottom stripe.

The stripe tab is the minimise.

One window per stripe group.

Connect, a sessions group, and a run configuration widget.

The user's second review named three things. Quick Connect is just Connect: the menu picks a profile and connects it, and the chevron already says there is a choice to make. Connect, Disconnect all and Close all are one group about sessions, and Run does not belong in it. And "Run" is confusing because the word names a verb while the menu runs three kinds of thing (a one-off load run, a saved load set, a saved scenario set), so no noun renames it honestly: "Load" would lie about scenario sets. IntelliJ's answer is the run configuration widget, a chip that names the selected configuration with a ▶ beside it, and that is what the toolbar gets.

Step 4 pulled forward.

The labelled chips and the four groups were sequenced after the pane-grammar build because the renames wanted the pane nouns. The labels do not, and an unlabelled icon row was the first thing the user saw as unfinished, so the chips, the dividers and the sentence-case tooltips landed with the amendment. The renames that touch pane twins still follow the grammar build.

  3. Filter row (built, then folded into the toolbar by the amendment). Decisions

decidedStripes, not only a Window menu.
Both. A menu names a panel. A stripe puts the button where the panel opens and shows you it is open without being asked. IntelliJ ships both and so does this, with the stripe as the thing you point at and the menu as the thing you search.
decidedTrace goes on the bottom stripe.
Superseded. There is no bottom stripe. Trace is a tab in the one bottom dock, with its stripe tab at the bottom end of the left stripe.
decidedToggle state is a pressed tab, not a tint.
Pressed tab. A slightly brighter tint on a grey icon is what made the current row unreadable: eight of the twenty-four buttons carry state and none of them announces it from more than a foot away.
decidedClear all stays one click and stays unconfirmed.
One click. It is isolated by two dividers, it is the only warm-coloured control in the row, and its tooltip says "no undo". Reconnecting and re-running are cheap, and a confirmation on the single destructive button would only train people to click through confirmations.
decidedBlank line stays on the toolbar for now.
Stays. It is the one action people press in the middle of doing something else, to mark the moment before they try the next thing. It becomes a candidate to drop as soon as the menu bar gives it a home and a shortcut.
assumed⌘1 to ⌘8 for tool windows.
IntelliJ's numbering, in stripe order, left then right then the bottom of the left stripe. ⌘F stays Search all sessions, which it already is.
assumedOne noun per tool window.
Editor, Scenarios, Detail, Connection, Order book, Latency, Terminal, Trace. "Repeatable Scenarios", "Message Detail", "Latency Stats" and "Trace across sessions" go. A stripe tab has room for a noun and no room for a sentence, and the sentence was only ever there because a tooltip had to carry the whole explanation.
decidedReal estate beats the kind rule.
Placement follows the row count. A rule that costs a permanent row above the panes loses to the empty middle of a bar that already exists.
decidedTwo stripes, not three.
The bottom edge belongs to the docks themselves. Their tabs live at the bottom end of the side stripes, IntelliJ's arrangement.
decidedOne bottom dock.
Everything at the bottom is a tab in it. Tools and documents alike, one height, one tab strip. Full width between the stripes, the side windows end above it.
decidedOne window per stripe group.
IntelliJ's rule. A tab click replaces the group's window, and the layout store keeps three selections instead of eight flags.
decidedHide is the only minimise for a dock.
One gesture per outcome.
decidedDoes the filter row show by default in a fresh workspace?
Superseded. There is no filter row. The filter is always on the toolbar.
decidedConnect, not Quick Connect.
Connect. The menu picks a profile and connects it. Quick said nothing the chevron did not already say.
decidedA run configuration widget, not a Run menu.
The widget. The menu runs three kinds of thing, so no noun names it. The chip names the selected configuration, the ▶ runs it, ⌃R is the shortcut, and while it runs the ▶ is a ■. IntelliJ's widget, in IntelliJ's place.
decidedIntelliJ's arrangement is the default answer.
Where a layout question has an IntelliJ answer, that is the answer unless a FixTool-specific reason is written down here.
openShould the stripes hide when nothing is open?
Default: no. They are how you find the windows, and 26px on each edge is a cheap price for the app telling you what it can show you.
