The Venue Is Not a Session

An acceptor with TargetCompID = * gets a session pane, a session toolbar and a full cell of the split grid, and it is not a session. It is the container the sessions live in. Four ways to fix the category error, and the one worth building.

nothing to put here

Struck-through icons are inert. In RAW mode the venue pane carries eleven controls and four of them do something: connect, move left, move right, close. The filter bar below the header is the worst of the seven, because it draws before the venue check in SplitView.kt:587 and so renders a working-looking regex box above a list it cannot touch.

Which panes earn their cell

Four of the five do. The two client panes and the two venue-side panes are the same conversations from opposite ends of the wire, which is the FIX equivalent of holding the client log and the server log side by side. They carry different sequence numbers, different socket stamps and different latency. That duplication is the point of the tool, not a bug in it.

The fifth pane is the only one that is not a conversation, and it is the only one that is not pulling its weight.

always empty

A venue's own message list cannot be non-empty. QuickFixService.deliver is the single sink, and for a venue every branch routes to a per-client channel.

1 + N, not 2N

The overview is a fixed extra pane, not a per-client one. Against an external counterparty a venue costs 1 + N panes. It is only in a FixTool-against-FixTool test that one client visibly produces two.

odd always wastes

SplitView.kt:87 picks columns from a fixed table and rounds rows up. 3 panes fill 4 cells, 5 fill 6, 7 fill 8. Every odd count leaves exactly one dead cell, in both orientations.

controls elsewhere

Rules and latency, the two things you actually set on a venue, live in the connection profile editor (ConnectionPanel.kt:1559 and :1663). The pane only echoes a status line about them.

one hidden action

Clicking a client row focuses that client's pane. It is a bare Row with .clickable, no hover state, no cursor change, no chevron. An action with no affordance is an action nobody finds.

So the venue pane holds one thing that exists nowhere else in the app: refused logons. QuickFIX/J answers an unrecognised logon with silence, so a wrong CompID, a wrong port and a closed firewall look identical from both sides. That is a strong argument for the information and a weak one for a grid cell.

A  —  Keep the pane, strip the furniture

Gate the seven dead controls on !session.isVenue, move the filter bar below the venue check, and give the pane the controls a venue actually has: stop listening, clear the refusal log, jump to the rules. Make the client rows look clickable.

C  —  The venue is a group, not a pane

Take B's model and put it where the eyes already are. A venue's client panes sit together in the grid under one thin strip that carries the venue's name, port, live count and refusal badge. The strip costs about 28 px instead of a cell, it never leaves the screen, and the grouping states something true: the bottom row is one venue's view of the traffic in the top row.

Four panes, four cells, one strip. The client panes drop the venue prefix from their titles because the strip above them already says whose venue it is, so a narrow pane spends its header on the counterparty rather than on a name repeated four times. The chevron on the strip collapses the whole group when you want the client side alone.

What the strip does that a pane cannot

  • It stays. The refusal badge is next to the traffic, which is where you are looking when a client will not connect. In B that answer is behind a panel you closed to make room for grids.
  • It scales to two venues. Two strips, two groups, unambiguous. Two overview panes in a flat grid are two more cells and no stated relationship.
  • It survives an empty venue. A listening venue with no clients is a strip with no panes under it, reading waiting for a client on 19876. That is a better empty state than a pane with an empty table, and it answers the one thing a pane cannot: the venue is up and nobody has arrived.
  • It states the relationship. A grid of peers says these five things are alike. A group says these two panes belong to that venue, which is what is actually true.

Where I would push back on myself

C is the most work of the three, and the cost is concentrated in one place: SplitView's grid loop is a flat uniform grid indexed by row * columns + col, and grouping means sorting panes by venue and letting a strip span a row. That is a real rewrite of the layout function, not a guard clause. TABS mode needs an answer too, and the honest one is that the strip becomes a header above the grid whenever the active tab is a venue client, which is cheap.

There is also a case for A as a stepping stone, and I would take it, but only as the same afternoon's work rather than as the answer. Gating the dead controls is independent of everything else and makes the venue pane honest while C is built.

D  —  Minimize, and what it must stay aligned with

Minimize is the better version of A+, because the space win arrives with a feature that stands on its own: today the only way to quiet a pane is to close it, and close calls destroy(), which disconnects the session and throws the log away. There is no way to say not now to a pane.

Two designs are possible and only one works here. Collapse in place cannot reclaim anything, because a cell is sized from the row and column weights and never from its content, so a collapsed pane is a header floating in a full-size cell. Minimize out of the grid works: n drops by one and the existing column arithmetic reflows on its own. So a minimized pane leaves the layout and becomes a chip in one strip above it.

The strip is also where the venue lives, minimized by default. One bar, not two, or the space saved goes straight back into stacked chrome.

One object, two densities

The chip I first drew carried a Rules button, a Stop button and two counters the pane did not have, which quietly made the venue two features instead of one thing at two sizes. The contract that fixes it is a single sentence: the chip is a strict subset of the pane. If the chip shows a number, the pane shows it. If the chip offers an action, the pane offers the same action under the same label. Anything that appears only in the chip is a bug, not a feature.

What the chip drops is detail, never capability. And what earns a place at either size follows the rule this codebase already states twice, in the refused-logon list and in the discarded-messages badge: identity and live state always, everything else only when it deviates from boring. A counter that reads the same on every healthy venue is furniture, and the comment on the discarded badge says exactly that.

And the same alignment, upwards

Applying the subset rule found one thing flowing the other way. The one chip state that is not a subset of anything, because the pane cannot need it: a visible pane does not have to announce that Send will reach it. It stays.

Moving a pane, with one hidden

This is the part that breaks quietly if it is done by arithmetic. SessionPanel asks for onMoveSession(index, index - 1), and once the grid is drawn from a filtered list, that index - 1 is a position in visible order while moveSession expects one in real order. Off by however many panes are minimized to the left.

The rule that works: move to the real index of the previous or next visible pane, never to real ± 1. Moving Client C left with B minimized:

real, beforeABCD
visibleACD  ← move C left
real, afterCABD
visibleCAD  as expected

Two consequences worth stating rather than discovering. Move left is withheld at visible position 0, not at real index 0, or the leftmost pane grows a dead button whenever something is minimized ahead of it. And a restored pane returns to its place in real order, which may not be where it sat in visible order when it was minimized, because panes moved around it while it was away. That is the simplest defensible rule and the one I would ship.

The editor link, which is safer than it looks

The send path does not use an index at all. App.kt:1211 passes selectedSession = activeSession, and sendMessage reads _activeSessionState.value, which holds the session object. So reordering and filtering cannot misdirect a send, and a minimized pane remains a perfectly valid target: the message really is sent, really is logged, and really appears when the pane comes back.

What needs care is the parallel index. _activeSessionIndex is maintained by hand alongside the object, and setActiveSession(index) also drives selectedEditorProfile when autoSyncSessionToEditor is on. Hand a filtered index to that function and the editor selects the wrong profile while sendMessage still sends to the right session, which is the worst of both: the header names one counterparty and the wire carries another. Every index crossing the boundary gets mapped, or the callbacks take the session object instead. I would take the object.

Tests to write

Grouped by the thing that would break. The first four are the ones you asked for and the ones I would not ship without.

M1

A minimized pane is still the editor's target.Minimize the active session, then sendMessage. Asserts the message reaches that session, its log grows, and selectedEditorProfile did not change.

M2

Sends while minimized survive the restore.Send three, restore, assert all three are in the pane's grid in order. Proves the pane was hidden and not detached.

M3

Move with one hidden lands where the eye expects.Panes A B C D, minimize B, move C left. Asserts real order C A B D and visible order C A D. The regression that arithmetic-based indexing causes.

M4

Close with one hidden closes the pane that was clicked.Minimize B, close D. Asserts D is gone and A, B, C survive. The silent, destructive failure if indices are not mapped.

M5

Move left is withheld at visible position zero.Minimize A, assert the pane now leftmost offers no move-left. Guards the dead button.

M6

A refused logon reaches a minimized venue's chip.Venue minimized, a client addresses the wrong CompID. Asserts refusedLogons grew and the chip's badge reads it. The one fact that exists nowhere else in the app.

M7

A client arriving on a minimized venue still gets a pane.Venue minimized, a counterparty logs on. Asserts attachVenueClient ran and the new pane is visible, not minimized with its parent.

M8

Closing a minimized venue still closes its clients.Preserves the existing closeSession venue rule, which recurses through isClientOf, when the venue is not in the grid to be clicked.

M9

The FX Venue example opens as four panes in a 2 × 2.The space claim, pinned. Asserts one chip, four cells, no empty cell, and that restoring the venue returns five panes.

M10

Minimized state survives a restart, by profile and not by index.Round-trips through LayoutState. Panes are identified by profile id and slot, because FixMessageSession.id is a fresh UUID each run and a venue client pane does not outlive the process at all.

M11

Every pane is present exactly once after a minimize, reorder and restore.The invariant that catches whatever the enumerated cases missed.

What shipped

A and D, together

Built as described above, verified against the running FX Venue example: five panes exist, one is a chip, four are in the grid, and the layout is a 2 × 2 with no empty cell. While minimized the venue kept its port bound, kept 21 rules live, fired them (2 triggered, 3 sent), recorded a refused logon, and answered Stop from its chip by unbinding the port and dropping both clients. Its own pane held 0 messages throughout, which is the fact that made a grid cell the wrong home for it.

One deliberate trim: no right-click menu. The contract only requires that the chip's actions are a subset of the pane's, and Rules, Stop / Start and Clear refused already are. Close stays pane-only, which is the safer place for something that takes every client pane with it, and restoring the pane is one click. That also avoided introducing a context-menu mechanism to a codebase with no precedent for one.

Three things the build found that the drawings had not. Minimizing must not retarget the editor, and the send path made that free rather than fiddly: sendMessage resolves through the session object, so a minimized pane is a valid target and no index can misdirect a send. The parallel _activeSessionIndex is the hazard, since it also drives the editor's profile selection, so every pane is now addressed by session rather than by index — a stale index does not fail loudly, it closes the wrong pane and disconnects it. And the move arrows were the only text glyphs in a row of icons, so they were the only buttons with no accessible name; they are icons now.

Twenty-two tests: the deviation rule as pure unit tests, the move-and-close bookkeeping against a real view model, the rendered tree for the gated controls and the withheld move-left, and two venue integration tests for a refusal reaching a minimized venue and a close cascading to its clients.

The recommendation

A

Pane, de-junked

Honest but unchanged in shape. The venue still competes with its own clients for a cell, and the odd-count blank stays.

Take it now, as a same-day fix, not as the answer.

B

Rail only

The correct model on the wrong shelf. Live state ends up behind a panel that is shut exactly when the state matters.

Adopt its rail node as part of C, not instead of it.

C

Venue as a group

The venue's clients grouped under it in the grid. The best end state, and the only one that stays unambiguous with two venues, but it needs the grid loop rewritten to span a row.

Later, as an upgrade to D's strip.

D

Minimize, venue minimized by default

One mechanism instead of two rules. Any pane can leave the grid for a chip, the venue simply starts that way, and the space win arrives with the non-destructive quiet that split view has never had. Same 2 × 2 as C, without touching the grid loop.

Build this.

Ship A first, because it is independent and takes an afternoon. Then D, which subsumes A+ by making the venue's missing cell a default rather than a special case in the layout code. Fold B's rail node in alongside, since the rail is the right home for setup and for a venue with no clients yet while the strip is the right home for live state. Keep C in view as the upgrade that makes D's single strip into per-venue groups, and build it when a second venue makes the grouping worth the grid rewrite.

The whole of D's risk is index arithmetic at one boundary, and the four tests that cover it are M3, M4, M5 and M1. The send path itself is already index-free, which is why this is worth doing now rather than after a refactor.
